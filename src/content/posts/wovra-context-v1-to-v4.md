一个 AI Agent 的上下文模型能长出几代？Wovra 的答案是四代，而其中三代已经被淘汰、留在仓库里只作历史取证。这一篇想讲的不是"功能怎么越做越多"——正好相反，它的叙事是**机制越做越少**：V4 干的最大一件事，是把 V3 精心设计的按域重组整段拿掉。

所以这里不写编年史，写**岔路口**。每一代都站在一个分叉上：两条路看起来都合理，我们选了一条，实测之后又退回来。把这些选择摊开，比按顺序罗列特性更能看清这套东西的形状。

## 一、先纠正一条题面

如果照着"V1→V2→V3→V4"往下数，第一反应会把 V1 当成"初代上下文机制"。读文档时我们才发现这个数法本身就错了。

V1 那份文档（`docs/organization-runtime-v1.md`）开宗明义写的是「本文档封的是**不变量**」——它封的不是一个跑起来的机制，而是一组原则；它处理的层也不同：V3 解决的"**一个**上下文怎么不撑爆"是**节点内**问题，而 V1 解决的是"应该存在**几个**上下文"——**节点间**问题。两者根本不在一条轴线上。

真正沿着"节点内上下文"这条轴往下长的，起点是那份已经淘汰的 `docs/context-runtime-experiment.md`——第一次 A/B 对照实验。而 `organization-runtime-v1.md` 是**另一条平行的冻结分支**：多智能体编排，走的是节点间那条线，跟上下文模型是两回事。

多智能体那条线本身有独立的结局——它被一场 Minecraft 复刻实验判死了（等效成本 4.6×、现金 2.4×、墙钟持平、质量只是噪音级），这事在前一篇里已经写过，这里不再展开。这篇只交代它在这张地图上的位置：**它是被冻结的平行分支，不是上下文模型的"上一代"。** 后面再提到它，也只是当一条已经封存的岔路。

这条澄清不是抠字眼。如果按错误的谱系去读，会得出"组织运行时被上下文机制取代了"的结论，而事实是**组织层后来换了个形态重新落地**——它没有作为同步多智能体回来，而是变成单运行时内的分流（注册表 + notify/consult），是水位整理的副产品，不是一场独立的架构革命。谱系划错了，因果就全错。

V1 组织运行时自己把两个禁地写得很硬，值得抄下来当这条分支的墓志铭：**不裁视野、不删部门历史**。它当年想护的东西——"每个上下文有界"、"主 agent 从不做具体工作（真正的理由不是职级礼仪，是**资产保护**：主上下文一旦开始装 46KB 源码，整个架构就退化回单 agent 旧世界）"——后来一条一条都在 V4 里以别的形态活了下来。死的是"同步多智能体"这个形态，不是这些原则。

它当年想实现的东西，读起来其实很有野心：递归的主/子 agent、**原始需求逐字下传**（每层只追加自己的拆解与接口约定，不改写上层的话——防"电话游戏"）、目标下传 / 事实上传 / 方法不进传递、人当根节点（全权、时间最少、系统的职责包括把决策空间整理成"人尺寸"的选项）。这些规则每一条都成立，失败的不是规则本身，是**把它们实现成"同步多智能体"这个形态**——四组并行上下文意味着四份需要协调的前缀、一套跨 agent 的同步协议、以及一份谁都不肯让步的"公共真相"。判死它的不是某条规则错了，是**协调成本超过了隔离收益**。后来 V4 用"单运行时内分流"重做同一件事：共享同一份历史、只按文件切私有细节、谁都不并发执行——把"多智能体"的全部野心，压进一个不需要协调协议的形态里。

## 三、岔路口一：压缩 token，还是降低基座

V1 的时代，整个项目对上下文管理的直觉是一句话：**管理 = 压缩 = token 变少 = 省钱**。

首轮 4 轮 A/B 给了第一次打脸。把四轮的账摊开看得很清楚：managed 输入合计 59,012、baseline 87,659——输入确实省了 32.7%；但 managed 的**思考**（reasoning）合计 27,511，baseline 只有 2,887，输出维度 managed 反超 **83.6%**。总 token 一算，managed 104,086 对 baseline 112,210，只省 7.2%。耗时更难看：managed 1138 秒，baseline 505 秒，**2.25 倍**。

省下来的输入，被两件事买回去了。第一件是"整理调用本身也在思考"——V1 的整理跑在**和主任务相同的模型上、思考开着**，一轮整理烧 3K 思考 token 是常态。V2 的 `context-runtime-v2.md` 把这条教训写成一句很硬的话：

> 越稳定的信息越靠前，越易变的信息越靠后。这比"压缩 token"更本质：**少 token 但破缓存，实际更贵**（V1 实测：输入省 32.7%，总成本只省 7.2%）。

这句话的关键在于后半句——"更贵"不是估算，是实测。压缩省下的 token 是"少花钱"，但你为了压缩在上下文中部改写了字节，从改写点往后的整段前缀缓存全部作废，那些 token 按全价重算。省的是折扣钱，赔的是税基。

到 V3，这条从"感觉"升级成了公式：**每一步等效成本 ≈ 新增 token + 基座/折扣率**。命中率决定**折扣**，基座决定**税基**。同一个实验里两边互相印证：

- baseline（全量回放）证明折扣的威力：R13 单轮名义 592,560 prompt，命中率 99.3%，当轮等效只剩约 5K——因为纯追加结构是完美的前缀缓存布局；
- managed 的高峰轮证明税基的可怕：R15 上下文 66K、命中率 96.4%，当轮等效仍约 118K——**96% 的折扣救不了一个臃肿的税基**。

于是"命中率至上"被判死：

> 命中率至上"是错的——baseline 全量回放命中率高达 99.3%，但臃肿基座上的高命中照样贵。正确的优化对象是**基座**。

这里还藏着一个更细的推理：**整理本身是一种主动的、一次性的缓存破坏**。它故意在装配中部撕开一道口子，换取之后所有步骤的低税基。所以真正的决策点不是"怎么提高命中率"，而是"**什么时候值得主动破坏缓存、破坏后把基座压多低**"。这一句把上下文管理从"省钱技巧"抬成了"调度问题"。

**岔路的选择：不是"压缩 token"，是"降低基座"。** 压缩只是降基座的一种手段，而且是最容易伤到自己的那种。这一条后来成了 V3 封版清单的定调句："基座是主要的成本控制对象，命中率是诊断指标。"

岔路口一还有个尾巴值得记：折扣深度是**服务商参数**。同一套机制换供应商，可能从净赚变净亏。把两组实验的命中/未命中数据当折扣率的函数重算，从 1/40 到 1/5 横跨 8 倍——行业主流的 1/10 下，managed 的等效成本优势是 1.56×（含整理 1.30×）；最深的 1/40 下，含整理开销反而略亏 0.95×。**任何"打平/领先"的结论，不标注折扣深度就是耍流氓。**

补一句后来才暴露的第四项成本：Claude 系定价里还有**缓存写入溢价**（5 分钟档 1.25×、1 小时档 2×）。在这套价目表下，managed 每轮重写装配尾部不只是"缓存失效"，还要按溢价重新写入——"追加稳定尾部"因此多了一条独立的经济学理由。反向地，1 小时缓存写入成了"隔夜冷启动"的解药：中断数小时后的第一轮仍可命中，避免整基座按原价重付。

### 1. 成本必须分三笔账，否则问题问不出来

V1 那场 4 轮实验之所以难看，还有一半原因是**账本身记错了口径**。V1 把"输入 / 输出 / 思考 / 合计"混在一起记，只能看到一个总数，看不出"管理机制自己贵不贵"。V2 因此立了一条新规矩：**成本分三笔账**。

```text
C_total = C_working（干活调用）
        + C_organization（后台整理）
        + C_expansion（展开内容的后续携带成本）
```

为什么非得拆开？因为一个总数回答不了三个不同的问题。"整理值不值"要拿 `C_organization` 单独比"它换来的降档收益"；"优化是不是把负担转嫁了"要看 `C_expansion`（展开当然是省钱的，但如果展开的内容要一路带着走，它的**携带成本**会慢慢还回来）；"干活本身有没有变贵"才看 `C_working`。三笔账一拆，14 轮那 98K 整理费就无处藏身，`C_expansion` 的隐性负担也现了形。

配套的还有两件事。一是**每轮记 `usage` 事件**：`input_tokens / cached_input_tokens / uncached_input_tokens`、`effective_input = uncached + cached/30`、`cache_hit_ratio`，三桶分开累计。二是**"命中率不能当验收指标"**——这一条有实测支撑：同一场里出现过"无原因的全量未命中"（`cached=0`，prompt 81,712 全 miss），而前后 6–9 秒的调用都正常命中，中间**没有任何代码或轮次变化**，紧接着下一次又命中。这是上游节点/路由切换导致的，不是你的代码坏了。所以该看的指标是**"等效未命中"**，不是"命中率"。

这条后来在 V3 里升级成了一条更完整的**延迟账**：基座不只是**成本乘数**，还是**延迟乘数**。真实体感锚点——上下文约 80 万 tok 时首 token 延迟近 1 分钟；压到 1.8 万后约 3 秒（约 20×）。机理是 prefill 时间 ≈ 未命中 token ÷ 吞吐，而缓存折扣保护**成本**却不保护**时间**：TTL 过期、服务重启、空闲时段切换后的冷启动，都要按全量基座重算 prefill。于是 managed 的低基座同时是**延迟保险**——稳态 ~50K 即使冷启动也只有秒级。这条把"降基座"从省钱理由升级成了省时间理由，两者共用同一个决策变量：基座压多低、何时破坏缓存。

## 四、岔路口二：每轮必整理，还是水位批量整理

V2 定稿时，"轮闭合即整理"看起来天经地义——趁热打铁，每轮结束立刻产出一份精修索引，下一轮就有干净的视图可用。

实测账目很难看。14 轮整理共 98,111 token，约 7K 一轮。更扎眼的是单个轻轮：一轮的干活成本 2,816，而这一轮的整理费 3,118——**整理比干活还贵**。把视角拉到整场：这 98K 整理费，几乎把 managed 相对 baseline 在等效成本上的全部优势吃回去了（含管理成本后 B/A 从 1.26× 拉回 **1.00×**）。

V3 于是改成**水位触发的批量合并整理**：轮闭合后不再立即整理，未整理轮的原始体量往上垒，垒过阈值（`WOVRA_ORG_WATERMARK=100k`）才触发一次，把所有未整理轮**一起**处理。收益是双份的——调用次数从 N 轮 N 次降到 1 次，摊薄了"重读整段"的成本；跨轮去重也是天然的，模型每轮重复交代的背景在合并 State Patch 时自动消掉。

顺带修掉的是**同步阻塞**。V1 的整理发生在主对话线程里，用户提问之后得等整理跑完才能继续——这就是 2.25× 耗时的来源。V2 把它挪进**后台单线程 FIFO 队列**：Round 闭合后任务入队，主对话立即继续；`chat` 模式退出时最多等 10 秒（带状态行），没跑完的 Round 标记 `pending`，下次加载会话时**惰性补跑**。两个生命周期（用户请求 / 历史维护）从此彻底分离。

配套还有一条容易忽略的决定：**整理调用关闭思考**（`thinking: disabled`）。V1 实测里思考 token 是成本抵消的主因（27.5K 对 2.9K），而整理本质是**格式化任务**，不需要推理。关掉思考，等于把 V1 血亏的那一项直接砍掉。

还有一条挂在异步管线上的安全阀值得记：**多进程防护**。会话目录加锁文件，第二个进程打开同一会话时显式拒绝（"该会话正在另一个进程中使用"），不做静默单写者假设。异步让"谁在写这份历史"变得不显然，锁是必要的。

**岔路的选择：不是"每轮必整理"，是"攒到水位一次整理"。** 小会话可能全程不触发，整理成本直接归零，早期那种"为了整理而整理"的负优化就消失了。

这里还有一条元教训，写在 v3 里专门叮嘱后来人：

> **水位阈值不要追求理论最优**——不同任务的最优值不同，陷入 70%/72%/68% 的参数调优是局部陷阱。

也就是说，选"水位"这条路，不是选了一个精确的点，而是选了一种"大致合理的区间"。前瞻性决策（什么时候值得破坏缓存）留给下一代——原文那个判据写得很清楚：`整理是否值得 ≈ (基座 − 整理后基座) × 预计未来步数 / 折扣率 > 整理成本 + 缓存重建成本`。

### 1. 一个先决问题：什么才算"一轮"

"轮闭合即整理"也好、"水位批量整理"也好，都建立在一个定义上：**一轮从哪开始、到哪结束**。V2 把这个定义抠得比想象中严：

> **只有 AI 产出最终回答，Round 才闭合。** 中断、异常、无回复的尝试都不闭合——期间的所有用户输入**并入同一个开放 Round**（原文各自保留为事件），跨会话持久化。闭合时才进入整理队列。

这个定义背后是一条很实在的成本账。设想网络中断，用户连发三条"继续"，AI 都没回复，恢复后 AI 完成回答——按朴素数法这是四轮，按 V2 的定义这是**一轮**：四条输入 + 期间所有事件，整理时合并成一条澄清意图。差别在哪？**空转的尝试不再产生整理成本。** 如果每次"继续"都算一轮、都触发一次整理，那三次无回复的输入就要为三次整理付费，而它们其实什么都没推进。把"闭合"锚在"AI 真的答完了"上，等于是让计费跟着**有意义的边界**走，而不是跟着用户的按键走。

这条定义还顺带解决了一个装配一致性问题：开放轮期间，模型看到的是**同一个**在生长的轮，而不是几个破碎的半成品轮。整理永远发生在闭合之后，装订永远发生在轮边界——两件事都对得上。

### 2. 整理不是摘要，是索引

V2 把整理产物的三个字段重新排了一次座次，这件事值得单独说，因为它改变了"整理"这个词的含义。

旧的整理是**摘要系统**：把一轮压成一段更短的话，读的时候只读那段话。新的整理是**索引系统**：

> Original = 事实｜Normalized = 用户到底想干什么｜RefinedIndex = 这一轮发生了什么｜Full = 如果不信，自己去查

四个字段对应四种读者、四个精度层。`Normalized` 是**意图**——用户原话可能零散、随口、带情绪，Normalized 把它澄清成"用户到底想干什么"，注意它**可以扩写**（不是压缩），因为澄清往往比原话更长。`RefinedIndex` 是**过程**——逐事件的一行精修摘要，比如"读取 ICP 源码定位误差来源 / 运行测试 3 个用例失败（变换矩阵初值问题）/ 修改初值估计逻辑 / 重跑全部通过"。`Full` 是**退路**——原始协议消息永不变，谁不信索引就自己去读。

这个改法有个副作用值得记：**`RefinedIndex` 的质量上限由工具截断模板决定**。索引是模型看着 `Truncated` 流写的，如果某个工具的截断行丢掉了关键信息（比如 `run_command` 没留 `exit_code`、`read_file` 没给行数概览），索引就无从写对。所以 V2 专门立了一条守则：每种工具的截断规则（`describe(event)`）**必须有测试覆盖"关键信息不丢失"**。索引系统的天花板，不在这套系统本身，而在它最脏的那个上游。

### 3. 一个靠错误口径做出来的决定

水位这条路有一个凶险的插曲，值得当成"测量骗了决策"的标本。

在早期那份 11 轮对照报告里，曾经得出过一个惊人的结论：baseline 在约 R11 就开始"压缩"了、组织机制"触发得太早"。数字看着很有说服力——触发器是 800K（80% × 1M 窗口），而账本显示水位早就过了线。于是"该不该这么早压缩"被当成一个真问题讨论了。

后来发现，**触发那个"压缩"的水位线，用的口径本身是错的**。当时水位取的是"**累计计费输入**"——也就是每一步都把整段 prompt 重新算一遍、一路累加；而真实的上下文体量是"当前窗口装了多少"。两个口径差多少？修订注写得清清楚楚：

> 当时水位用"累计计费输入"（每步重复计整段 prompt），R10 时已虚增至真实上下文的 **19 倍**（584,946 vs ~30,822），R11 的重活把它推过 800K 即触发。按窗口占用口径，B 的真实上下文峰值 ~330K 从未逼近 800K，**这 11 轮本不该压缩**。

19 倍。也就是说，"baseline 提前压缩了"这个被讨论了几天的现象**根本没发生过**——它是水位线自己算出来的鬼。修复是把口径换成窗口占用（`_baseline_context_estimate`）。这件事的分量比它看起来重：**一个决定（该不该这么早压缩）建立在了一个错误读数上，而那个读数来自一个没人怀疑过的计费口径。** 如果不是有人去核了那个数字的来源，整个讨论都会在一个不存在的现象上空转。

顺带把"压缩成本"这条也一起判了：那次压缩的 5,615 token 花在 R11 闭合之后，而会话到此结束——压缩收益只属于 R12+，**这笔钱实际未换来任何后续收益**。一个由伪影触发、又买不到收益的优化，是这条岔路上最贵的一课。

### 4. 异步不是免费的：批次冻结与惰性补跑

"后台 FIFO 队列"听起来只是把整理挪到别的线程，但它带来了一整类新问题：**整理期间历史还在走，产物回来时已经对不上了**。

V2 的解法是**批次冻结**：触发那一刻，将要整理的那批轮就定死了；产物**按轮键控**（每轮一段），所以整理期间新闭合的轮天然不在产物里——它们全量保留原文、等下一批。异步错位于是不需要任何特例，只是让新轮多等一轮才进批次。

但有两个真风险必须用机械规则封掉：

1. **全局标量被旧快照覆盖**——批次产物按"触发时刻的历史"算，落地时历史已经往前走了几轮，那么 `current_status` / `goal` / `is_done` 这些**单值字段**会用旧结论盖掉新状态。修法是**批次模型只产出 append-only 条目**，标量由代码从"最新一轮"重新渲染。
2. **结案越界**——"关闭"是唯一会**删**的操作，如果它落到整理期间刚加进来的条目上，就是误删。修法是条目带序号，序号 ≥ 批次起点的不可结。

还有一个更隐蔽的：**pending 轮的临时占位**。闭合了但整理没跑完的轮，历史加载时先用 Runtime 机械生成的截断索引顶着（零成本、立即可用，模型不会"看不到"刚发生的事），等整理完成，**在下一个缓存断点批量替换**为精修视图——不单独制造断点。这条和"迟到不出事"的整条纪律是一致的：**快的东西先上，好的东西在下一个合法断点再上，绝不为它单独断一次前缀。**

### 5. 关于"既要详细又要短"：一个不可能的需求

V1 的整理产物里有一个字段叫 `round_summary`，规格原话是"分步高浓度摘要（每步保留结论，可合并，不过度压缩）"。这句话拆开看是自相矛盾的：**要"高浓度"（短）又要"每步保留结论"（详细）**，等于要求一句话承载全部结论。

V2 的处理干净利落：**删掉这个字段**，把它的两种诉求拆给两个专门的东西——`Normalized`（用户到底想干什么，意图层）和 `RefinedIndex`（这一轮发生了什么，逐事件一行摘要）。V2 文档里把整件事重新定义成一个**索引系统**而不是摘要系统：

> Original = 事实｜Normalized = 用户到底想干什么｜RefinedIndex = 这一轮发生了什么｜Full = 如果不信，自己去查

这个改法的妙处在于，它承认了"既要又要"不可满足，然后**不让任何单一产物同时背两个 KPI**。想看意图就读 Normalized，想看过程就读 RefinedIndex，想要原文就 expand。四种读者、四个出口，谁也不必迁就谁。这条思路后来一路长到 V4——V4 的"内容可以丢、存在性不能丢"本质上是同一句话的加强版。

## 五、岔路口三：三档滑动窗口，还是全量常驻 + 单一断点

V2 的装配设计得不含糊：近 3 轮全量原文（档 0），更早的轮次按预算自动降档——档 1 是浓缩视图、档 2 去掉事件索引、档 3 压成一行话题行。预算吃紧就往下滑（预算 = 窗口的 30%，1M → 30 万 token）。这套"三档滑动窗口"在纸面上很优雅：永远把最有用的留在高分辨率，把最旧的压成一行。

实测把它判死了，而且判得特别干净——**命中率 83.7% → 49.9%**。

原因在缓存的三条定律里。前缀缓存只认"尾部追加"：追加免费、从尾部裁剪免费、**改写中前部 = 从改写点起全部作废**。而三档滑窗每轮都在做的事，恰恰是"在装配的中部重新决定哪一轮该降到哪一档"——近 3 轮往前滑一格，就有一轮的档位变了，那一位一变，从它往后的所有前缀全部失效。**它每轮都在装配中部改写历史。**

把失败看清楚：模型每一轮拿到的不只是"新输入 + 旧上下文"，而是一份**被重新排版过的旧上下文**。上一轮 R7 还在档 1（带索引的浓缩视图），这一轮突然变成档 2（只剩意图、索引没了）；R8 从档 2 掉到档 3（一行话题）。从模型的座位往下看，它没觉得自己少读了什么，它觉得**手里的历史在悄悄变形**——昨天还在的索引今天不见了，它只能靠"大概是这么回事"往下推。而站在计费侧，每一次这样的重排版，都让那个从变化点起的整段前缀按全价重算。模型困惑和账单变贵，是同一件事的两张脸。

V3 的修正是一句反直觉的话：**未整理的轮次全量原文常驻**。不做逐轮降档了，让历史老老实实待在装配里，唯一的缓存破坏点只有一个——**整理生效的那一刻**。整理是批量、低频的，把"每轮断一次"变成"水位到时断一次"，命中率的账立刻反过来。v3 的差异清单里把这条记成了封版项：

> 历史三档滑窗（V2 装配遗留）→ **废除**——未整理轮次全量原文常驻，已整理轮次紧凑视图；唯一前缀破坏点 = 整理生效时刻（窗口保底除外）。实测滑窗每轮在装配中部改写历史，命中率 83.7% → 49.9%。

**岔路的选择：不是"按预算逐轮降档"，是"全量常驻、只在整理那一刻断一次"。** 局部看，常驻更浪费——你一直带着一堆本可以压掉的历史在跑；全局看，它把每一轮的缓存断点省下来了。典型的"局部最优害死人"。

这条路上还顺带拿下另一个断点：**提醒信封从"事件之前"移到"绝对尾部"**。todo、TaskState、文件地图都是每轮在变的高频状态，放在当前轮事件之前时，它每变一次就作废其后全部前缀——D 组实证：26 次 todo 变化把某段命中率砸到 **77.5%**，而零变化的段是 99.2–99.5%。挪到尾部之后，状态变化只作废信封本身（约 1-2K），信息与时机完全不变，纯粹是一次缓存布局修正。

## 六、一条贯穿始终的排序原则：把变化频率映射到位置

上面所有岔路都压在同一条底层规则上，V2 把它叫"Context Layout 原则"：**把变化频率映射到上下文位置——越稳定的信息越靠前，越易变的信息越靠后**。依据就是缓存第一性原理：**追加免费、从尾部裁剪免费、改写中前部 = 从改写点起全部作废**。既然"越靠后越可以随便动"，上下文排布就不是内容问题、是**位置问题**；V2 给出的排序是 system 人设 → 历史浓缩视图 → Task State/降档索引 → 当前轮事件 → 新输入，从"几乎不变"排到"每轮追加"。**V3 信封挪尾、V4 文件变更提醒注入轮首、fork 只在轮边界**，都是这条原则的具体化——四代里所有"缓存相关"的修正，做的都是同一件事：**把会变的东西赶出中部**。

有一个反例把这条讲得最透，就是 **"砍开头 = 0 命中"**：受控实验里，纯追加命中 **99.4%**、砍尾部 + 指令仍 **99.6%**，而**砍开头 + 指令直接 0.0%**（26,811 全按未命中价重付）。砍尾部还是前缀，动开头则是**整座楼重盖**——系统提示词放最前、tools 数组恒定、人设永不改，这些"看起来僵化"的规矩都是在保护那个最贵的开头。也正因如此，**在中间删内容又想保住命中是错觉**；唯一合法时机是"换档那一刀"（那时本就要重建前缀）。V4 的折档线、V3 的水位整理，本质上都是"攒够了，合法地砍一刀"，而不是"随时想动就动"。

## 七、岔路口四：按域重组历史，还是取消重组（最大的一次）

V3 封版后，地图上下一个区域是**职责划分**：一个上下文撑不下的时候，凭什么不能有几个上下文？于是有了"分域"——按活着的文件把工作画成一棵树，每个域一个 agent，各有各的视图。

这条路的第一版做得很"完整"：要给每个域**重新切一份历史**，按文件归属把事件块分给各个域，拼出各自的上下文。直到一场真实会话暴露了它的病根。

驱动案例是一次 GAIA 评测加提示词审查——9 轮、11 个活性文件。症状被总结成一句很准的话：**"结构树没问题、上下文不对"**。树画得对，节点对、文件对，但装配出来的上下文就是不对。V4 的意图文档把现状列成了六条**可复现**的失败，共同的病根只有一句：

> 算法之所以要算"块归谁"，纯粹是因为要给每个域**重新切一份历史**。**取消重组，上面六条一起消失。**

六条里最典型的几个：

- **两套真相源**：模型的语义树 vs 代码的机械判据链，同一份历史在两个面板走不同规则。这不是显示 bug，是结构决定的。
- **兜底桶承担"未知"**：环境块、没人认领的文件、保底块、其余——四条路径都落到主 agent，本质是"不知道给谁就给它"。N 个域之后它把分域的收益反向吃掉（本场 Main 装配 14,415 tok = 基准 100%）。
- **"主 agent 不许有文件"的检查被悄悄换窄了**：原来的"事后校验 + 抛错中止"退场，改由 `_bind_files_by_path` 的**构造保证**承担——但那条保证只覆盖**活性文件**，只读/幽灵文件走另一条路，"没域认领就跟轮走"是**渲染期**兜底，不在保证内。本场 R1 的幽灵块就是这么进了 Main。
- **没有"树错了"的机械信号**：唯一的覆盖缺口检查被"兜底给主 agent"静默吸收，树 8 个节点、agent 只有 2 个，系统自己是沉默的。

分域要解决的到底是什么？V4 文档先纠了一个常见误解：**不是省 token，而是"注意力别被污染"**。解 A 问题时带着 B 的一堆内容，真正的代价是**串味**——把 A 的框架和结论套到 B 上。本场就是活标本：模型一边捧着 GAIA 评测那一摊（九个脚本、260 个事件、跑批结果），一边被问"你是不是不知道自己是 Wovra"，它把"测试 Wovra"理解成"搭 harness 去测那个平台"。由此判据从"内容重不重要"改成"**它对当前问题是什么角色**"：

| 角色 | 判据 | 处理 |
|---|---|---|
| 前提 | 丢了这问题本身读不懂（R1–R3 之于 R4–R9 的质问） | **必留**（可压成一行结论/指针） |
| 参考 | 丢了不影响理解、影响结论质量 | 留**指针 + 结论**，细节按需取回 |
| 无关 | 既非前提也非参考 | 不留内容，**但留存在性** |

这条判据叫**不对称原则**（本设计的地基）：**内容可以丢，存在性不能丢**。"不知道它存在"会让模型重新发明轮子、或得出"网上没资料"式的错误结论——我们在检索那条线上刚踩过同一个坑。内容是可恢复的，存在性不可恢复。

V4 的动作因此非常激进：**取消按域重组**。取而代之的是三层结构——

| 层 | 内容 | 谁带 | 变化频率 |
|---|---|---|---|
| **常量** | 工作区、解释器、shell、任务状态 | 系统提示词/信封，全体 | 几乎不变 |
| **共享叙事** | **每轮一段话** + 执行者 + 轮次 | 全体（逐字节相同） | 每轮追加一段 |
| **私有细节** | 自己的工具结果、分析、文件全文、决策 | 只有该域 | 该域干活时才长 |

历史不再按域切片，只有**一份共享的压缩叙事**（每轮一段话，由**执行者自己写**），外加各域私有的细节。写的那一刻用的是轮末装配快照、产物尾部追加——纯追加实测命中 99.4%：每轮只付"指令 + 锚 + 产物"那一小截新增，不重付内容、也不破坏前缀。

"每轮一段话"这条契约有一个硬生生踩出来的教训。为了让产物更短，我们一度把分块地图砍掉，结果"每轮一句话"立刻开始**张冠李戴**：5 个纯对话轮（零工具调用）里有 3 条的产物在描述**别人轮次**的工具工作——"启动 4 题重测跑""停掉 bg-1（exit_code=-9，进程树强杀）""逐行审查 `prompt.py` 并交付 349 行报告"，而那些工作在别的轮。回头看，旧契约里那句"块 ID 与内容必须严格一一对应"不是啰嗦，它是**位置锚**；锚删了，模型就按"这几轮大概讲了什么"重新分配内容。补回机械锚（代码从事件里抽出工具名×次数、读写文件清单、非零退出命令作为**动作清单**）后重跑：告警 13 → 3，零动作轮上的违例 6 → 0。

**岔路的选择：不是"给每个域切一份历史"，是"一份共享叙事 + 私有细节"。** 这是四代里最大的一次取舍：它放弃了"每个域都拿到最贴合自己的高分辨率历史"，换来了"没有第二份需要同步的真相"。取消重组的直接后果是，那六条失败一起消失了——因为它们的病根消失了。

### 1. 每轮一段话：谁写、写多细、怎么保证不写歪

"共享叙事"这个抽象，落到实现上有三个必须定死的细节。

**第一，谁写？答案反直觉——执行者自己写。** 不是另起一个便宜的小模型来"摘要"这一轮，而是**干这一轮活的那个 agent** 自己在轮末写。理由很实在：调用输入就是**轮末装配快照**，本轮事件原样在其中，尾部追加的指令是唯一的新字节——**最高保真、最低成本**。让第三方来写，等于要它先把这一轮重读一遍，多付一次整段输入，还多一层转述失真。

**第二，写多细？粒度是"交棒单元"，不是"轮"。** 一轮 → 一段（一句话，关键数字/路径原样）；但一轮里如果有多次交接（`join_with`），就**每棒一条**，各带自己的执行者。所以"段落"实际切在**参与者**的边界上——**每个参与者只写自己那一棒**，指令里写明"别的参与者的部分由它们各自追加"。渲染上还有个小规则：只有该轮有多条（多棒）或执行者不是 Main 时才显示 `〔执行者〕` 标签（分域前全是 Main，逐轮挂标签只是噪音）。

**第三，怎么保证不写歪？三个字段由代码盖章，模型只填一部分。**

| 字段 | 谁来填 | 为什么 |
|---|---|---|
| 执行者 / 轮次 | **代码盖章** | 不让模型自报身份——本会话的病根就是身份错位，让它自报等于给它一次写错的机会 |
| 一句话叙事 | 模型 | 这是它唯一被信任的部分 |
| 失败与坑 | **代码强制非空** | 本轮有非零退出 / 操作失败 / 拦截，就必须写进去；事实由代码扫成"失败候选"喂给它 |
| 账本增量 | 模型（可空） | 约束/坑/拍板/待决 |

这套分工有个名字叫"**模型写内容，代码保完整**"。它承认一个事实：模型擅长把一堆动作说成一句人话，但不擅长记住"我是谁""这轮有没有失败"。凡是**不能让模型错**的东西，都由代码盖章。同样地，用户原话由代码**逐字承载**，`🎯意图` 降级为"执行者怎么读这条要求"——**不冒充用户意图**，因为本场那次"测试 Wovra → 搭 harness"的方向错误，恰恰出在把模型的读法当成了用户意图。

## 八、岔路口五：按域归属，还是按文件归属

V4 内部还藏着两个更小的岔路，都关于"东西归谁"。

取消重组之后，唯一需要归属的东西变成了**文件**。但 V3 时代留下的问题是：归属的判断依据是什么？"这个文件在不在单独目录里"看起来很自然——`output/gaia/FINDINGS.md` 在 `output/` 下，那就单列一个域？

第一版演练就这么干了，立刻被指出是**过度分域**。原话很准："写这个需要 gaia 的内容，且很多……那这个 agent 不是得频繁与 gaia 交流或者读其文件了"。那个文件要写出来，得读 GAIA 的全部内容，把它单列，等于逼它频繁去读别的域。缺的判据不是"文件在不在单独目录"，而是"**这个域能不能独立接活**"。

修法两条。一是补判据——`docs/`、`output/` 这类**目录名不是职责**，一个文件的产出工作属于谁它就归谁；自查一句"这个域要干活时，是不是得频繁去读别的域的文件？是，就别拆"。二是加一道**零 LLM 的机械耦合检查**：同一轮里一起被碰过的文件，就是"同一域"的证据。对旧树一跑，当场抓到 `⚠「gaia_bench」与「gaia_findings」在 R2 里被一起碰过 → 疑似应合并`——证据是 R2 同一轮里既写了前者的文件、又写了后者的 FINDINGS。修后重跑，顶层域 3→2，节点数 16→2，`completion` 从 3,795 掉到 1,133。

然后是更硬的一条：**文件表必须完整，缺一个就是缺陷，不许兜底给主 agent。** 因为兜底给 main 正是前面那场会话所有毛病的源头之一。已存在但没人认领的文件被写 → **拒绝并叫人**，不设"公共区"这种默认桶。归属的计算也是机械的（`_bind_files_by_path`，按最深的 path 前缀）。同一把尺子还要用在活性文件上——分域落地后立刻查一遍，发现没人认领就记 `split_defect` 并报警，因为"活性文件无人管"本身就是机制问题，不是可以静默兜底的边角情况。

**岔路的选择：判断依据不是"目录结构"，是"能不能独立接活"；归属本身不是语义推理，是文件路径的机械计算。** 这一步把"谁该拿什么"从模型的语义判断里彻底摘出来，交给零 LLM 的代码。V4 的意图文档里还留了一条注解：这套东西默认**粗**，被逼才细——第一次分域时材料少，一两轮里"一起被改"可能只是巧合，拆细就是瞎猜。落地成机械读数就是"自足度"（某域被改过的轮里"只有它自己动"的轮数占比），共现 ≥2 轮且占比 ≥60% 才合并；而且**只算"改"（写/编辑/删），只读不算**——读一个文件说明不了它属于谁，实测就有过"只是 grep 了一下"被当成"单独动过"、把本该合并的两个域钉成两个的教训。

## 九、岔路口六："公共历史是中立历史"，还是"公共就是主的历史"

最后一个岔路埋在 fork 机制里，看着像术语之争，实则是架构洁癖的对决。

V4 里子 agent 有个"fork"语义：未激活的 agent 不持有自己的上下文，看到的就是**公共上下文**；第一次被激活时才从公共上下文 fork 一条自己的线。于是"公共上下文"是什么，就成了必须定死的问题。

一个直觉的答案是：公共上下文应该是一份**中立**的历史，谁都不偏，所有 agent 平等地读它。这个直觉的问题是——它会给主 agent 的历史**剥掉路由动作**（`route_to` 这类调用），因为那是主 agent 私有的行为。而剥掉历史中部的字节，直接踩上前缀硬线：**V2 三档滑窗就是这么被判死的**（命中率 83.7% → 49.9%，见岔路口三）。剥一次路由，就从那个点起重新计费。

V4 选了相反的答案：**"公共上下文"就是主 agent 那条历史。** 路由动作本来就在里面——`route_to` 只是一次普通工具调用，它的 `tool_call` 与回执都落进那一轮的事件流，装配时照常出现，不需要"再加一份"，也不该剥掉。原文写得很直白：

> 别再追求"公共历史是一份中立历史"：它就是**主 agent 的历史**（叙事 + 它自己的路由动作）。**一个定义、一份字节、多个读者**（主 agent 自用、子 agent fork 的基线、回落的目标）——少一份需要同步的真相，就少一类"两边不一致"的 bug。

配套它的是"Main 不干活"这条纪律：主 agent 分域后**不碰任何文件、只路由**——**读也算活**。需要文件内容的活，哪怕只是读一下，也交给那个文件的主人。收益是双份的：公共上下文不被文件正文污染；主人手里往往**已经有**那份内容，省一次读。只有不碰文件的对话（寒暄、澄清、拍板）留在 Main。如果主 agent 还自己干活，它的工作轮就会把任务细节灌进公共历史，那份"叙事 + 路由"就不干净了。为了让"Main 不干活"不被用户需求顶穿，还得留一个出口：无主的活走**就地新建**（`route_to` 给一个保留目标 `new`，复制当前上下文 + 本轮输入交给它），而不是跑一次全量分域。

**岔路的选择：公共历史不追求中立，追求"一份字节、多个读者"。** 反直觉，但和取消重组是同一条思路——真相源越少越好。

### 1. fork 与回落：压缩这件事，只有公共上下文有

定完"公共是什么"，紧接着是一条更细的取舍：**子 agent 自己要不要单独维护折叠线？** 直觉上每个 agent 该有自己的水位、自己的折叠。实测与推演都偏向另一个答案：**折叠这套机制只有公共上下文有**，子 agent 达到水位 → **回落到"当前公共上下文 + 自己的职责"**，像个新的分支，继续往后追加。

好处是**所有 agent 的压缩基线一致**——不会各折各的、越走越偏。代价是回落时它自己的旧轮细节不再留在上下文里，靠三样东西兜：**文件是状态载体**（细节在盘上）、**账本是结论载体**（免裁剪档）、**检索/窗口能取回原文**。这三样恰好是前面几条岔路攒下来的资产，在这里结成了落回机制的安全网。

公共折叠还有第二条触发线：子 agent 因水位要回落时，若公共那条线**已占 40% 水位**（100K → 40K），**先折一次早期内容再让它回落**，给这个 agent 的后续工作留出余量。而且**已 fork 的子 agent 不跟着这次折叠走**（前缀冻结）——公共的折叠只服务**未来的回落与 fork**。

## 十、岔路口七：`expand_history` 一种用法，还是三种

折叠只降分辨率、不删事实，所以必须有取回通道。V2 时代的取回只有一种形态：**展开一轮**（`expand_history(ids, level)`）。

但一轮可以有多大？本场实测给了数——`R2` 一轮 **260 个事件 / 229,285 字符（≈16 万 tok）**。整轮倒出来就是一次灌满上下文，等于把刚压下去的东西又搬回来。于是 V4 把 `expand_history` 改成三种用法：

| 用法 | 调用 | 返回 |
|---|---|---|
| ① 检索 | `pattern="正则"`（可配 `scope` / `source`） | 命中清单 + 总数 + 续取指针，一次只列 5 处 |
| ② 看窗口 | `ids="R3-E02"` + `around="关键字"` | 该处窗口（默认 800 字符，尾部给续读 offset） |
| ③ 看地图 | `ids="R3"` + `level=summary/truncated` | 该轮块视图 / 事件索引（先看地图再取细节） |

三种用法各治一种病：**检索**治"我只记得大概，忘了在哪轮"；**窗口**治"我知道在 R3-E02 附近，但不要整轮"；**地图**治"我要先看看这一轮都发生了什么，再决定取哪块"。一种模式（整轮倒出）做不到这三件事——它对小轮浪费、对大轮爆炸。配套还退役了**轮级 `full`**（改成返回"本轮 N 个事件 / M 字符 + 检索入口"，不再整轮倒出），只保留有界的事件/块级 full（单事件实测 p50 547、p90 1,891、max 15,437 字符）。

有个细节值得单独记：**0 命中必须说清"这不等于历史里没有这回事"**——这和检索那条线上"网上没资料"的错误结论同源。模型拿到"没找到"的红灯，很容易得出"这件事从未发生过"的结论，而真相往往是"换个词就能找到"。

## 十一、岔路口八：V3 的三个"治标"发明

三档滑窗、每轮整理这些"机制级"岔路切开之后，V3 还留下三个更小的发明。它们都没进 V4 的现行形态，但每一个都解决了一类真实的疼——而且它们思考问题的方式，比机制本身更值得记。

**文件地图：让降档历史能被精准定位。** 全量常驻的代价是：某轮一旦被降档，模型就**丢了文件内容**，于是"盲目重爬"——最惨的一次同一个文件被读了 39 次。V3 的修法是往装配里注入一张**文件地图**（对降档历史里出现过的文件列出"**路径 + 写/读轮次**"），模型因此知道"`src/icp.cpp` 在 R3 和 R7 被写过"而不是"我大概在哪见过它"。效果 39 次重读 → **3 次读取**——正好理论最小值。这一刀本质上是把"存在性"重新塞回上下文：降档可以丢内容，但不能丢"这东西在哪被碰过"。它后来在 V4 长成了**执行者索引**（不只记"文件被哪些轮碰过"，还记"谁碰过哪些文件"，零 LLM、从分块直接算、不采信模型说法），和职责表形成"声明态 vs 事实态"的对照——两者对不上本身就是信号。

**锚点自愈：把"未命中"变成一次可修正的提示。** `edit_file` 原先找不到要改的文本就报错，模型只能整文件重读。V3 把它做厚——未命中时给出**最接近内容的行号**，成功时回显改动行号，文件不存在时报出解析路径。旧版只说"没找到"，新版给"最接近的是第 145 行"，模型一次就能修正。实测里"一轮 6 次失败"的主因就是这种定位失败，锚点自愈之后从"重爬"降成"微调"。它的价值在于把错误从**终止信号**改成了**修正信号**：同样的失败率，省下来的不是一次调用，是整条重读链。

**信封移到绝对尾部。** `runtime-reminder` 信封里装的是 todo、TaskState、文件地图这些**高频变化**的状态，原先放在当前轮事件**之前**——它每变一次，就从那个位置往后的整段上下文全部作废。D 组实测：**26 次 todo 变化把某段命中率砸到 77.5%**，而零变化的段稳在 99.2–99.5%。修法是把信封挪到**绝对尾部**，状态变化从此只作废信封本身（约 1-2K），信息和时机完全不变。它和 V4"文件变更提醒注入轮首、轮内冻结"是同一条纪律的两端：**高频变化的东西，要么放在尾部追加区，要么放在轮首的一次性区，永远别放在中间。**

## 十二、那些彻底放弃、再没回来的

四代里最值得列成一表的，其实是**放弃清单**。这些都是明确判死、没有以任何形式回归的东西：

- **轮内折叠（50 事件软上限）**——废除。它把模型同一轮里刚读到的文件内容也折成一行索引，诱发"读 → 折叠 → 失忆 → 重读"的死循环：40 步上限内 39 次 `read_file` 重读同一文件，只完成 3 个 `edit`。
- **2KB 的 `SAFE_RESULT_LIMIT`**——废除。这把"锁孔"让 `expand_history` 的承诺根本无法兑现：模型正确地判断出"完整原文"对一个 19KB 的结果不可得，于是 0 次调用展开、只能一寸寸蹭文件。11 次读取全部沉没、零产出。三代机制对同一任务的实测形成一条干净的对照线——折叠时代 39 次重读、2KB 时代 11 次全沉没、**零截断后 3 次读取一轮完成**（理论最小值）。
- **`round_summary`（既要详细又要短）**——V2 删除。这个字段本身就是个内在矛盾的自述：摘要既要详细又要短，等于要求一句话承载全部结论。
- **三档滑动窗口**——废除，见岔路口三。
- **`auto-promote`（按相关性自动升档）**——**从未启用**。原文的口径是"默认关闭，由实测数据决定"。它被 V4 的检索模型取代了。
- **embedding / 聚类 / 向量库**——**明确拒绝**："先不引入"。这一点值得单独说一句：一个专门做上下文管理的项目，**主动拒绝了向量搜索**。理由是当时的"分簇"用时间邻近 + Normalized 意图 + 状态字段就够，犯不上为它提前引入一套向量基础设施。
- **硬性 15 步预算**——被数据否掉。小轮命中率只有 69.8%（主 agent 6 小轮） vs 大轮 98.3%，"轮边界重建 ×2.7"这笔预算税不划算。改成**里程碑驱动的轮**：轮长由派发时写明的检查点定义，步数上限退化成安全网。
- **两层理论形式化的 plan → todo 工具**——先被否，后以 `depth≡1` 的形态重新落地。
- **主不做活 → "留痕/配置类域一律不建 agent"**——加了又被用户撤销（"理解偏了"，用户可以有一个 agent 专门写报告）。

倒数第二条（拒绝向量库）和倒数第四条（15 步预算被否）是同一种气质：**不是"这个想法不够先进"，而是"这个想法的收益不配它的成本"。** 这是整份材料里最像工程判断的地方。

## 十三、一条贯穿四代的主线：四条生命周期

放弃清单很长，但有一条**拆分从没被放弃过**——它从 V1 的实验文档一路活到 V4 的现行机制，四种机制换了一茬又一茬，这个骨架纹丝不动。V2 文档把它的原始形态写得最清楚：

```text
事实存储（History，不可变）
  → 视图生成（Organization，后台维护管线）
  → 上下文装配（Assembly，按变化频率排序的缓存友好布局）
  → 按需展开（Expansion，临时提升分辨率，不改历史）
```

为什么是四条、不是三条或两条？因为它把"历史"这件事按**谁拥有、能不能改**切了四刀：

| 生命周期 | 拥有什么 | 能不能改 | 在哪个时刻活着 |
|---|---|---|---|
| **History** | 原始协议消息（Full） | **永不修改** | 永久，落盘 |
| **Organization** | 派生视图（意图 / 索引 / 状态补丁） | 可重建、可丢弃 | 后台异步，与对话并行 |
| **Assembly** | 这一次请求看到的上下文 | 每次请求重算 | 一次请求的生命周期 |
| **Expansion** | 临时提升分辨率的那一块 | 用完即弃 | 一次工具调用的生命周期 |

关键的两刀：**History 与 Assembly 分开**——"磁盘上的事实"和"这次请求的视图"是两样东西，视图永远可以丢弃重建，事实永不修改。这条一下解决了"压缩到底压掉了什么"的焦虑：压掉的只是视图，事实还在盘上，`expand_history` 随时取回。另一刀是 **Organization 与请求生命周期分开**——整理是**维护任务，不是用户请求的一部分**；用户提问时 Agent 立即工作，与此同时后台 Worker 在维护历史。V1 之所以耗时 2.25 倍，正是因为这两条生命周期当时**粘在了一起**。

为什么这个四分法能活过四代？因为它切的是**问题的固有边界**，不是某种机制的实现细节。无论你用轮摘要还是每轮一段话、用三档滑窗还是全量常驻、按域重组还是取消重组，你都得回答这四个问题：事实存在哪、视图谁来生成、这次装配放什么、要细节怎么取。后来每一代换的只是**这四个格子里的填充物**，格子本身没人动过。V4 的三层（常量/共享叙事/私有细节）填的还是 Assembly 这一格；`expand_history` 的三态填的还是 Expansion 这一格；"原始历史不可变"写进 V3 封版清单第 6 条，仍是 History 那一格。

一条能活过四代的拆分，比任何一代的具体机制都值得记。机制是会对的、也会错的；能对四代的，是对**问题形状**的判断。

## 十四、一个真实的负案例：触发条件在实践中够不着

放弃清单里那些是"机制被否"，还有一类更朴素的问题：**机制没错，触发条件设计得够不着**。

V4 的组织触发设计在水位（`WOVRA_ORG_WATERMARK=100k`）上。那场 35 轮的产品实验（`docs/org-product-35rounds.md`）本想跑到触发分域、验证多 agent，结果**整整 35 轮都没触发分裂**。原因不复杂：分裂判据是"**≥2 个互不重叠的活性文件域**"，而不是"聊了几个话题"。那场会话里操作的文件基本属于**同一个话题**（一个文档域），用户自己也认同"不会触发分裂"，然后在 R27 发现问题——"啊！不触发分裂，我测试什么？"

这条留下一个很实在的教训：**判据锚定在"文件域"上，就别指望靠"聊散"去凑出多个域**。想测多 agent，必须让上下文真实存在多个独立文件域（建 project-alpha / project-beta 两个互不重叠的子工程、交错推进），否则水位再怎么涨，域还是那一个。一个设计得再精巧的机制，如果它的触发条件在真实使用里根本够不着，那它就等于不存在。这也解释了为什么 V4 后来把分域判据从"话题"彻底转向"文件的机械共现"——话题是模型说的，文件是代码数得出来的，后者才配当触发器。

顺带一提，这场实验还照出一个更微妙的坑：**聊天内容会污染分裂模型**。分裂模型的唯一输入是触发时刻的装配快照，而快照里就有你们讨论"会不会分裂""现在有几个域"的那些话。如果讨论里提到了一个现实中并不存在的域，模型可能当真并误判可分。所以验证必须拿 `split_assessment.domains` 和现实 `ls` 一一对照——多出聊过但不存在的域，就是自指污染的实锤。

## 十五、V4 的内部零件：折档线、fork 基线与三条机械保证

岔路口讲完，V4 的骨架还没拆。这一节把它的几个内部零件摆出来——它们都不是"又一个机制"，而是让前面那些取舍**真的能跑起来**的传动件。

**折档线（`_advance_fold_line`）：把"压缩"从整理里独立出来。** V3 的压缩动作只有一种——整理（把轮压成视图）。V4 在它之外多了一条折档线：公共上下文到 **40% 水位**就折叠，**只保留最近 N 轮**（默认 50），更早的轮降成"只留用户输入"。分工是：**整理负责"每轮写成一段话"，折档负责"哪几轮换成段落形态"**，从最老的往近处推、折到目标线以下停手。它还被刻意砍掉了两条触发线——曾经设计过"原文窗口"和"轮次上限"两个**轮号侧机制**，实测代价很清楚：窗口守卫让"会话早期冲过水位"（4 轮顶着 261K）**一轮都折不动**，而且**静默返回**——一个不干活还不说话的守门员，于是被整条删掉，**只剩水位触发折档**。

**fork 基线（`_fork_baseline`）：每个 agent 从哪条线取历史。** 三条规则——fork 过的 agent 走自己那条线（自己干的轮全量原文，**别人干的轮只进一段话**）、**没有产物的轮按原文进**（fail-safe，宁可多花 token 不丢内容）、**未激活和 Main 都按公共上下文装配**（Main 永不 fork）。配套最要紧的一条是**"fork 只在轮边界"**：公共上下文必须是确定快照，轮中 fork 会让同一 agent 的两次调用看到**不同的前缀**，直接撞缓存硬线。

**回落的三个兜底。** 子 agent 达到水位 → **回落到"当前公共上下文 + 自己的职责"**。这一刀切掉了"各折各的"，代价是丢掉它自己的旧轮细节，靠三样兜：**文件是状态载体**（细节都在盘上，重读就拿回）、**账本是结论载体**（免裁剪档，坑/约束/拍板永不丢）、**检索/窗口能取回原文**。三条合起来就是那条纪律的落地——**内容可以丢，存在性不能丢**。

**三条机械保证，让"迟到/缺失"不出事。** 异步系统最怕的不是出错，是**错误在错误的时刻发生**：

1. **档位在轮闭合时判定并落成标志**（`r["folded"]`），渲染只读标志、不每请求重算——note 迟到也不会在轮次中部改字节，且**不需要暂存区 / promote**（这一条顺便删掉了 V3 遗留的 `pending_org` 暂存区 + `_promote_org_results` 生效点）。
2. **一次换到位**：逐轮换会把"还没折的原文"整个重发一遍，又勤又贵。实测换档实价——替换后下一次调用 `prompt 13,908 / cached 7,808`，**断档只花 6,100 tok**，上下文从 ~139K 掉到 ~14K；**换得越彻底越便宜**。
3. **缺 note 的轮不换档**（fail-safe）——按原文顶着，只有成本、没有正确性风险。V4 的口令很直白："**不，失败，就由失败产物顶着，真感觉丢失什么，就自己展开**"——**只要产出了内容就照用**，校验结果**只留痕、不拦、不重发**。**判据不用来制造重发**，这是 V4 对待"不完美产物"的基本态度。

**增量演进：名字即身份，只增不重排。** 早期每次分域都是**推倒重画**——模型重新画树、注册表**按顺序**发编号（第一个顶层 = `A`、第二个 = `B`……）。后果严重：下次节点数量或顺序一变，**编号就换了人**，而路由、账本、执行者索引全靠名字认人，一乱全错还白断前缀。修法（`_land_domains_incremental`）：名字已存在就就地更新（**id 不变**）；名字匹配不上就**按文件重叠 ≥50% 认身份**（机械兜底——实测模型会把 `[现有域]` 的编号当名字用，只认名字会让身份跟着名字一起丢）；都不匹配才发**最小空闲字母 id**，且**不退休任何既有条目**。配套还有一条摆法教训：`[现有域]` 要**名字在前、编号只当附注**——第一版把 `A（名字）` 写行首，模型直接把编号当名字用了。**让模型不犯错的办法，是把正确答案摆成最顺手的那个。**

有了增量演进，"结构树"的定位也变了：**树只描述话题结构、可生长、不重构；分不分裂由代码算**。它有一句诚实的注脚——那条经济算式**只在分域落地之后**被调用，写一行"该不该分"的留痕，**拦不住任何一次分裂**；真正的判据是几何的（某线体量 ≥ 水位 且 活性文件同轮共现 ≥2 簇）。读代码的人容易误以为分裂有经济闸门，其实它是一笔事后记账。

## 十六、这些数字到底能证明什么

那场 14 轮受控实验给出了整篇最常被引用的一组数：名义 token 2,255,448 vs 4,966,437（2.20×）、等效输入 377,668 vs 475,686（1.26×）、含管理成本后 ≈1.00×。但比这组数更重要的是**它不能证明什么**——文档自己列了三条诚实说明：它是**轻中度负载**（峰值只到窗口的 3.0% / 6.6%，**从未触发压缩线**，机制的重度优势没展开）；任务是**工具密集型**（R11 那轮"1.02× 打平"就是 B 多背 30K 历史、A 多读 46KB 文件，两个反向效应抵销）；且 **n=1、无验收快照**。所以"含管理成本 1.00×"这种打平结论**既不能当捷报也不能当丧钟**——它在轻负载下成立，而更重的真实负载里，29 轮生产数据给出的是相反方向（GLM 2.65–2.83×、DeepSeek 空闲 1.48–1.54×）。两个数据集是**同一公式在不同税基下的解**：负载越重，管理越值钱。

实验里还有个插曲能说明"归因"多容易偏：V1 那场 managed 的 R4 输入冲到 **36,304**（R3 才 8,187），被列进"待决策项"。这类尖峰很危险——**是机制 bug 就得改机制，是任务波动改了反而误伤**。文档的处理是先归因、再决定治理，而不是看到尖峰就动刀：**先证明异常是机制产生的，再改机制**，否则你在对着自己的影子优化。

同一种谨慎还出现在"auto-promote 从未启用"上：这个按相关性自动升档的功能从设计之初就写着"默认关闭，由实测数据决定"。它**没有因为"看起来聪明"就被打开**，而是被挂在一个可观测的判据上，等着数据说话。**先把旋钮装上、但别急着拧**——这种克制在这份材料里反复出现。

## 十七、还没定的事

诚实地说，V4 是"现状"不等于"完事"。`context-management-v4-intent.md` §12 把这件事写得很坦白：它给每个话题标了"已定"或"仍待定"，而已定的那批，几乎每一条都带着删除线——**是被推翻过的旧口径**。把这张"已定/待定"表翻一遍，比读机制本身更能看清这个项目的性格。

几条曾经纠结过、后来被拍死的：

- **轮次上限**：先定了一个数，后来**整体删除**（2026-09-18 用户："将 50 轮那个机制彻底删了"）。理由是实测——窗口守卫让"会话早期冲过水位"（4 轮顶着 261K）一轮都折不动，而且静默返回。
- **喂法（全量 vs 截断）**：曾经想做"择路"（小轮走截断、大轮走全量）。按 `甲 < 乙 ⟺ h·C < R` 一算，h ≈ 0.02、C = 200K 时门槛只有 4K——除了一轮比 4K 还小，全量几乎通吃，而那种小轮省下的绝对值只有几千等效 token。**多一条分支不值得，删掉**，统一全量纯追加（实测命中 99.4%）。
- **折扣 h 到底是多少**：端点（`api.commandcode.ai`）**测不出来**——usage / 响应头 / metadata 三处都不给金额，`/models`、`/user/balance`、`/usage` 全 403，`cache_write_tokens` 实测是 `null`。最后以用户口径的 **0.02** 为准。一个核心经济参数，居然是靠外部口径定的，这条值得留个心眼。
- **"问"要不要新造机制**：用户口径是"**别再造新机制**"——复用现成的 `consult`。
- **异步与否**：定成**异步**（触发即入队，批次冻结），后台跑完**阻塞补齐**维护期间闭合的轮。判据同样是"别让历史在整理期间乱走"。

**仍待定的只剩一条**：**并行**什么时候进入设计——真并行时，公共段才需要瘦身。

这条悬着有它的道理。现在的成本论证有一句**前提**：**现在是分流，不是并行**——一轮只有一个执行者。由此"公共段"是**复用不是复制**：每轮只有一个请求，公共段在那个请求里出现一次，逐字节与上一轮相同，跨轮命中缓存。**不是 N 个 agent 各存一份。** 真并行一上来，公共段会同时出现在 N 个请求里、被多台消费者读取，段落该压多狠就成了新问题。所以原文的口径很克制：**并行不提前优化**，先记一笔。

还有两个"知情代价"说明白这份设计的边界在哪：**公共上下文会变得很粗**——Main 不干活之后，公共那条线只长叙事（用户逐字 + 每轮一句 + 账本 + 职责表），从它 fork 出来的新 agent 拿到的是一份**很粗的历史**，上手要多花几次读文件，靠 `expand_history` 兜底（这是"取消重组"这个最大取舍，在 fork 场景里的利息）；**空闲 agent 冻结**——不干活就不发请求，上下文不增长，这既是省钱的，也是"子 agent 不会出现断裂性上下文"的来源。整套东西的**成本中心是"重写公共段"**（整理生效 → 一次全局断前缀），不是"复制公共段"——这个区分决定了优化该往哪使劲。

另外，V4 意图文档自己点出的唯一真风险是**跨线保真度**：分流到另一条线时，追问方手里只有那一段话。出口是"只读文件 + 问"，所以**段落质量比段落长短更重要**。这条不算未决项，算一条时刻得盯住的红线——摊开是两条具体的风险：**总结质量**（执行者自写可能自我美化或漏坑 → 用固定字段 + 代码对账兜，失败项由 `exit_code` 强制写入）和**公共段膨胀**（一句话实际长度约 195 字符/轮，200 轮约 39K 字符 ≈ 30K tok，靠分层压、原文始终在盘上可回取）。还有一条分流架构下**唯一会重复发生的浪费**值得留档：跨域取细节走"问"，一问一答各一小段——但**问的答案必须回写共享段**（至少一行结论 + 执行者 + 轮次），否则下一个空闲 agent 会重问一遍；这条至今仍靠纪律，没有机械保证。

最后必须钉死效度。**V1、V2、V3 全部是淘汰文档**（README 把 V1–V3 框成"历史证据 / baseline 模式已删除"）——这篇讲的整个故事，就是这些被移除的世代怎么被移除的。而所有实验的数字一律是 **n=1、无验收快照**，正如 V3 原文自己写的：

> **n=1、无验收快照**……V3 不能当成"严格实验的性能结论"……它是**经过真实长任务打磨的机制基线**。

这句话我们原样转述，因为它是这篇最该被记住的一句。四代机制的演进，不是四代"被证明"的更优方案，而是四代"踩过真实长任务、留下可复现代价记录"的机制。每一代为什么被删，都是账本说的，不是品味说的。下一代如果有人问"V4 为什么是对的"，答案不应该是"因为它最新"，而是——**因为它删掉的那六条病根，都有实测记录在案。**
