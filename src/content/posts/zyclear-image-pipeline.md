上一篇把参数面板装了起来：37 项参数变成了能点、能改、能下发的控件树。那一篇结尾我说，参数只是配置——**相机真正持续不断往外吐的，是一秒几十帧的图像**。

这一篇就写这条图像链路。主角是 `src/CameraInterface/CameraImageQueue.h`/`.cpp` 这个不到 80 行的类，和它串起来的另外三处：`src/CameraFactory/HikCamera.cpp` 里的采集回调、`src/ViewWidget/` 里的采集线程与显示、`src/Utils/ImageConver.h` 里那座 cv::Mat → QImage 的桥。

一句话先立住：**从 SDK 回调线程到界面那块显示控件，中间隔着三个线程和一条有界队列。界面永远不被采集拖住。**

## 为什么必须是异步的

先算一笔账，跟前几篇同一种算法。

工业相机的采集是**持续满帧**的。假设一台 GigE 相机跑 30fps、500 万像素彩色，那么每一帧是 `2592 × 1944 × 3 ≈ 14.4 MB`（不考虑对齐填充）；30fps 意味着**每秒 430 MB 的图像数据往主链路里灌**，平均每 33 毫秒就要有新帧到达。

现在假设界面是同步处理的：一个循环里「等下一帧 → 转 QImage → 刷新控件」。会发生两件事，而且两件都致命：

1. **等帧的那次阻塞会把主线程钉死。** 相机如果没出图、或者频率掉到 15fps，主线程就停在「等 33 毫秒还是一个世纪」的状态里，按钮点不动、窗口拖不动、整个界面卡成一帧。
2. **处理本身会倒挂到采集节奏上。** 一帧 14MB 的像素格式归一化加跨格式转换，如果处理时间偶然超过了帧间隔，队列里的帧就积压，界面显示的永远是几秒前的旧画面——**延迟越滚越大，最后相机还在采，界面已经不知道跑到哪一帧去了。**

这不是「理论上会卡」，而是「同步写法必然卡」。后来我在另一个项目 agent4cpp 里重犯过同一个错——同步 `Run` 把界面冻成了白屏，那个故事留给第 13 篇讲。这里我先记下结论：**图像链路的第一原则，是「取」和「用」必须分处两个线程。**

值得把「分处两个线程」再拆细一点，因为只分两个线程还不够。真正的问题是**生产速率和消费速率都是波动的，而且波动的相位不重合**：

- 生产端（相机）的节奏由曝光时间和带宽决定，是**硬的、规律的**——33ms 一帧就是 33ms 一帧，它不关心你在干什么。
- 消费端（界面）的节奏由渲染和事件循环决定，是**软的、抖的**——用户拖着窗口缩放、后台在重绘、GC 偶尔喘一口，某一帧的显示耗时可能是平均值的几倍。

**两个波动系统的耦合，必须靠一个缓冲区来吸收相位差。** 没有缓冲区，两个系统的抖动会直接叠加：相机快一拍、界面慢一拍，两个抖动撞在一起，那一帧就卡。缓冲区的作用是在两者之间插入一段「存量」——生产端多出来的先存着，消费端喘不上气时先欠着，**只要存量在容量范围之内，两个系统就感觉不到对方的抖动。** 这一篇后面讲「有界队列」和「保新弃旧」，本质上都是在回答同一个问题：「这段存量该有多大、满了怎么办」。

## 四级隔离：每级各解决什么

`docs/architecture.md` 第四节的图把这条链路画成了四段。我照着代码把每一级的作用点补齐：

| 级 | 载体 | 在哪个线程 | 解决什么 |
|---|---|---|---|
| 一、SDK 回调 | `HikCamera.cpp` 的 `ImageCallBack` | **SDK 内部采集线程** | 把 SDK 交出来的裸 `pData` 归一成统一格式的 `cv::Mat`，塞进队列就走 |
| 二、有界缓冲队列 | `CameraImageQueue` | 跨线程（自带锁） | 解耦「生产端有多快」和「消费端有多慢」，满时保新弃旧 |
| 三、采集线程 | `AcquireImageProcess`（一个 `QThread`） | **独立辅助线程** | 把「等帧」这件事从界面线程彻底挪走，还负责 cv::Mat → QImage |
| 四、界面渲染 | `GraphicsView::SetImage` | **UI 线程** | 只剩把一张 `QImage` 贴成 `QPixmap` 并刷新 |

**四级不是四层封装，是四道「速度不同的东西之间的减震器」。** 采集回调是毫秒级的、SDK 说了算；界面渲染是帧率级的、用户说了算；采集线程在中间做格式转换和等帧。**任何一段变慢，都被自己前面那级队列或线程的吸收窗口挡在外面，不会顺着链路顶到上一级。**

我特别想讲清楚第一级的边界。看 `HikCamera.cpp` 里那个回调的注释：

```cpp
// __stdcall 是 MVS 回调的 ABI 硬要求，调用约定不符会在栈上出问题。
// 回调运行在 SDK 的内部采集线程而非 UI 线程，整段函数体（含像素转换）都在那个
// 线程上跑，所以这里的耗时直接顶到 SDK 的收帧节奏上，不能做重活。
```

**「这里的耗时直接顶到 SDK 的收帧节奏上」是这一整章的设计前提。** 回调函数体里不能再干任何重活——不能转 QImage（那要遍历像素）、不能碰界面、不能等锁（除了入队那一次短暂的锁）。它只做一件事：**归一化 + `Put` + 返回**，把耗时压到最短，让 SDK 的采集线程尽快回去收下一帧。至于归出来的 `cv::Mat` 什么时候被显示，不归它管。

这个「回调线程不能做重活」的约束，跟第三篇那条 `RGB8_Packed` 漏认是同一处代码的两面：回调里那句 `if (!HikConvert2Mat(...)) return;`——转换失败就静默 return，**连队列都不进**。所以回调一旦沉默，下游只会等来超时，界面上就是黑屏。

这里补上第三篇讲格式归一时的下半句。那篇讲的是 `IsMono` / `IsColor` 这对判定**必须互补且不留缝**，漏一个格式就整类帧被静默丢弃。这一篇要讲的是**归一化的产物长什么样**——它决定了后面整条链路能不能零分配：

```cpp
// 回调里的转换目标只有两个：单色→Mono8，彩色→RGB8_Packed
cv::Mat cvImage;
if (!HikConvert2Mat(pCamera->CameraHandle(), pFrameInfo, pData, cvImage))
    return;
pCamera->ImageQueue().Put(cvImage);
```

**相机原生能吐二十多种像素格式**（我去数了 `HikCamera.cpp` 里 `IsColor` 的 `case`：BGR、RGB、两种 YUV422、再加 Bayer 的 8/10/12/16 位共 29 种；单色 Mono 8/10/12/14/16 共 7 种），**但穿过回调之后只剩两种**：`CV_8UC1` 和 `CV_8UC3`。这个「收敛到两种」是整条链路能讨论「尺寸不变就复用」的前提——如果没有归一化，每帧进来的 `type()` 都可能不一样，`Put` 里那个 `buffer.type() == m.type()` 判断就永远为假，稳态零分配根本无从谈起。

**所以归一化和零分配是一件事的两头**：第三篇保证「所有进来的格式都被正确识别、没有漏网之鱼」，这一篇保证「识别之后统一成固定的那两种输出」。**前者防的是丢帧，后者防的是每帧重新分配。** 两个目标都指向同一个输出契约——**归一化层是这个契约里唯一认识「相机原生格式」的地方，往上走，`CV_8UC1`/`CV_8UC3` 就是全世界。**

顺带说一个和第三篇呼应的细节：`cvMat2QImage` 里只认 `CV_8UC1`、`CV_8UC3`、`CV_8UC4` 三种类型，其余一律返回空 `QImage`。**这个「只认三种」不是偷懒，正是建立在归一化已经收敛到两种的前提上**——多出来的 `CV_8UC4` 是给别的数据源（比如将来的虚拟相机或离线图片）留的口子。如果归一化层漏了某个格式，让一个 `CV_16UC1` 混进来，这里会安静地返回一张空图，界面上就是一片空白。

## 双队列 + 保新弃旧

整个队列类只有两个成员队列，就是它的全部机关：

```cpp
std::mutex m_mutex;
std::condition_variable m_condition;
std::queue<cv::Mat> freeImageQueue;   // 空闲缓冲池
std::queue<cv::Mat> workImageQueue;   // 待消费的工作队列
uint8_t m_queueSize;
```

**`freeImageQueue` 是一池「空壳」缓冲，`workImageQueue` 是装好帧的待处理队列。** 两者加起来的总量恒等于容量——一块 `cv::Mat` 要么在池子里空着，要么在队列里装着数据，**不会同时在两边，也不会凭空多出来**。构造时先把池子填满：

```cpp
CameraImageQueue::CameraImageQueue()
{
    m_queueSize = ImageQueueSize;          // ImageQueueSize = 10
    for (int i = 0; i < m_queueSize; i++) {
        freeImageQueue.push(cv::Mat());    // 先发 10 块空缓冲
    }
}
```

**队列为什么要有界、容量为什么是 10，值得算一下。** 无界队列在预览场景里是灾难——生产端一旦长期快于消费端，队列会一路涨到内存爆掉，而且界面看到的画面越来越旧。有界是强制「宁可丢、不可积」。那 10 这个数怎么来的？我在 `CameraImageQueue.h` 里定义 `#define ImageQueueSize 10`，它是这样倒推出来的：

- **下限**由抖动幅度决定。消费端一次卡顿如果持续几百毫秒，按 30fps 算就有十几帧的相位差——但预览**不需要**吸收这么大的抖动，卡顿期间本来也不需要显示「这期间所有帧」，所以下限不高。
- **上限**由内存和延迟共同压。库容越大，积压越久。按 14MB 一帧算，10 帧就是 140MB 的驻留内存；再多，一是内存占用顶上去，二是队列一旦开始积压，用户看到的延迟就按「库容 ÷ 帧率」放大。
- **10 帧 = 约 330ms 的缓冲深度**。这个量级刚好能吸收一次普通的渲染卡顿，又不至于让延迟明显到用户能察觉。**容量不是一个「多多益善」的参数，它是「抗抖动」和「低延迟」之间的一条折中线上取的点。**

而 `Put` 的后半段（下面讲的 `copyTo`/`clone`）之所以强调「复用池中已有缓冲」，恰恰是因为**容量固定为 10 就固定了内存上限**：池子一共就 10 块，无论如何不会超过这个数——**有界不只约束队列长度，也约束了整条链路的内存峰值。**

`Put` 的前半段是「满队列保新弃旧」，这段是这一节的核心：

```cpp
// 队列满时丢最旧帧，并把它占用的缓冲收回空闲池
if (freeImageQueue.empty() && workImageQueue.size() >= m_queueSize
    && !workImageQueue.empty()) {
    freeImageQueue.push(workImageQueue.front());   // 丢掉最旧那块
    workImageQueue.pop();
}
cv::Mat buffer;
if (!freeImageQueue.empty()) {
    buffer = freeImageQueue.front();               // 从空闲池取一块
    freeImageQueue.pop();
}
```

注意 `workImageQueue.front()`——**`std::queue` 的 `front()` 是最早入队的，也就是最旧的那一帧。** 队列满了要腾地方时，我们丢的是队头，不是队尾。这是「保新弃旧」的字面实现。

**为什么丢最旧的，值得讲透。** 因为**预览要的是「当前」，不是「完整」。**

图像链路和别的队列不一样。一般队列（比如任务队列）的态度是「一条都不能丢」，丢一条就丢一个任务。但预览这条链路的态度相反——**如果消费端追不上生产端，堆在队列里的旧帧没有任何价值**。相机的画面摆在这里，用户眼睛看的是「现在相机拍到了什么」，不是「3 秒前相机拍到了什么」。队列里积压的 10 帧旧画面，对预览来说是 10 份过期的记忆。

如果反过来保旧弃新（丢最新的、留下最旧的先处理），后果更糟：**延迟会累积。** 用户看到的画面永远滞后于现实，而且随着生产端偶尔变慢，滞后量只增不减。工业现场上，一个滞后半秒的画面可能让操作员按下已经过时的按钮。**宁可直接跳到最新帧、丢掉中间，也不要一段平滑但持续滞后的回放。** 这就是「保新弃旧」的全部理由。

顺带说一句方向和寻址：`Put` 每入队一帧 `m_condition.notify_one()`，`Take` 用 `wait_for` 等条件变量。**队列自己带锁和条件变量，上层的生产端（回调线程）和消费端（采集线程）从不相见，只通过这个类对话。** `CameraInterface.h` 第 74 行那句注释把契约写明了：「供取帧回调线程 Put、上层 Take/Recycle；内部自带锁，可跨线程访问」。

## 稳态零堆分配

`Put` 的后半段，是我在这个类里最得意的一处：

```cpp
// 尺寸与类型不变时复用已有内存，仅在分辨率或格式变化时重新分配
if (buffer.size() == m.size() && buffer.type() == m.type()) {
    m.copyTo(buffer);      // 原地写入，不重新分配
} else {
    buffer = m.clone();    // 尺寸或格式变了才另开一块
}
```

拆开看：从空闲池取出一块 `buffer`（它可能上几帧刚被 `Recycle` 归还，头还在、内存还在），**先比较尺寸和类型**。

- **尺寸和类型都一样** → `m.copyTo(buffer)`。此时 OpenCV 不会给 `buffer` 重新分配内存——目标的维度、类型、步长都对得上，它直接把 `m` 的像素**原地写进 `buffer` 已经持有的那块内存**。
- **尺寸或类型变了**（换分辨率、换像素格式）→ `m.clone()`，另开一块。

于是整个链路的堆分配模式是这样的：**首帧到来时，池子里那 10 块空 `cv::Mat` 陆续被 `clone` 成真实尺寸的缓冲，各分配一次内存；此后只要分辨率与格式不变，每一帧都走 `copyTo` 原地覆盖，零分配。** `docs/architecture.md` 把这条写成了一行：「稳态零分配：分辨率与像素格式不变时，`copyTo` 原地写入，堆分配只发生在首帧」。

**为什么这件事重要**：满帧采集时每秒处理几十帧，如果每一帧都 `clone` 一次 14MB 的新缓冲，就是每秒 400 多 MB 的 `malloc`/`free` 在滚。**高频的大量小块分配不只是慢，还会让内存碎片化、让延迟出现毛刺**——某一帧恰好赶上分配器在做整理，那一帧就慢了。把分配收敛到首帧那 10 次，后面全是覆盖写，链路的延迟曲线才平。这是 `Recycle` 这个「归还」动作为什么必须存在的根本原因——**没有归还，空闲池很快耗尽，`Put` 里那句 `else` 分支持续命中，退化回「每帧新建缓冲」**。`HikCamera.cpp` 第 650 行的注释说得直白：「空闲池一旦耗尽，队列就退化成持续新建缓冲，长跑下内存会来回抖」。

## 超时保护：200ms 一个值管两件事

`Take` 不是无限等待的：

```cpp
uint32_t CameraImageQueue::Take(cv::Mat& m)
{
    std::unique_lock<std::mutex> locker(m_mutex);
    std::chrono::milliseconds dura(TIME_OUT_MS);           // TIME_OUT_MS = 200
    auto state = m_condition.wait_for(locker, dura, [this] { return NotEmpty(); });
    // 取不到帧时回超时码，不产出空帧
    if (state == false || workImageQueue.empty()) {
        return GETIAMGE_TIMEOUT;
    }
    m = workImageQueue.front();
    workImageQueue.pop();
    return ZYCLEAR_OK;
}
```

`TIME_OUT_MS` 是 200，定义在 `CameraImageQueue.h` 第 12 行。`wait_for` 等满 200 毫秒还没帧，就返回 `GETIAMGE_TIMEOUT`。

**为什么必须带超时、不能无限等**：如果 `Take` 无限阻塞，那相机一旦停止出图（拔线、掉电、用户停采），采集线程就永远沉睡在里面。之后想停它就得靠强杀——而强杀一个正卡在 SDK 调用里的线程，会把 SDK 的内部状态留在未知态，比让一个僵尸线程待着更危险。

**超时的真正价值在于：它让「等待」这件事有了一个可预测的上界。** 空闲时采集线程每 200ms 醒一次空转一轮，`AcquireImageProcess.cpp` 里写明了这个权衡——「空闲时此处每 TIME_OUT_MS 空转一轮，靠固定超时把单核占用压到可忽略」。

但这里有一个我从注释里读出来的、更值得记的观察：**这个 200ms 同时决定了停止采集的最坏响应延迟。** 看 `AcquireImageProcess::stop()`：

```cpp
void AcquireImageProcess::stop()
{
    requestInterruption();
    // 取帧最长阻塞 TIME_OUT_MS，等待需覆盖一次超时
    if (!wait(TIME_OUT_MS + 2000)) {
        qWarning() << "AcquireImageProcess: 采集线程未在超时内退出";
    }
}
```

`stop()` 先给线程打上中断标记，然后 `wait(TIME_OUT_MS + 2000)` = 等 2200 毫秒。为什么是「超时值 + 2000」？

因为 `run()` 里那次 `getImageLast` 可能正卡在 `Take` 里阻塞。线程收到中断请求后，**必须等它当前那次 `Take` 超时返回**，才能回到循环顶部看中断标记、退出。所以「最坏退出延迟」= 一次 `Take` 的超时上限 = 200ms，`stop` 的等待上界必须盖过它，再加 2000ms 给真正在干活的转换留余量。

**同一行 `#define` 同时回答了两个问题**：取帧该等多久、线程退出最坏要多久。这是个「一个常量在两个语义里复用」的典型——**它是耦合的**。哪天把 `TIME_OUT_MS` 调到 2000，`Take` 的空转变粗、线程停下的最坏延迟也跟着变成 2 秒。头文件第 11 行那句注释把这个双关点破了：「取帧等待上限，同时决定停止采集的最坏响应延迟」。**写下这个常量的人得同时想清楚这两件事**，否则调超时值只为「省 CPU」时，会顺手把退出延迟也改坏。

超时还有一层语义保护：**超时返回的是错误码，不是空帧。** `if (state == false || workImageQueue.empty()) return GETIAMGE_TIMEOUT;`——两种「没取到」的情况（等超时了、或者被虚假唤醒但队列还是空）都回错误码，**绝不把一块空的 `cv::Mat` 当有效图像交出去**。这样消费端只要判 `ret != ZYCLEAR_OK` 就能安全跳过，不用额外去判 `image.empty()`。

## 第三级：采集线程为什么投递 QImage 而不是 cv::Mat

采集线程 `AcquireImageProcess` 是 `QThread` 的子类，`run()` 结构很简单：

```cpp
while (!isInterruptionRequested()) {
    QImage image;
    auto ret = CameraContext::Instance()->getImageLast(m_serial, image);
    if (isInterruptionRequested()) break;   // 阻塞期间可能收到停止请求
    if (ret != ZYCLEAR_OK) continue;        // 超时是空闲常态，刻意不记日志
    emit sigUpdateImage(image);
}
```

这里有个刻意的类型选择，写在头文件的信号声明旁边：

```cpp
// 刻意投递 QImage 而不是 cv::Mat：Mat 的缓冲归采集队列的池子所有，出了
// 取帧作用域就要归还，跨线程拿着它等于拿野指针；QImage 在转换时已深拷贝，
// 且隐式共享让队列投递只加一次引用计数。
void sigUpdateImage(const QImage& iamge);
```

**为什么不能投递 `cv::Mat`**：`cv::Mat` 取出来的那块缓冲**不是无主的**——它来自队列的空闲池，用完必须 `Recycle` 还回去。如果把它跨线程 `emit` 给界面线程，界面线程就攥着一块「本应已归还、可能已被下一代 `Put` 覆盖」的内存，等于拿野指针。

**为什么投 `QImage` 就安全**：因为 `QImage` 是**重建出来的、拥有自己像素的**对象。更妙的是 Qt 的隐式共享（copy-on-write）——`emit sigUpdateImage(image)` 穿过线程队列时，只在引用计数上加一，不复制像素。**深拷贝只发生一次，在转换那一刻；投递本身是廉价的。**

连接方式也值得看一句，`ViewWidget.cpp` 第 117 行：`connect(m_pImageProcess, &AcquireImageProcess::sigUpdateImage, m_pViewBox, &GraphicsView::SetImage)`。发送方在采集线程、接收方对象的线程归属是 UI 线程，**Qt 自动走队列连接（queued connection）**，信号参数被拷贝进事件、投到 UI 线程的事件循环里执行。所以从采集线程到渲染的这最后一跳，是 Qt 替我们做的。

这里还有一个时序契约，`ViewWidget.cpp` 第 115 行：

```cpp
// 先接信号再启动相机：startGrabbing 之后首帧可能立刻到达，晚接会丢帧；
// 断开则反过来先于停相机，保证停流之后不会再有帧投进视图。
```

**「先连后启、先断后停」**——连接要在启动采集之前（否则第一帧来的时候没人在听），断开要在停止采集之前（否则停流后还有帧在路上）。顺序反了就是丢首帧、或者收到停流后的幽灵帧。

## cv::Mat → QImage 桥的两个契约

`src/Utils/ImageConver.h` 里那个 `cvMat2QImage` 是整条链路上唯一一处把 OpenCV 世界和 Qt 世界接起来的地方。它开头那段注释，把两个契约钉死了：

```cpp
// 两者共用一个关键契约：clone=false 时构造出的对象只是「借用」对方的像素缓冲，
// 不做深拷贝。于是被借的那一方必须活得更久，且期间不能被改写或复用。
```

**契约一：必须传 `mat.step`，不能自己算行长。** 看灰度分支那句：

```cpp
// 直接指向 mat 的像素首地址。下面构造 QImage 时务必把 mat.step 一并传进去：
// OpenCV 的行间可能有对齐填充，自己按「宽 × 通道数」算行长会整幅错位。
QImage image(pSrc, mat.cols, mat.rows, mat.step, QImage::Format_Grayscale8);
```

`QImage` 的构造函数有个重载是 `(数据指针, 宽, 高, 每行字节数, 格式)`。**第四个参数「每行字节数」如果传成 `cols × 通道数`，就是错的**——因为 OpenCV 的 `cv::Mat` 行与行之间可能有对齐填充（典型是补齐到 4 或 8 字节的倍数），真实行长是 `mat.step`，可能大于 `cols × 通道数`。传错行长，`QImage` 每一行都会从错误偏移开始读像素，**整幅图从第二行起斜着错位**，看起来像「画面被水平剪切错开」。

这个坑的阴险之处在于**窄图像常常不触发**——因为尺寸恰好是对齐倍数时 `step == cols × ch`，两者相等，代码「碰巧对」。直到某台相机分辨率一改，行尾需要对 4 字节对齐，`step` 就多出来几个字节，画面立刻错位。**所以要养成习惯：永远传 `mat.step`，永远不要自己乘。**

**契约二：`clone = false` 只是「借用」，被借的一方必须活得久且不被改写。** 默认参数是 `clone = true`，此路径下每一支都走深拷贝：

```cpp
if (clone)
    return image.copy();
```

`clone = true` 时 `image.copy()` 复制像素，返回的 `QImage` 从此独立于 `mat`——**安全，但多一次拷贝。** 这正是采集线程需要的（它要把 `QImage` 投递出去、还 `Recycle` 掉 `mat`），也解释了为什么 `CameraContext::getImageLast` 敢在转完之后立刻归还缓冲：

```cpp
image = ImageConver::cvMat2QImage(cvImage);   // 默认 clone=true，深拷贝
// QImage 已深拷贝，缓冲归还空闲池
camera->ImageQueue().Recycle(cvImage);
```

而 `clone = false` 那一支就危险得多，注释里专门警告了：

```cpp
// 这是就地改写：cvtColor(mat, mat, ...) 把结果写回入参 mat 指向的
// 那块缓冲。形参写着 const cv::Mat& 也只约束了头部重绑，
// 拦不住写像素 —— 调用方的原图会被永久改成 RGB 顺序。
```

**注意这里叠了两个坑**：第一，`clone = false` 时返回的 `QImage` 和入参 `mat` **共用同一块像素内存**，`mat` 一旦被复用或释放，`QImage` 就成了野指针；第二，那条 `rb_swap` 分支里的 `cv::cvtColor(mat, mat, COLOR_BGR2RGB)` 是**就地改写**——把结果写回 `mat` 自己指向的缓冲。`const cv::Mat&` 这个形参只保证了你不重新绑定 mat 的头部，**根本拦不住你改它指向的像素**。

这个契约总结成一句：**`clone = false` 是「我把你的内存借来用，你别动它、也别比我先死」；`clone = true` 是「我复制一份，从此两不相欠」。** 工业软件的图像链路上没有省这一次拷贝的余地——跨线程、跨归还池，任何一处共享缓冲都是悬垂指针的温床。**所以默认值必须是 `clone = true`，`false` 只留给明确知道「借的人和还的人一生一世在同一个栈帧里」的场景。**

## 归还闭环的所有权时序

把最后一块拼图放上：一块缓冲的一生。

![归还的那一行必须在深拷贝之后](/images/zyclear/归还时序.svg)

```
构造：池中 10 块空 Mat
  Put：从池取一块 → copyTo 写入像素 → 进 workImageQueue（此刻它属于队列）
  Take：从 workImageQueue 取出 → 交给调用方（此刻它属于调用方）
  转换：cvMat2QImage 深拷贝（此刻新 QImage 拥有自己的一份像素）
  Recycle：把 cv::Mat 还回 freeImageQueue（此刻它重新属于池）
```

**关键契约是这一条：`Recycle()` 必须在消费者完成深拷贝之后才发生。** `docs/architecture.md` 写的是：「归还动作在消费者完成深拷贝**之后**才发生，保证同一时刻一块缓冲只有一个所有者」。

拆开这个「只有一个所有者」：一块缓冲在任一时刻，要么在空闲池、要么在工作队列、要么在被某个消费者拿着——**三种状态互斥。** 一旦它在被消费者拿着的同时又回了池子，`Put` 下一帧就可能把它取出来覆盖，而消费者手里那份还在读——**读到一个正在被覆写的缓冲，画面撕裂或花屏，而且是概率性的、只在负载高时出现。** 这种 bug 最难查，因为它不报错、不可复现、看起来像相机故障。

**为什么「借用」和「归还」一定要用同一块 `cv::Mat` 对象来做（而不是归还一个裸指针或索引）**，这里其实藏着一个 C++ 的取舍。`Take` 里那句 `m = workImageQueue.front();` 是按值赋——`cv::Mat` 的赋值是**浅拷贝头部、共享像素**（引用计数 +1）。所以「取出」这个动作本身就在共享缓冲区，`Take` 返回后，`workImageQueue` 里那份头部被弹掉了，但**像素数据还活着，因为调用方手里那份头部还指着它。** `Recycle` 再把这份头部推回池子，`Put` 从池子取出时同样按值拿到它——**整条所有权链上，传递的都是「头部」，像素只被引用计数管理，从不被真的搬动。**

这也解释了为什么 `Recycle` 接的是 `const cv::Mat&` 而不是别的：它要的就是那份**指向同一块像素的头部**，把它重新登记进池子。**借出的是头部的使用许可，还回的也是头部**——像素自始至终没有易主，只是引用计数在池子和队列之间来回跳。

所以 `Recycle` 的位置是精确的：**不能早于深拷贝（否则野指针），也不能晚到忘了还（否则空闲池耗尽、退化成每帧新建）。** 看 `CameraContext::getImageLast` 里的顺序——先 `cvMat2QImage`（深拷贝），**下一行才** `Recycle`。这个「下一行」就是整个所有权协议的执行点。**顺序反过来，就是数据竞争；顺序对但漏掉了，就是内存退化——两个错法，两种症状，都不报编译错。**

我把这条时序的因果链写进了代码注释，因为它不写在人能看到的地方，下一个人改动顺序时根本不会意识到自己动了什么。

## 我踩过的坑

**坑一：把 `clone = false` 当成了「默认就深拷贝」。**

我最早读 `cvMat2QImage(const cv::Mat& mat, bool clone = true, ...)` 这个签名时，注意力全在 `mat` 上，**没注意到最后一个参数的含义是反的**——我以为 `clone` 是「要不要克隆」，默认 `true` 就是「默认克隆」，安全。这个理解其实是对的，但我当时**把 `clone = false` 当成了「更高效且等价」的选项**，在一次「优化」里给某处传了 `false`，理由是「反正马上就显示了，省一次拷贝」。

结果那块 `QImage` 和 `cv::Mat` 共用像素，`cv::Mat` 随后经过 `Recycle` 回了池子、被下一帧 `Put` 覆盖——**显示控件那一帧读到的像素正在被改写，画面偶尔闪出一条错行。** 我一开始以为是采集丢帧，排查了很久。教训：`clone = false` 不是「优化开关」，是**一份所有权的让渡契约**——你拿到的不是一份数据，是「别人内存的使用许可」，许可的期限由对方决定。**能用默认值就用默认值，`false` 要能说出「借的人和还的人在同一个作用域里且借期被严格包住」才敢用。**

**坑二：以为 `Put` 每次都会分配新缓冲。**

我在第一次做性能观察时，看到 `Put` 里有个 `buffer.size() == m.size() && buffer.type() == m.type()` 判断，**当时把它当成了一个「防呆检查」**——觉得「反正尺寸不会变，这个 if 永远走 `copyTo` 分支，没什么用」。**我完全没意识到它恰恰是「稳态零分配」的实现点。**

后来想明白了这个判断的意义，才反过来理解到另一半：**如果空闲池被耗尽、或者有人忘了 `Recycle`，这个池子补不上来，`Put` 就只能一直走 `else` 分支 `clone`，退化成每帧新建。** 而「忘了 Recycle」的后果不是崩溃，是**内存开销悄悄涨上去、延迟毛刺变多**——一个不会报错、只在长跑后才显现的性能退化。**「零分配」不是自动的，它依赖归还闭环每一环都扣上。**

**坑三：调 `TIME_OUT_MS` 只考虑了 CPU，没考虑退出延迟。**

`AcquireImageProcess::run()` 空闲时每 `TIME_OUT_MS` 醒一次空转，我一度觉得 200ms 太频繁，**动过念头把它调到 1000ms 去「省 CPU」**。幸好动手前先读了 `stop()`——`wait(TIME_OUT_MS + 2000)`。**我要是把超时调到 1000，退出延迟的最坏值就从 200ms 变成 1000ms，`stop()` 的等待也得跟着改。** 这个常量不是「取帧超时」一个语义，它同时是「采集线程的退出响应上限」。**一个 `#define` 喂了两个语义，改它的影响面比看起来大。** 现在头文件第 11 行那句「取帧等待上限，同时决定停止采集的最坏响应延迟」就是冲着这个双层含义写的，提醒后来人改之前先想清楚两个后果。

**坑四：领会「保新弃旧」花了一段时间。**

我一开始对「队列满时丢弃最旧帧」是有心理障碍的——**丢数据这件事，直觉上就该尽量避免。** 我甚至在脑子里推演过「要不要丢最新的、先把旧的消费完」。直到我把这条链路的用途想清楚：**它是预览，不是录像。** 预览的职业是「如实、及时地显示现在」，录像的职业才是「一帧不落地保存」。**两种职业对「丢帧」的态度完全相反**——录像要把队列做得足够大、宁可延迟也不能丢；预览要主动丢掉旧帧、宁可跳帧也不延迟。用录像的直觉写预览，就会做出一个「平滑但永远慢半拍」的界面。

**坑五：`stop()` 里把线程的「当前阻塞」当成「随时可响应」。**

`requestInterruption()` 只是**设了一个标记**，它不会打断正在执行的 `Take`。**线程收到标记后，必须等当前那次 `wait_for` 超时返回，才能在循环顶部看到标记并退出。** 我一开始以为 `requestInterruption()` 能像信号一样立刻让线程停下，于是 `stop()` 里差点写成「打个标记就返回」，那线程还在后台多转最多 200ms 才退，而调用方以为它已经停了、随后可能就把相机对象析构了——**回调线程拿着已析构的 `this`，又是野指针。** 现在 `stop()` 老老实实 `wait(TIME_OUT_MS + 2000)`，等的就是那次不可避免的阻塞超时。**凡是靠「轮询标记」停线程的地方，退出延迟都等于「一轮的周期」，这个周期必须被调用方知道。**

**坑六：`QImage` 的每行字节数一度被我算成 `宽 × 通道数`。**

这一条我没在自己的代码里真爆过，因为 `ImageConver.h` 里那句注释把我拦住了——但正因为它离坑只有一步，我把推理过程记下来。我构造 `QImage` 的直觉是「给指针、给宽高、给格式」，**第四个参数「每行字节数」我第一反应就是 `cols × channels`。** 这是错的：`cv::Mat` 的行有对齐填充，真实步长是 `mat.step`。**如果某次手上没有 `mat` 只有裸指针，我可能真就按 `cols × ch` 算了**，然后窄图恰好相等、测试全过，换个分辨率才错位。**「每行字节数」是个必须往前追溯到数据源、而不能凭宽高推算的量**——凡是上一步的布局带有「实现相关的填充」，下一步就不能靠「逻辑尺寸」反推它的物理步长。

## 结尾

一条图像链路，从 SDK 回调到界面渲染，中间是四级隔离：回调线程只做归一化和入队（耗时压在收帧节奏之内）、有界双队列做生产者与消费者的减震（满时保新弃旧、稳态零分配）、采集线程把「等帧」从界面挪走并完成 cv::Mat → QImage 的深拷贝、界面线程只剩贴图刷新。

四级的价值可以浓缩成一句话：**任何一侧的慢，都被它前面那级吸收了，不会顶到下一级。** 相机偶尔掉帧、转 QImage 偶尔变慢、界面偶尔忙于重绘——它们各自在自己的减震器里消化，链路整体不失控。

这一篇也埋了三处「一个东西同时管两个语义」的耦合：`TIME_OUT_MS` 既管取帧等待、又管退出延迟；`clone` 既管深拷贝、又管所有权让渡；`freeImageQueue` 既管复用、又管总量守恒。它们都是**便利和风险的同一枚硬币**——省了一次参数、一次拷贝、一个计数器，代价是这三个量在读代码时都得同时想到两层含义。

到这里，六层架构里的「图像链路」这一层从回调一路走到了像素。但还有一条贯穿全项目的暗线没讲：这一篇里到处出现的「先接信号再启动」「停流之后不能再有帧投进来」「相机状态变了通知谁」——**这些都不是图像链路自己的事，而是全项目的通信骨架：事件总线。**
