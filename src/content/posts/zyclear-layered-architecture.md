这是我给智澈 ZyClear 写的系列第一篇。整个系列讲一件事：一个跨品牌的工业相机上位机，怎么从零搭起来，怎么做到换品牌只改一处、加型号不编译。

但我不打算从代码开始讲。**代码是一层一层堆上去的，如果不先把"墙"画好，后面每一篇都会变成补丁**。所以这一篇只讲架构的骨架：六层怎么分、依赖往哪走、以及三条我能当场敲命令给你看的约束。

先说清楚一件事：这篇文章里所有的 grep 命令，我都在这台机器上真跑了，不是抄文档。文档里写的"期望无输出"，跟实际跑出来有没有输出，是两码事——这一点后面第五节的坑里我会细讲。

## 为什么工业相机客户端需要分层

先讲一个具体的现场。

工业视觉产线上跑的相机上位机，通常不是只伺候一台相机。一条产线可能同时挂海康、大恒、巴斯勒三家的机器；今天这批设备是海康 MV-CS060，下个月客户换了台 MV-CU120，再下个月整条线换成了别的牌子。

我最早写的版本（一个只有几百行的 demo）是这么组织的：`MainWindow` 里直接持有两个相机 SDK 的类型，界面上每个按钮的槽函数里写 `if (相机是海康的) { 走海康这条路 } else { 走另一条 }`。

这个写法在只有一家品牌时完全没问题，甚至更短。但它有三个必然的后果：

- **接第二家品牌，要改遍了整个上层。** 因为"品牌判断"像藤蔓一样爬满了 MainWindow、参数面板、图像显示——每个地方都得加一条分支。
- **参数面板和 SDK 类型绑死。** 海康的参数是 `MVCC_FLOATVALUE`，别家可能是自己的一套结构体。参数面板一旦接受了海康的类型，它就再也不认识别的相机了。
- **没法在没有相机的地方跑。** 界面想调一下布局？得先借一台真机插上。CI 想跑个单元测试？机器上没有海康 SDK 就编不过。

我后来真正动手重写时，先做的不是写代码，是做一件事：**把"哪个部分会因为什么原因变化"列出来**。

列完就清楚了——变化频率完全不一样：

| 部分 | 多久变一次 | 变化的原因 |
|---|---|---|
| 主题配色、图标 | 几乎不变 | 产品设计定稿 |
| 按钮、表格、图像控件布局 | 偶尔变 | 需求调整 |
| 参数有哪些、什么类型 | **经常变** | 客户型号不同，参数就不同 |
| 厂商 SDK 怎么调 | **最经常变** | 换品牌、升 SDK 版本、补一个型号 |

**变化频率差了一个数量级。** 搅在一起写，就是让那个"几乎不变"的部分，每次都被"最经常变"的部分拖着一起改、一起测、一起发版。

分层的全部动机，就是把这几种变化**按频率拆开**。

## 六层怎么分的

我把整个 `src/` 拆成六层，从最上面（离人最近）到最下面（离设备最近）：

```
┌──────────────────────────────────────────────────────┐
│  资源层   AppStyle │ Icon │ Resource(参数 Schema)      │  主题/图标/Schema 数据
└──────────────────────────────────────────────────────┘
                          ▲ 编译进可执行文件，按名字引用
┌──────────────────────────────────────────────────────┐
│  交互层   ControlWidget │ ParamWidget │ ViewWidget    │  按钮、面板、图像显示
│           └─ 模型层  CameraParamModel / Item / Delegate│  表格数据与渲染
└──────────────────────────────────────────────────────┘
                          │ 只凭序列号寻址
┌──────────────────────────────────────────────────────┐
│  门面层   CameraContext                               │  序列号→设备对象的映射
└──────────────────────────────────────────────────────┘
                          │
┌──────────────────────────────────────────────────────┐
│  契约层   CameraInterface（17 个纯虚方法）             │  能力边界（纯抽象）
│           ZCCameraParam │ CameraImageQueue │ CameraError│
└──────────────────────────────────────────────────────┘
                          ▲ 依赖倒置：实现层来实现契约
┌──────────────────────────────────────────────────────┐
│  实现层   HikCamera（海康）│ VirtualCamera（仿真）      │  接触厂商 SDK 的唯一地方
│           CameraFactory：按厂商名登记创建器+枚举器      │
└──────────────────────────────────────────────────────┘
```

一层一句话：

| 层 | 目录 | 一句话职责 | 明确不做什么 |
|---|---|---|---|
| **资源层** | `AppStyle/` `Icon/` `Resource/` | 主题 QSS、图标、参数 Schema（JSON） | 不含任何逻辑 |
| **交互层** | `ControlWidget/` `ParamWidget/` `ViewWidget/` | 设备列表、参数表格、图像显示 | 不判断厂商、不调 SDK |
| **门面层** | `CameraInterface/CameraContext.*` | 序列号寻址、多机生命周期托管、会话状态 | 不认识任何具体适配器 |
| **契约层** | `CameraInterface/CameraInterface.h` 等 | 定义硬件无关的能力边界和数据模型 | 不依赖 Qt Widgets，不认识任何相机 |
| **实现层** | `CameraFactory/` | 各品牌 SDK 适配、图像格式归一化 | 不接触界面，不接触 Qt Widgets |

这里有一个我核实过、值得单独拎出来的点：**契约层和实现层是两个独立的东西，不是一回事。**

- **契约层**只有纯虚接口和数据结构。`CameraInterface` 里 17 个纯虚方法，一个实现都没有，`= 0` 结尾。它描述"一台相机应该能干什么"——连接、断连、拉流、读参数、写参数、给一块图像缓冲。
- **实现层**是最底下那层，**唯一接触厂商 SDK 的地方**。`HikCamera.cpp` 有 29KB，里面全是 MVS SDK 的调用、像素格式转换、错误码映射。它实现契约。

为什么要拆成两层而不是一层？因为它们的**依赖方向是反的**。

正常的调用链是往下的：交互层调门面，门面调契约。但契约是个纯虚类，它没法凭空干活——它需要有人来实现。于是实现层**向上**找到了契约，把自己挂上去。这就是**依赖倒置**：高层（门面）和低层（海康适配器）都依赖中间那个抽象（契约），谁都不依赖对方。

这也是为什么契约层里**不能**出现任何一个具体相机的名字。一旦它 include 了 `HikCamera.h`，倒置就塌了，契约就变成了"海康的形状"。

## 三条能 grep 验证的约束

架构图谁都会画，画完能不能守住是另一回事。规矩如果只写在文档里，三个月后没人记得，藤蔓又长回来了。

所以我在写第一版的时候就给自己立了个规矩：**每一条核心约束，都得能变成一条 grep 命令，当场敲，当场看到结果。**

约束不是"我们应该保持低耦合"这种话——那种没法验证。约束得长这样：**在某个目录里，不许出现某个字符串。**

我立了三条，全都写在仓库的 `docs/architecture.md` 里。

### 约束一：门面与契约层不许认识任何适配器

```bash
grep -rn "HikCamera.h\|VirtualCamera.h" src/CameraInterface/
```

门面层和契约层都在 `src/CameraInterface/` 这个目录里。这条命令在这个目录下搜两个适配器的头文件名，期望**无输出**。

含义是：`CameraContext` 和 `CameraInterface` 都不许 `#include "HikCamera.h"`，也不许 `#include "VirtualCamera.h"`。它们只能通过契约抽象跟相机打交道。

这条约束带来两个直接好处。第一，**新增品牌不用动门面**——因为门面本来就不认识任何品牌。第二，**门面能在没有 SDK 的环境里编译**——它没 include 过任何 SDK 相关的东西，自然不依赖 SDK。第二点很实在：我的 CI 就是在没装海康 SDK 的机器上跑门面层的测试的。

### 约束二：面板之间不许互相持有引用

```bash
grep -rn "ControlWidget\*" src/ParamWidget/ src/ViewWidget/
```

含义是：参数面板和图像面板里，不许出现指向控制栏（设备列表）的指针。期望**无输出**。

面板之间要联动怎么办？走**事件总线**和门面。比如切相机的时候，图像面板要清空旧帧、参数面板要重新拉参数——这件事不是参数面板直接喊图像面板"你清一下"，而是控制栏往总线扔一个"相机切换了"的事件，谁关心谁去订阅。

为什么要这么严？因为面板之间的直接引用会变成**网状耦合**。三个面板互相引用是 3 条边，五个面板就是 10 条边，每加一个面板，耦合边数按平方涨。总线把它压成"每个面板只连总线一次"，新增面板不触动任何既有面板。

### 约束三：交互层不许出现厂商名判断

```bash
grep -rniE "hikrobot|\"Hik\"|MV_CC_" src/ControlWidget/ src/ParamWidget/ src/ViewWidget/
```

这是三条里最狠的一条。它同时在三个面板目录里搜三种东西：

| 搜什么 | 代表的是 |
|---|---|
| `hikrobot` | 厂商名字符串（不区分大小写，所以 `Hikrobot`/`HIKROBOT` 都算） |
| `"Hik"` | 硬编码的厂商名简写 |
| `MV_CC_` | 海康 MVS SDK 的函数前缀（比如 `MV_CC_OpenDevice`） |

期望还是**无输出**。意思是：界面层里，**既不许出现厂商名字符串，也不许出现任何一个 SDK 函数调用**。

这一条守住的意义最大。它意味着：整个界面——按钮怎么摆、表格怎么渲染、图像怎么显示——**对"底下挂的是哪家的相机"完全无知**。界面看到的所有东西，都是契约层翻译好的统一形态。相机是海康的还是虚拟的，界面的代码一个字都不变。

### 我实测的结果

我把这三条都跑了。下面是实际结果：

| 命令 | 实测结果 |
|---|---|
| 约束一 | **无输出**（`grep` 退出码 1，即没匹配到） |
| 约束二 | **无输出**（退出码 1） |
| 约束三 | 在 `src/` 三个面板目录里**无输出**；但直接搬文档里那条原命令跑，会命中 3 行——**全都不是界面代码** |

第三条我得解释一下，因为这是我这次核实才发现的细节，而它恰恰证明了约束本身是成立的。

我把文档里那条原命令原样跑，它命中了三处：

- `docs/architecture.md:68` —— 就是这条命令**自己**写在文档里的那一行
- `docs/resume/v7-真伪核对.md:161` —— 同一个命令在另一份文档里的副本
- `src/CameraFactory/HikCamera.cpp:7` —— `HIK_CAMERA_VENDER = "Hikrobot"`

前两条是**文档在自我引用**，第三条在 `CameraFactory/`，**根本不在被搜索的三个面板目录里**。所以准确的结论是：**在被约束的三个交互层目录里，这三条命令全部无输出，约束成立。**

这里还有个更值得说的发现：如果你不加过滤直接在仓库根目录下跑第三条，它会额外命中一堆**二进制文件**——`bin/zyClear.exe`、各种 `.obj`、`.pdb`、`.ilk`。原因是 exe 和 obj 里编译进了 `HikCamera.cpp` 的代码，自然带着 `Hikrobot` 这个字符串。grep 默认会把它们当中文本处理，于是吐出 `Binary file ... matches`。

**我一开始就是被这个吓到的**：改完架构，一跑命令，看到好几行 `Binary file matches`，以为约束根本没守住。其实那是构建产物，跟源码约束是两回事。后来我给这类命令固定加上 `--exclude-dir=build --exclude-dir=bin`，或者干脆在 `src/` 里跑，世界就清净了。

这个小插曲我放进了后面的坑里，因为它非常典型：**验证命令本身如果不隔离构建产物，就会给你假信号。**

## 全仓厂商条件编译只有 2 处

上面三条约束守的是"界面不知道品牌"。但还有一件反过来要想的事：**总得有个地方知道品牌吧？**

有。就是工厂。

我核实过：整个仓库里，厂商相关的条件编译（`#ifdef ZYCLEAR_HAS_HIK_SDK`）在**源代码**里一共只有两处，都在 `src/CameraFactory/CameraFactory.cpp` 里，第 3 行和第 27 行。

（顺带说一句：如果按字面数全仓所有文件，`ZYCLEAR_HAS_HIK_SDK` 这个串会出现 10 次左右——但另外那些都在 `CMakeLists.txt` 的条件分支、以及测试文件的中文注释里。真正的 C++ 条件编译指令 `#ifdef` / `#endif`，就这两处。我在核实的时候特意区分了这两者，因为"字符串出现次数"和"条件编译处数"是两码事。）

第一处在文件顶部，管的是**适配器头文件要不要 include**：

```cpp
#include "CameraFactory.h"
#include "VirtualCamera.h"
#ifdef ZYCLEAR_HAS_HIK_SDK
#include "HikCamera.h"
#endif
#include <QMutex>
```

第二处在单例的初始化里，管的是**这个品牌要不要登记**：

```cpp
auto* factory = new CameraFactory();
factory->registerVendor<VirtualCamera>(
    VirtualCamera::VIRTUAL_CAMERA_VENDER);
// 未接入 SDK 时不注册该品牌
#ifdef ZYCLEAR_HAS_HIK_SDK
factory->registerVendor<HikCamera>(
    HikCamera::HIK_CAMERA_VENDER);
#endif
m_instance = factory;
```

**为什么这两处必须存在、而且必须在这里。**

工业项目的现实是：不是每个开发机、每台 CI 机器都装了厂商 SDK。海康的 MVS SDK 是个几个 G 的安装包，还要配环境变量。如果代码硬要求它存在，那任何一台没装 SDK 的机器都编不过整个项目——这在一个多人协作、多环境交付的项目里是灾难。

条件编译解决的就是这件事：**SDK 在，就把海康适配器编进来、注册上；SDK 不在，就一个字都不编，程序退化成"只有虚拟相机"的形态，照样构建、照样跑、照样过测试。**

这个"降级"能力不是可有可无的锦上添花。我的 CI 流水线就是**故意在缺 SDK 的环境下**跑全量构建和单元测试的。等于说，每推一次代码，都在验证"降级路径没坏"。

那为什么只有这两处？因为**别的地方都不需要知道品牌**。

- 契约层：只有一个抽象接口，没有品牌概念的容身之处。
- 门面层：它持有的是 `CameraInterface*`，是基类指针，海康的还是虚拟的对它没区别。
- 交互层：`CameraContext::EnumerationCamera` 返回的是 `CameraMetaInfo`，一个只有序列号、显示名、厂商名的纯数据结构，界面对它一无所知。

所以"品牌"这个信息，从实现层往上走，走到契约层就**被抽象吸收掉了**。工厂是唯一需要"具体品牌类型"的地方——因为它的工作就是**把名字翻译成类型**。翻译这件事，世界上只需要发生一次。

## 变化点向内收敛的含义

把上面这些串起来，其实就是一句话：**变化点向内收敛。**

"内"指的是离设备近的那一头，"外"指的是离人近的那一头。我说的是**把变化最频繁的东西，放在最里面（最底层），让它动的时候，外面一点都感觉不到。**

回头看第一张表就明白了——变化频率是**越靠近设备越高**的：

```
交互层 ←————— 变化少（界面稳定几个月）
门面层 ←———
契约层 ←——   （能力边界相对稳定，17 个方法不轻易加）
实现层 ←— 变化最多（换品牌、升 SDK、补型号，都在这）
```

所以把实现层放在最底下是对的：它最不稳定，就让它离"稳定"的部分最远，中间用契约层做缓冲垫。

换个说法：**如果哪天海康 SDK 升级了，函数签名变了，会发生什么？**

答案是：只有 `HikCamera.cpp` 要改。契约层不知道有海康，门面层不知道有海康，界面更不知道。改完重新编译，上层全部零改动。

这就是"换品牌改动面收敛 95%"背后的机制。剩下的 5% 是什么？就是第二节末尾说的那两处条件编译，再加上你新写的那个适配器文件本身。

反过来说，如果没这么分层——所有代码搅在一起——那么 SDK 升级这一天，你要改的就是二十来个文件，改完还得把整个界面回归测一遍。因为界面里也可能藏着品牌判断。

**分层不是为了"优雅"，是为了让最频繁的那类变化，代价最小。**

## 我踩过的坑

这一节集中说我实际踩到的，比架构图本身更值得记。

**坑一：用 grep 验证架构，被构建产物打了假信号。**

这是最大的一个。我立完三条约束，兴冲冲地跑第三条 `hikrobot|MV_CC_`，结果屏幕刷出来好几行 `Binary file ... matches`。我当时的第一反应是"完了，架构没守住，界面上有厂商判断"。

排查了半天才发现，那些命中全是 `bin/zyClear.exe`、`build/.../HikCamera.cpp.obj`、`.pdb`、`.ilk`。**它们是构建产物，不是源码。** exe 里编进了 `HikCamera.cpp` 的代码，自然带着 `Hikrobot` 字符串，grep 二进制命中完全正常。

症状是"命令有输出，看着像约束被破坏"，原因是**搜索范围没隔离构建目录**。修法是把构建目录排除掉，或者干脆限定在 `src/` 的源码目录里跑。

这件事教会我一个原则：**验证命令本身也要被验证。** 如果一条命令的结果你解释不了，先别急着下结论"架构坏了"，先看看命中的到底是什么文件、什么行。

**坑二：门面层差点 include 了适配器头文件。**

写门面 `CameraContext` 的时候，有个方法要从设备信息里取序列号，我顺手就 `#include "HikCamera.h"` 了——因为那一刻我脑子里想的是"反正底下就是海康"。写完之后跑约束一，当场红灯。

我当时想的是"契约层和门面层是一回事，都在 `CameraInterface/` 目录，那认识具体相机也算在同层内部"，其实完全错：**门面认识适配器，就等于把实现层的依赖吸到了门面层，依赖倒置直接塌掉**。门面必须只持有 `CameraInterface*` 这个基类指针。

修法很简单——把 include 删掉，改成前置声明 `class CameraInterface;`（你去看现在的 `CameraContext.h`，第 25 行就是这句前置声明），所有设备的沟通都走基类虚函数。但这一个 include 的诱惑，说明了一件事：**分层规则不靠自觉，得靠能自动化跑的检查。** 我要是没立那条 grep，这个 include 会一直躺在代码里。

**坑三：以为"契约层"和"实现层"是一层。**

这是概念上的坑，最早画图的时候我把它们画成了一层，写成了"底层 = 契约 + 实现"。写文档的时候被自己绕晕了：如果一个层里既有纯虚接口又有具体实现，那依赖方向到底往哪走？

想明白了才拆成两层：**契约层是"口"，实现层是"手"。** 口在上，手在下，手伸上来接口。它们必须分开画，因为分开之后"契约层不依赖任何相机"这个结论才写得出来。如果混淆成一层，这句话就不成立了——你自己这一层里就有相机，怎么说不依赖相机。

**坑四：`CameraMetaInfo` 差点设计成持有 SDK 句柄。**

设计枚举结果结构体的时候，我想过把海康的设备句柄一起塞进去，这样门面拿到就能直接操作。

幸好没这么干。一旦 `CameraMetaInfo` 里有 SDK 类型，它就没法放在契约层（契约层不许有 SDK 类型），那枚举结果就得定义在实现层，门面层又要认识实现层——依赖倒置又塌了。最后它就是个纯数据：序列号、显示名、厂商名。

这里还有一个相关的真实缺陷，记录在 CHANGELOG 里，正好说明"纯数据"这件事也有坑：虚拟相机的枚举器用聚合初始化构造 `CameraMetaInfo` 时，参数顺序写成了 `{名称, 序列号, 厂商}`，而这个结构体真正声明的顺序是 `{Serial, UserDefineID, VenderName}`——**序列号和显示名互换了**。功能上自洽（上层一律按 `info.Serial` 寻址），所以编译过、测试过、界面也正常，但字段的语义是错的。逐文件补注释的时候才被发现。

这个坑的教训是：**结构体的字段顺序在聚合初始化里太脆弱了**，三个连续字段没有类型区分度（都是 `QString`），写反了编译器一声不吭。后来我给这类构造加了指定初始化或者显式赋值，不再靠位置。

**坑五：以为条件编译越少越"干净"，一度想把那 2 处也干掉。**

我一度觉得"既然只有工厂认识品牌，那能不能连工厂里的 `#ifdef` 也去掉，做成运行时判断？"——比如先探测 SDK 在不在，再决定注册不注册。

想过之后放弃了。运行时探测意味着**你得先把 `HikCamera.h` include 进来**，而一旦 include，SDK 不存在时就连编译都过不了。`#ifdef` 是**编译期**判断，它能让"SDK 完全没有"这种情况下的代码**根本不参与编译**，这是运行时判断做不到的。

所以这 2 处 `#ifdef` 不是"没消干净的残留"，而是**降级构建能力的承重点**。删掉它们，CI 就跑不了无 SDK 的降级路径了。

## 这一层墙立起来之后

到这里，骨架就立好了。回到最开始那张表——界面不知道品牌、门面不认识适配器、工厂只出现两次条件编译——这套结构定下来之后，后面每一篇讲的东西都是在它上面填肉。

下一篇讲**契约层**：那 17 个纯虚方法到底怎么切的。

这是个我反复改过的地方。能力边界切粗了，适配器里就要藏一堆自己的数据；切细了，每接一个品牌都要实现一大堆方法。我会讲我怎么从"按界面需求切"改成"按设备生命周期切"，以及为什么最后定在 17 这个数——还有，参数那个统一模型 `ZCCameraParam` 是怎么把六种参数类型压成一个外观类的。

再往后是门面层的序列号寻址、参数体系、图像链路。但那是后面的事了。先把墙画好——**没有墙，后面每一块都立不稳。**
