上一篇讲完插件，留了个话头：**「这个项目里所有『不需要真相机也能验证』的设计，最后都汇进了那套测试里。」** 这一篇就是把那一摊收掉——构建、测试、静态分析、CI。这是系列的最后一篇。

先把这一篇要回答的那个难题摆出来，因为整篇东西都是围着它转的：

**一台没有海康 SDK、没有相机、甚至没有 Windows 的机器，怎么把整个客户端构建出来、还要把整条相机链路测通？**

不是「顺便」测一下界面布局那种通，是门面、工厂、虚拟相机、参数模型、图像缓冲队列，从上到下真的跑一遍。而这台机器上，厂商 SDK 一个字节都没有。

## 降级路径是常态，不是例外

先讲这个项目里我认为最有想法的一处设计。

海康的 MVS SDK 是几个 G 的安装包，要单独下载、单独配置环境变量。**现实是：大部分开发机、所有 CI 机器，都没有装它。** 如果代码硬要求 SDK 存在，那这些机器全都编不过——这在多人协作、多环境交付里是灾难。

第一章讲六层架构时提过一个伏笔：`src/CMakeLists.txt` 里 SDK 探测是**条件**的，头文件与库目录齐备才把适配器纳进来。这一篇要讲的是它背后那条决策链，以及它在 CI 里怎么被「顺带」验证。

探测逻辑本身很短：

```cmake
set(HikSDK_ROOT "${CMAKE_CURRENT_SOURCE_DIR}/../depends/HikCamera"
    CACHE PATH "海康 SDK 版本根目录")
if(EXISTS "${HikSDK_ROOT}/Includes" AND EXISTS "${HikSDK_ROOT}/Libraries")
    set(ZYCLEAR_HAS_HIK_SDK ON)
    message(STATUS "海康相机 SDK：已接入（${HikSDK_ROOT}）")
else()
    set(ZYCLEAR_HAS_HIK_SDK OFF)
    message(STATUS "海康相机 SDK：未找到（${HikSDK_ROOT}），本次仅构建虚拟相机")
endif()
```

**注意 `HikSDK_ROOT` 是个 `CACHE` 变量，能在命令行覆盖。** 这个属性是整篇的支点——它意味着「SDK 在不在」不是由机器决定的，而是由**构建命令**决定的。同一台机器，加一个 `-DHikSDK_ROOT=...` 就能从降级态切到接入态。

这个开关一旦存在，就引出了一个我没预料到、但后来觉得非常值的玩法：

### `HikSDK_ROOT` 故意指向一个不存在的路径

看 CI 里的配置步骤：

```yaml
- name: 配置（刻意不提供海康 SDK）
  run: |
    cmake -S . -B build -G Ninja \
      -DCMAKE_BUILD_TYPE=Debug \
      -DHikSDK_ROOT=/nonexistent
```

**`/nonexistent` 这个路径是我故意写的，它当然不存在。** 我明明可以不传这个参数、让探测自然落到默认路径、自然找不到——那我为什么还要显式写一个不存在的路径？

因为这里有两件不同的事被我区分开了：

- **「没传参数」**意味着「我用默认值，碰巧默认值指向的目录是空的」。
- **「传了 `/nonexistent`」**意味着「我明确要求：这次构建里 SDK 一定不存在」。

**后者是一条被钉死的测试条件，前者只是运气。** 如果哪天有人把 `depends/HikCamera` 目录不小心提交进了仓库，或者默认路径改了，那「不传参数」的那种写法会在某次推送里**悄悄变成「SDK 存在」**，降级路径就再也不被测到了——而且没有任何信号告诉你它测不到了。`/nonexistent` 把这条路堵死了：无论仓库里发生什么，这个 job 永远跑在缺 SDK 的形态下。

**于是每一推送，都顺带把「缺厂商 SDK 时降级为纯虚拟相机」这条分支覆盖了一遍。** 这条分支不是「理论上支持」，是每次 CI 都要实际走一遍、走不通就红灯的。**它从一条边缘路径，变成了主路径。**

我在别处的项目里见过把「缺依赖的降级」当兜底、当例外、当没人真的去跑的东西。这里正相反：**降级路径是被 CI 反复验证的那一条，接入路径反而是本地开发才偶尔跑的。** 理由很简单——CI 天天跑，本地只在开发海康适配器时才需要 SDK。**哪个路径跑得多，哪个路径就该是主路径。**

## 为什么是 Ubuntu，不是 Windows

项目本身是 Windows 桌面客户端，跑在 Windows 上，用 MSVC 构建。那 CI 为什么不选 Windows runner？

答案在这个 workflow 开头的那行注释里：

```yaml
# 选 Ubuntu 是因为 Qt 与 OpenCV 一条 apt 即可装齐，Windows runner 需现场编译 OpenCV。
```

**Qt6 和 OpenCV 在 Ubuntu 上就是 `apt-get install`，一条命令的事：**

```yaml
- name: 安装依赖
  run: |
    sudo apt-get update
    sudo apt-get install -y --no-install-recommends \
      build-essential cmake ninja-build \
      qt6-base-dev qt6-base-dev-tools \
      libgl1-mesa-dev libopencv-dev
```

而在 Windows runner 上，Qt 和 OpenCV 都没有现成的包管理器能一条装齐，**OpenCV 得现场从源码编译**——那是以小时计的构建时间，还得配一堆 CMake 选项。为了「CI 和本地同一个平台」，付出这个代价不划算。

**这里我做的取舍是：CI 不负责验证「MSVC 能编过」。** 它验证的是「代码本身是干净的、逻辑是对的、降级路径是通的」。这几个结论在 GCC 下和在 MSVC 下是等价的——因为它们验的是**代码语义**，不是**编译器特性**。真正需要 MSVC 才能验的东西（比如插件的 ABI 那一摊），本地跑就行。

**CI 验所有平台无关的结论，平台相关的留本地。** 这不是偷懒，是把「该在哪儿跑」这件事想清楚。

## CI 两个 job 的分工

![两个 job：一个卡合并，一个只给报告](/images/zyclear/CI两个job.svg)

`build.yml` 里一共两个 job，边界划得很清楚。我把它俩的差异摆成一张表：

| | `build-and-test` | `static-analysis` |
|---|---|---|
| 干什么 | 配置 → 构建 → 跑测试 | clang-tidy 扫全部 `.cpp` |
| 装什么 | build-essential / cmake / ninja / qt6 / opencv | 上面那些，**外加 clang-tidy** |
| 配置差异 | — | 多一个 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` |
| 卡不卡合并 | 卡（失败就是红灯） | **不卡**（`continue-on-error: true`） |
| 产物 | 无 | `clang-tidy.log`（`if: always()` 上传） |

### job 1：配置 → 构建 → 测试，一条直线

```yaml
- name: 构建
  run: cmake --build build

- name: 运行单元测试
  run: ctest --test-dir build --output-on-failure
```

三步：配置、构建、`ctest`。`--output-on-failure` 是关键——**只有失败的用例才打印它的输出**，通过的用例保持安静。

这行参数解决的是一个具体毛病。CTest 默认不显示用例输出，某个用例挂了，你只看到一句 `Test #7: test_cameracontext ... Failed`，**看不到究竟是哪条 assertion、哪个值不对**。`--output-on-failure` 把失败用例的标准输出原样倒出来，报错信息里就带着行号和期望值/实际值。

顺带说一个我没在 CI 里做、但本地必须做的事：**测试目标里刻意不注册海康适配器。** `src/tests/CMakeLists.txt` 里 `test_camerafactory` 这个目标的注释写得很明白——「本目标不定义 `ZYCLEAR_HAS_HIK_SDK`，工厂因而只注册虚拟相机品牌，测试与真机、与厂商 SDK 彻底无关」。**测试用的工厂，跟 CI 用的是同一个降级形态。** 测试能不能跑通，不取决于机器上有没有相机。

### job 2：静态分析单独拎出来，而且不卡合并

这是 `build.yml` 里我思考最多的一块。先看完整的分工声明，注释写得比代码长：

```yaml
# 静态分析单独成一个 job：它比构建慢，且规则随 clang-tidy 版本演进，
# 混在构建 job 里会让「代码能不能编过」这件事被无关告警淹没。
#
# continue-on-error：结论先以报告形式给出，不卡合并。
# 需要把某一类问题变成硬性门禁时，去掉这一行，并在 .clang-tidy 里相应加严。
static-analysis:
  name: 静态分析（clang-tidy）
  runs-on: ubuntu-latest
  continue-on-error: true
```

**为什么单独一个 job，而不是塞进 job 1 的最后一步？** 注释给了两条理由，我展开讲：

**第一，它比构建慢。** clang-tidy 要对每个 `.cpp` 做完整的语义分析，单文件几十秒，`src/` 下所有窗口加起来是分钟级的。**如果把这两件事串在一个 job 里，「代码能不能编过」这个结论就被拖在静态分析后面等**——本来一分钟后就能知道编译结果的，得等好几分钟。分开跑，两者并行，编译结论第一时间出来。

**第二，也是更重要的：规则随 clang-tidy 版本演进。** 今天干净的一个检查项，下个版本的 clang-tidy 可能改了判定逻辑、多报出一批告警。**如果静态分析和构建在同一个 job 里，「构建挂了」和「clang-tidy 多报了几条」这两种红灯长得一模一样**——你会分不清到底是代码编不过，还是只是某个检查项升级了。工具有专门的模块处理这两件事，混在一起就没法处理。

**所以这条划分的实质是：把「代码能不能编过」和「代码写得规不规范」这两个结论，拆成两个独立的信号。** 前者是硬门禁，后者是报告。

**`continue-on-error: true` 就是给后者贴的标签：它红了不算整体失败，不挡合并。** 注释里那句「结论先以报告形式给出」，意思是这个阶段的静态分析是**观测工具**，不是**门禁**。我看报告、决定哪些值得修，但不让一个会随版本漂移的工具卡住全队的提交。

**什么时候该把它变成门禁？** 注释也写了：「去掉这一行，并在 `.clang-tidy` 里相应加严。」**这是有意的两阶段策略**——先跑一段时间、把规则集调到稳定、把存量问题清干净，再把开关拧成硬门禁。一上来就硬卡的后果是：所有人提交都被一堆无关告警挡下来，没几天大家就学会加 `// NOLINT` 了，静态分析退化成走过场。

### 分析用 `xargs -P4` 并行，结果落成 artifact

分析步骤本身有三处细节值得说：

```yaml
- name: 分析
  run: |
    find src -name '*.cpp' -print0 \
      | xargs -0 -n1 -P4 clang-tidy -p build --quiet 2>&1 | tee clang-tidy.log
    echo "::notice::clang-tidy 告警 $(grep -c 'warning:' clang-tidy.log || echo 0) 条"
```

**第一，`xargs -P4` 并行。** 注释写着「单文件几十秒，串行跑完整个 src 太久」。clang-tidy 每个文件是独立进程，天然可以并行——`-n1` 表示每个文件单独调一次 clang-tidy，`-P4` 一次跑四个。**这不是锦上添花，是把分钟级的等待压到能接受的量级。**

**第二，`tee` 到日志。** 结果同时进标准输出和 `clang-tidy.log`。进标准输出是为了 CI 页面能直接看，进文件是为了当 artifact 留存。

**第三，`::notice::` 打印告警条数。** 这一行把日志里 `warning:` 的行数数出来，用 GitHub Actions 的 notice 注解显示在 CI 页面上。**我不需要点开日志就能看到「这次分析了 42 条告警」**——它把一大坨文本压成一个数字，是「报告」这个定位的直接体现。

最后，日志是 artifact：

```yaml
- name: 上传分析结果
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: clang-tidy-log
    path: clang-tidy.log
```

**`if: always()` 是这里的关键。** 默认情况下，前面某步失败了，后面的步骤不会执行。但静态分析**恰恰是失败的时候最需要看日志**——分析挂了、或者告警爆了，你更要拿到那份 `.log` 去看看到底发生了什么。`if: always()` 把上传从「成功才上传」改成「无论如何都上传」，**让这份日志成为失败时的证据，而不只是成功时的纪念品。**

## CMakePresets：把散落的参数固化下来

上面那个 `cmake -S . -B build -G Ninja -D... -D... -D...` 的长命令，在 CI 里写一遍还行，本地天天敲就是灾难——**没人记得住那串 `-D`，于是每个人手上的构建参数都不一样。**

`CMakePresets.json` 干的就是把这件事固化。四套 configure 预设：

| 预设 | 生成器 | 用途 |
|---|---|---|
| `windows` | Visual Studio 18 2026 | 日常开发，产 Debug/Release 双配置 |
| `windows-vs2022` | Visual Studio 17 2022 | 未装 VS 2026 时的替代，其余 `inherits` 自 `windows` |
| `ninja` | Ninja | 导出 `compile_commands.json`，供 clangd / clang-tidy |
| `ci-linux` | Ninja | 与 CI 流水线同款，覆盖缺 SDK 降级路径 |

前两套的关系值得一提——`windows-vs2022` 不是重新写一遍，是继承：

```json
{
  "name": "windows-vs2022",
  "displayName": "Windows / MSVC（Visual Studio 2022）",
  "description": "未装 VS 2026 时用这套。其余与 windows 预设完全一致。",
  "inherits": "windows",
  "generator": "Visual Studio 17 2022",
  "binaryDir": "${sourceDir}/build/vs2022"
}
```

它只覆盖「生成器」和「输出目录」两个字段，其余（`CMAKE_PREFIX_PATH`、`architecture`、`BUILD_TESTING`）从 `windows` 继承。**这意味着两台机器上装的 VS 版本不同，构建出来的东西除了编译器版本之外完全一致。** 如果哪天要改 Qt 路径，改一处 `windows`，两个预设一起变——**没有「改了 2026 忘了改 2022」这种破事。**

后两套是钉死用途的。`ninja` 预设的全部意义就是那个 `CMAKE_EXPORT_COMPILE_COMMANDS: ON`——它对应 `.clangd` 里的配置：

```yaml
CompileFlags:
  CompilationDatabase: build/ninja
```

**clangd（编辑器的补全和跳转）和 clang-tidy 都靠 `compile_commands.json` 才知道「这个文件是怎么编的、包含哪些头」。** 而 VS 生成器**不产**这个文件——所以专门有一套 Ninja 预设来产它。`.clangd` 里那句注释「VS 生成器会忽略 `CMAKE_EXPORT_COMPILE_COMMANDS`，语言服务器便拿不到包含路径」，就是这个预设存在的理由。

而 `ci-linux` 最关键的一行，就是那个 `HikSDK_ROOT`：

```json
{
  "name": "ci-linux",
  "description": "刻意把海康 SDK 指向不存在的路径，顺带覆盖「缺厂商 SDK 时降级构建」这条分支。",
  "generator": "Ninja",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Debug",
    "HikSDK_ROOT": "/nonexistent",
    "BUILD_TESTING": "ON"
  }
}
```

**同一句「刻意指向不存在路径」在 CI 的 YAML 里和预设里各写了一遍——但这不是重复，是让本地能复现 CI。** 我在本地敲 `cmake --preset ci-linux`，得到的就是 CI runner 上跑出来的同一种构建：同生成器、同构建类型、同降级形态。CI 挂了，我不需要去猜 runner 上到底怎么配的，本地一条命令复现。

**把这四套预设合起来看，它买到的事情很清楚：构建参数的唯一来源是文件，不是某个人脑子里的记忆、也不是 README 里一段会过期的说明。** 预设之外还能 `--preset windows -D...` 临时覆盖，但默认路径永远是这四条——**新人 clone 下来，`cmake --preset windows` 一条命令就能开工。**

## 静态分析：`.clang-tidy` 的三条主张

`.clang-tidy` 只有五十来行，但它的注释比配置还多——因为这个文件的重点不在「开了哪些检查」，而在**为什么只开这些、以及边界在哪**。它定了三条主张。

### 主张一：逐条白名单指名启用，不开通配

```yaml
Checks: >
  bugprone-use-after-move,
  bugprone-dangling-handle,
  bugprone-sizeof-expression,
  bugprone-sizeof-container,
  performance-for-range-copy,
  performance-unnecessary-copy-initialization,
  concurrency-mt-unsafe,
  modernize-use-override,
  modernize-use-nullptr,
  readability-container-size-empty,
  portability-template-virtual-member-function
```

实际一共 27 项，一项一项列出来，**没有一个 `bugprone-*` 这样的通配。**

注释把理由写透了：**「不用通配，通配会把噪声也一起打开，报警多到没人看时，静态分析就退化成了一条永远被忽略的红线。」**

**这句话是整个 `.clang-tidy` 的灵魂。** 静态分析最大的敌人不是漏报，是**没人看**。一个通配符展开出几百条检查，里面混着大量和这个项目无关的、或者取舍上可有可无的告警——屏幕上刷出一版红字，第一次你还会认真看，第三次以后你就直接关掉它。**一份没人看的报告，价值是零，甚至负——因为它给了你「我在做静态分析」的错觉。**

**逐条白名单强迫我每加一条检查都想一遍「这条对这个项目到底有没有意义」。** 27 条都是我真觉得值得看的。代价是覆盖窄——通配能顺手捞到的漏网之鱼我这边抓不到。但**一条会被人认真看的窄规则集，胜过一条被人忽略的宽规则集。** 这是取舍，不是缺陷。

还有个纯技术细节值得记：这些检查名是 YAML 的**折叠块**（`>`），**块内的 `#` 不会被当成注释，而是内容**。所以 `.clang-tidy` 里所有说明必须写在块外，块内只允许出现检查名——注释里专门写了这条，因为一不小心就会把一行中文说明变成「一个看不懂的检查名」。

### 主张二：`WarningsAsErrors: ''`——不把警告当错误

```yaml
# 不把警告当错误：CI 里以「产出报告」为目标，避免一次规则升级就卡住所有人。
# 需要强制时在命令行显式加 --warnings-as-errors。
WarningsAsErrors: ''
```

这一条和上面那个 job 的 `continue-on-error` 是一对——**一个在 CI 层面，一个在工具层面，都指向同一个决定：静态分析现在不出手挡人。**

「规则升级卡住所有人」是个很具体的场景：某天 clang-tidy 升了个版本，本来从没报过的一个检查项，在那个新版本里判定变严了，一下多出十几条告警。**如果 `WarningsAsErrors` 开着，这十几条就变成了「编译失败」——而这个失败和任何人的代码改动都无关。** 修它也不难，但问题是：**凭什么一次工具升级，要全队停下来处理？**

所以命令行是默认关闭的，需要真卡的时候手动加 `--warnings-as-errors`。**这把「什么时候严」的控制权留在了人手里，而不是让工具的版本号替我决定。**

### 主张三：只报告自己的代码 + 直接采用项目自己的格式

```yaml
# 只对自己写的代码出报告，不分析第三方 SDK 头文件展开出的问题
HeaderFilterRegex: '(src|examples)/.*\.h$'

# 格式化建议直接采用项目 .clang-format，避免 clang-tidy 与 clang-format 各持一套风格
FormatStyle: file
```

`HeaderFilterRegex` 限定只对 `src/` 和 `examples/` 下的头文件出报告。**为什么？** 因为 clang-tidy 分析一个 `.cpp` 时会把所有 include 的头文件展开进来，包括 Qt、OpenCV、海康 SDK 的头。**那些头文件里如果有什么在 static analysis 看来可疑的写法，报出来也是别人的问题——我改不了 Qt，也不该去改。** 把报告范围钉死在自己写的代码上，日志里剩的就全是我能处理的东西。

`FormatStyle: file` 让 clang-tidy 提的格式化建议直接读项目的 `.clang-format`。**这个设置解决的是「两个工具各持一套风格」的分裂**：clang-tidy 某些检查会顺带建议你怎么排版，如果它用的是内置默认风格，那它建议的和 clang-format 实际格式化出来的就是两套——你按它改了，clang-format 又给你转回来。`FormatStyle: file` 把两者的风格源统一到同一个 `.clang-format` 文件，**建议即最终形态，不会来回打架。**

这份 `.clang-format` 本身也就 21 行，但它有自己明确的边界——`.editorconfig` 的注释写得很准：**「本文件管文件级格式——编码、换行符、行尾空白、缩进宽度；`.clang-format` 管代码级格式——括号位置、指针贴近、换行策略。两者不重叠。」**

## 测试策略：只测不依赖硬件的东西

`src/tests/` 下是 8 个测试目标，每个用例源文件单独一个可执行文件。`CMakeLists.txt` 里那句注释解释了这个结构：

> 每个用例文件单独成一个可执行文件：QtTest 的 `QTEST_MAIN` 宏会在每个用例源文件里各生成一个 `main`，合并进同一目标必然多重定义。

8 个目标分别是：

| 目标 | 被测对象 |
|---|---|
| `test_cameraparam` | 参数模型（header-only，直接包头文件） |
| `test_parseuijson` | JSON Schema 解析 |
| `test_cameraimagequeue` | 图像缓冲队列 |
| `test_listener` | 事件总线 |
| `test_camerafactory` | 相机工厂 |
| `test_cameracontext` | 门面层 |
| `test_cameraparammodel` | 参数模型（表格/渲染侧） |
| `test_imageconver` | 图像转换桥 |

**选被测对象的标准只有一个：能不能脱离硬件跑。** `CMakeLists.txt` 顶部写得斩钉截铁：

> 被测对象刻意只选不含硬件依赖的纯逻辑组件——图像缓冲队列、参数模型、JSON 解析、事件总线、相机工厂与门面——因此测试不需要相机、不需要海康 SDK。

**注意这里连「门面」都测了。** 门面是六层里管多机寻址、生命周期托管的那一层，按理说离硬件不远——但它测的是「序列号怎么映射到设备对象、会话状态怎么流转」这些**纯逻辑**。它依赖的是工厂，工厂在测试里只注册虚拟相机，虚拟相机不需要任何 SDK。**依赖链是「门面 → 工厂 → 虚拟相机 → JSON Schema」，全是软件件。**

`test_cameracontext` 是这个链最长的那个目标，它甚至要把 `resource.qrc` 编进去——因为参数骨架来自 Qt 资源，测试得能读到 `:/VirtualCameraParam.json`。**这说明它的覆盖是真的走到「相机对象、参数、图像缓冲都从门面过一遍」的程度，不是只调一个函数。**

于是这个项目就有了**两层不依赖真机的保障**：

- **第一层：虚拟设备。** 运行时的降级路径，让程序在没相机时也能起来、能被手动操作。
- **第二层：单元测试。** 构建期的验证，让上面那条降级路径的每个组件都有用例盯着。

**它们合起来兜住的事情是：代码能不能编过、逻辑对不对，跟机器上有没有插相机、有没有装 SDK 完全无关。** 这正是 CI 敢用一台光秃秃的 Ubuntu runner 的前提——**不是 CI 环境简陋所以凑合测，是整个项目的可测性设计，就是为了能在这种环境里跑全量验证。**

## 中文开发者会撞上的两个坑

这个项目注释密度高（CHANGELOG 里记着注释率由 2.3% 提到了 11.2%），源码里到处是中文。这对构建体系有两个具体的、绕不开的连带影响。

### 坑一：GBK / UTF-8 编码

中文源码最容易出的问题不是「编不过」，是**编过了但字符串是乱码**。MSVC 在中文 Windows 上默认用 GBK 读源文件，而项目里存的是 UTF-8——**同一份源文件，编辑器里看着是「相机连接失败」，编进 exe 里可能变成一串问号或方块。**

`.editorconfig` 里的 `charset = utf-8` 是这条链的第一环，它让支持的编辑器统一按 UTF-8 读写。但**光靠编辑器约定不够**，编译器那关也得处理——这是中文项目最容易被漏掉的一环。CI 跑在 Ubuntu 上、用 GCC，默认就是 UTF-8，反而不会暴露这个问题；**它只在 Windows + MSVC 的本地构建里发作，而 CI 恰恰覆盖不到那里。** 这也是为什么「平台相关的结论留本地验」——编码这种平台特性差异，Ubuntu runner 是测不出来的。

### 坑二：中文注释的源码被误判成二进制

这个坑 `.gitattributes` 开头一句就把来龙去脉讲清了：

```gitattributes
# 显式声明而非依赖自动探测：源码含大量中文注释，自动探测有误判为二进制的先例，
# 一旦被当成二进制，换行规范化与行级 diff 都会失效

*.cpp           text
*.h             text
*.md            text
```

**git 判断一个文件是文本还是二进制，靠的是一段启发式探测**（大致是看开头若干字节里有没有 NUL、以及各种字节的分布）。**一大段连续的中文（UTF-8 三字节序列）会干扰这个探测**，让 git 在某个文件上做出「这大概是二进制」的判断。**一旦被当成二进制，后果是两件事同时失效：换行符规范化不做、`git diff` 不给你行级差异，只说一句「Binary files differ」。**

对中文项目来说这是很疼的——**你跟同事 review 一个几百行的改动，git 告诉你「二进制文件不同」，你根本看不到改了哪几行。** 所以这里不能指望自动探测，得**显式声明**：`.cpp`、`.h`、`.md` 全是 `text`。`* text=auto` 兜底，然后把「源码、文档、配置」这批明确列出来。

**「显式声明文本类型」这件事本身是个更普遍的原则：凡是自动探测会给中文项目假信号的地方，就别让工具去猜。** `.gitattributes` 里连 `.gitattributes` 自己都声明成了 `text`——**尽职到这个程度，是因为这些元文件如果被误判，损失是最难排查的。**

顺带说一个反过来的坑：`.gitattributes` 把 `.bat`、`.cmd` 强制成 CRLF（`.editorconfig` 里也写了这条，注释是「批处理脚本必须 CRLF，否则部分命令解析出错」）——**这是唯一一处「不统一用 LF」的例外，因为它由不得你。** 中文项目常见的另一类翻车就在这里：为了「统一 LF」把 `.bat` 也改成 LF，脚本当场罢工。

## 我踩过的坑

**坑一：以为「不传 `HikSDK_ROOT`」就等于「测降级路径」。**

我最早写 CI 的时候，配置步骤里根本没写 `HikSDK_ROOT` 这个参数——心想「我不传，它自然找不到 SDK，不就降级了吗？」直到某次我把一个测试用的 SDK 目录结构误提交进了仓库，才发现问题：**那次 CI 里 SDK 是「存在」的，降级路径压根没被走到，但 CI 全绿，没有任何信号。**

**「没传参数」和「明确传一个不存在的路径」是两回事。** 前者把结果交给了默认值和仓库当前状态的巧合；后者是把「SDK 一定不存在」变成一条写死的、不依赖任何其它状态的测试条件。改成 `/nonexistent` 之后，我才敢说「每次推送都覆盖降级路径」这句话——**因为那个路径现在不可能被别的东西满足。** 教训：**当你想测一条路径时，要把触发条件钉死到不依赖任何别的东西，而不是让它「碰巧」成立。**

**坑二：误以为把静态分析塞进构建 job 更省事。**

我一开始的想法是「反正 job 1 都装了 Qt 和 OpenCV 了，clang-tidy 顺手在最后加一步跑不就完了」——觉得少一个 job、少一遍 checkout、少一遍 apt，是省事。

**跑起来才发现两件事都坏。** 一是构建结论被拖慢：明明一分钟能编完，非要等静态分析几分钟跑完才一起出结果。二是**红灯分不清**：有一次 CI 挂了，我第一反应是「代码编不过了」，点进去发现编译全过，是 clang-tidy 报了几条。**那一刻我意识到，「编译失败」和「静态分析有告警」这两个信号必须物理分开**，否则我每次都要先判断「这次是哪种红」。

拆成两个 job、静态分析加 `continue-on-error` 之后，这两种红的含义才彻底分家：job 1 红 = 代码编不过或测试挂了；job 2 有告警 = 可以晚点处理。**教训：「省事」的直觉经常对，但这次错了——两个不同性质的结论，值得为它们各付一遍环境准备的代价。**

**坑三：以为 `WarningsAsErrors` 开着更「严格」、更「专业」。**

我一度觉得「警告当错误」是专业做法——毕竟能保证没人忽略告警。有次 clang-tidy 升版本，之前零告警的项目突然冒出十几条，全是新版本判定变严导致的，和我的代码没关系。**那次所有提交都被卡住，只能临时去加 `// NOLINT` 或者关检查项，等于是被工具的版本号逼着做了一次和业务无关的维护。**

**问题的根不在「严不严」，在「严的时机是不是可控」。** `WarningsAsErrors: ''` 把默认关掉、需要时命令行显式加，是把主动权拿回来——**我不想让一个会自己漂移的外部工具替我决定「今天全队能不能提交」。** 现在这十几个告警只是报告里的十几行，我有空的时候统一处理。**教训：「严格」不是一种美德，是一种要付代价的策略；代价能不能承受，取决于它会不会不定期地强制发作。**

**坑四：忘了给 artifact 上传加 `if: always()`。**

这个坑小但典型。我第一版的上传步骤没写 `if: always()`，默认是「前面全成功才执行」。**结果第一次静态分析真的挂了的那个 push，artifact 没上传——我点进 CI 想拿日志看为什么挂，发现压根没生成 artifact。**

**这正是「最需要日志的时候恰好看不到日志」的经典形态。** 上传步骤的默认语义是「成功才留档」，但诊断的场景恰恰是「失败」。加上 `if: always()` 之后，日志从「成功的纪念品」变成了「失败现场的证据」。**教训：凡是产出诊断材料的步骤，默认就要假设它是在失败路径上被读取的，「成功才执行」在诊断语境里是反的。**

**坑五：以为有 CI 就等于有「全环境验证」。**

项目建成后我对 CI 挺满意：每次推送都构建、都跑测试、都扫静态分析。直到中文乱码这个坑——**它只在 Windows + MSVC 下发作，而 CI 跑在 Ubuntu + GCC 上，永远测不到。** 我一度以为「CI 全绿 = 整个项目没问题」。

**其实 CI 全绿只等于「CI 覆盖的那些结论没问题」。** 它是一个有边界的信号，不是一次全环境检查。CI 选 Ubuntu 是有明确代价的——它测不了 MSVC 的编码行为、测不了插件 ABI、测不了 Windows 上的批处理脚本。**这些留给了本地，而本地不是每次都跑。** 意识到这一点之后，我把「哪些结论 CI 覆盖、哪些不覆盖」这件事写进了对构建体系的理解里。**教训：一个自动化检查的价值，一半在于它测了什么，另一半在于它没测什么——不写清后一半，就会把「绿灯」误读成「什么都对」。**

## 结尾：这个系列，讲了十一个侧面

最后一篇收尾，回头看这个系列。

第一篇从「画墙」开始——六层架构、依赖倒置、三条能 grep 当场验证的约束。**整个系列的骨架就是那一篇立的。** 后面每一篇都在往墙上填一件事：契约层那 17 个纯虚方法怎么切、厂商适配器怎么各写各的、门面怎么用序列号收口多机、参数体系怎么用 JSON Schema 驱动到「加型号不编译」、图像链路怎么用四级异步隔离 SDK 回调和 UI 渲染、事件总线怎么把面板间的 n² 条引用收成一条广播、插件系统怎么跨文件边界买到「加面板不重编」，以及最后这一篇——**这套东西怎么在一台没有相机的机器上被构建、被测试、被反复验证。**

**这十一篇讲的是同一件事的不同侧面：一个工业软件项目，怎么把「变化」和「验证」这两件事，都变成有边界、可自动化、不依赖真机的过程。**

- **变化**被一层层收进了实现层——换品牌只改适配器、加型号只改 JSON、加面板只丢个 DLL。
- **验证**被一层层拆成了不依赖硬件的单元——虚拟相机兜住运行时、8 个测试目标兜住构建期、`/nonexistent` 兜住降级路径。

**而这两件事最后在 CI 里会合。** 一台 Ubuntu runner，没有海康 SDK、没有相机、甚至不是目标平台，但它每次推送都完整地构建、测试、分析一遍——**不是因为它环境简陋所以凑合验，是因为这个项目的设计从第一篇起，就在为「能在这种环境里验证」做准备。** 从六层架构那条「门面能在没有 SDK 的环境里编译」，到测试目标刻意不注册厂商适配器，到 `HikSDK_ROOT` 被钉死成 `/nonexistent`——这些散在十篇里的决定，收在同一个地方。

**「降级路径是常态而非例外」这句话，是我对这套构建体系最想留下的一句。** 一个项目支持「缺依赖时降级」，最大的风险是这条路径从来不被人真的走。这里把它变成了 CI 每次都要走的主路径——**降级不再是一条写在文档里的承诺，是一条每次推送都在被实际执行的、走不通就红灯的路径。**

写到这里，这个系列收束了。如果它只留下一个能被记住的东西，我希望是：**把一件复杂的事做得能自动化验证，比把它做得功能多，更重要。**
