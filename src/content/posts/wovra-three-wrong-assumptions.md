我们做的是一个长时运行的 Agent 运行时，Wovra。它是一个一起写的开源项目，这个系列的每一篇，都是我们某次"押了一个直觉、然后被自己的账本打脸"的复盘。

先说清楚"账本"是什么。第一版运行时就把逐轮开销写进 `task.json`——步数、上下文峰值、名义 token、等效输入、缓存命中、整理成本。名义 token 是每个请求的 prompt 加起来的数，看着吓人；等效输入是把命中部分按折扣价折进去之后真正"有重量"的那部分；缓存命中是 prompt 里有多少 token 命中了前缀缓存。这三个数分开记，是因为名义 token 和实际成本在缓存定价下能差一个数量级——只看名义 token，你会对着 37 万惊慌，对着 11 万放心，而这两者谁贵谁便宜，恰好是反的。

有一个细节，是整篇复盘的前提：**如果没有这套账，下面所有的结论都不存在。** 这三条想当然在"拍脑袋"的层面听起来都很有道理——省 token 当然省钱、命中率高当然好、早点整理当然轻。它们之所以能被推翻，不是因为后来有了更好的理论，是因为每一步开销都被逐条记了下来，于是直觉和账目第一次摆在了同一张桌子上对。文档里有一句我们很认同的话：**仪器先于实验，实验先于优化。** 先有账本，才有打脸。

这个系列的主角就是这本账。

## 一条曲线：从最后一轮回头看

有一个受控实验，同一份 Gradio 项目、同一份冻结的起始文件、同一句任务书（按清单逐轮实现十个功能）、同一个模型，A 组开管理、B 组纯全量回放，会话级 ABBA 交替。两边各跑十几轮。逐轮的名义 token 摊开来看，A 的分布大致是开头几轮小（一两千），中间偶有十几万的大轮（十三万、十七万、二十五万），最后两轮冲到百万级；B 则一路爬升，后半程几乎每一轮都是几十万到一百多万，最后一轮直接 175 万。

两边的上下文峰值也印证同一条趋势：A 从四百出头爬到五万七，B 爬到六万六。这都在说同一件事——会话越往后，历史越长，每一轮的 prompt 越厚。B 组的逐轮名义开销把这件事摊得最明白：开头三轮分别是一千七、三千二、一万一，中间开始出现十一万、三十多万、四十几万的轮，到了倒数第二轮是六十五万，最后一轮直接冲到一百七十五万——**会话最后两轮的开销，比前面十几轮加起来还多。**

于是很自然的推断是：**只要想办法让"厚重"这件事变小，成本就下来了。** 截断、压缩、摘要、每轮整理，全都是这条推断的产物。它几乎定义了我们最早一版运行时的全部优化方向。

三个想当然，全是从这条推断里长出来的。三个都被账本摁住了。下面一个个讲，每次都是先讲"我们当时怎么想的"，再讲"账本上撞到的是什么"。

## 想当然一：截断省 token

![三条直觉，三次被账本推翻](/images/wovra/三次想当然.svg)
这是被推翻得最彻底的一个。我们当时的原话更狠一点：**"截断省 token"是幻觉**——不是"不够好"，是方向都反了。

它是靠三代机制、同一个任务，一次一次换出来的结论。任务只有一个：给一个约 41KB 的 `chat.html` 加功能。三代机制都在同一个会话、同一句用户输入下跑过。

| | 第一代：轮内折叠（50 事件软限制） | 第二代：无折叠 + 2KB 截断 | 第三代：零截断 |
|---|---|---|---|
| 结果 | 撞 40 步上限，只落地 3 个 edit | 用户中断，**0 个 edit** | 一轮完成 6 组新功能，18 个 edit |
| 读取 | 39 次 `read_file`，区间大量重叠 | 11 次，每次只见结果的前 2000 字符 | **3 次，理论最小值** |
| 名义 token | 未记账（当时开放轮无 usage） | **110,080** | **374,732** |
| 缓存命中 | — | 87.3% | 89.8% |
| 等效输入 | — | **≈16,675** | **45,612** |

第一代的死法很典型。轮内折叠会把**模型同一轮里刚读到的内容**也折成一行索引，于是形成一个正反馈：读文件 → 事件涨 → 早期的读取被折叠 → 失忆 → 重读 → 事件更多 → 折叠更快。实测的读取区间是 `694-1003 → 700-769 → 864-1003 → 884-933 → 960-1003`，同一段反复读，40 步烧完，只落地了 3 个 edit。

第二代换了个死法。折叠废掉了，读取区间确实不再重叠——11 段互不重复。但每一段将近 20KB 的结果，进上下文时被截断到前 2000 字符。模型面对的是一个**2000 字符的锁孔**，只能一寸一寸蹭完整个 41KB 的文件。那一轮的账是：11 万名义 token 全部沉没，零产出，用户主动按下了中断。

**这里有一个必须说清楚的地方，因为它跟"贵不贵"没关系。** 看表里那张账：第二代失败轮的等效输入约 1.67 万，第三代成功轮约 4.56 万——**失败的那一轮，等效输入反而更低。** 所以我们最后推翻截断，不是因为"截断更贵"。按等效成本算，截断那一轮甚至更便宜。

推翻它，是因为那一轮**产出为零。** 文档里那句话写得很准：省上下文的机制省错了地方，**钱花了，活没干**。等效输入是唯一的成本口径，但它只在"活干成了"的前提下才有意义——省下来的 token 换不来任何东西，那这些 token 省得再漂亮也是纯损失。

还有两个细节值得单独拿出来说，它们合起来解释了为什么截断会从"省一点"变成"全盘崩"。

一是**那段理论最小值的读取不是运气**。第三代之所以能三次读完全文，靠的是另外两个配套机制：文件地图和锚点自愈。文件地图把降档历史里的文件列成"路径 + 写/读轮次"的清单注入装配，模型一眼就能定位该读哪个文件，不用盲目重爬——实测重读次数从 39 降到 3。锚点自愈则是在编辑未命中时，把最接近的内容行号回给模型，让它一次修正，而不是整文件重读。**读取次数从来不是靠"让模型更聪明"降下来的，是把"它在找什么"这个问题直接从上下文里消掉。**

二是**那个坏掉的把手**。第二代里，模型一次都没有调用 `expand_history`——那个"展开原文"的工具，零次。不是它没想到，是它判断这条路走不通：工具的上限被写死在一个数值上，对将近 20KB 的结果，"取回完整原文"这个承诺根本兑现不了。**模型正确地拒绝使用一个坏掉的把手。** 我们后来意识到，一个清醒的模型对残缺的工具有免疫力——它不会去够一个够不到的东西，它只会绕路，而绕路的代价就是那 11 万沉没的 token。所以"给个截断的把手、指望模型自己补救"这条路，从一开始就不成立。

第三代的读取区间是 `(1-400)(401-800)(801-1134)`——恰好是理论最小值，三次读完全文，零重叠。文档里对这件事的总结我们很喜欢：**没有任何一步花在"找回本该在眼前的东西"上。**

于是第一条机制就这么定下来了：**执行期零截断，压缩只属于整理侧。** 眼下不做任何剪切，唯一的天花板是模型自己的窗口——只有估算到"当前轮快撑满窗口的 90%"时，才紧急折叠最老的事件，而且那是最后手段，不是常规手段。轻中度的负载根本碰不到这条线（那个受控实验里，峰值只到窗口的 3% 到 6.6%）。

## 想当然二：命中率至上

第二个想当然短一点，因为它的完整推导留给这个系列后面一篇（"缓存命中率是折扣，基座才是税基"专门讲它），这里只记我们当时怎么被打脸的。

先交代我们的"立场偏见"：我们这一整套上下文管理，几乎是围绕"追加式装配"设计的——每一轮历史都往后追加，不回头改写前面的内容，因为这样前缀最稳定、缓存命中最高。这个设计本身没错，错的是它带来的**心理惯性**：既然命中率是我们花了大力气才做上去的，就自然而然地把它当成了成绩单。**一个自己努力挣来的数字，最容易变成不想质疑的对象。**

我们是做缓存的——上下文越"追加式"，前缀越稳定，缓存命中越高，成本越低。这条逻辑对得一塌糊涂，于是我们很自然地把它当成了优化目标：**把命中率干上去。** B 组是纯全量回放的纯追加结构，简直是为前缀缓存量身定做的布局，它的最好一轮命中率**99.3%**。

99.3%。看着像是拿到了满分。

然后账本摊开：那一轮单轮 prompt 是 592,560 token，99.3% 命中，当轮等效约 5K——漂亮。但同一个 B 组，另一轮 31 步、上下文 66K、命中率 96.4%，当轮等效**仍然接近 118K**。

命中率都在 96% 以上，等效成本却差着一个数量级。差在哪？差在**基座**——那一轮要重新按原价计算的、没有被命中的那部分底子，本来就大。

换个方式看这两轮，会更清楚：

| | B 组某一轮 | B 组另一轮 |
|---|---:|---:|
| 单轮 prompt | 592,560 | 66K 上下文、31 步 |
| 缓存命中 | **99.3%** | 96.4% |
| 当轮等效成本 | ~5K | **~118K** |

左边那轮的命中率更高、prompt 更大，等效成本却低得离谱；右边那轮命中率只低了不到 3 个百分点，等效成本却是它的二十多倍。**左右两轮的差别几乎全在基座，不在折扣。** 这就是为什么"命中率至上"这个想当然会骗人——它许诺的最优形状，和一个真实便宜的轮次，根本不是同一个形状。

我们把这个模型总结成一句话，它后来成了整个系列的题眼：**命中率决定折扣深度，基座决定税基。** 96% 的折扣救不了一个臃肿的税基。你在一大坨要付费的底子上打 96% 的折，付的钱还是比在一小坨底子上打 80% 的折多。这也解释了为什么"参考组"和"管理组"在有些轮次上命中率只差一两个百分点，等效成本却差一个数量级——**它们差的从来不是命中率那一两个点，是基座那一整个量级。**

顺着这个模型还能推出一件反直觉的事：**有时候"主动破坏一次缓存、把基座压低"比"维持高命中"更省。** 因为整理本质上就是一次主动的、一次性的缓存破坏——你付出这一轮全量重算的代价，换来之后所有步骤都站在一个低得多的基座上。什么时候值得破坏、破坏后压多低，这才是管理机制真正的决策点，而不是"怎么把命中率再提高 0.5 个点"。

所以第二个想当然的分量其实是"我们优化错了指标"：命中率是**诊断指标**，不是优化对象。真正该盯的是基座有多厚。这一条的技术含量在最平凡的算术上，不需要实验——但它推翻的是一个我们做了很久的方向。

## 想当然三：每轮必整理

第三个是三个里**测得最扎实**的一个，因为它有一个特别刺眼的账目。

V2 的规则叫"轮闭合即整理"——每一轮结束，就把这一轮的历史压缩、整理成结构化的视图。理由也很顺：历史越早整理越轻，拖着不整理只会越堆越厚。

实测：**14 轮整理，一共花了 98,111 token，平均一轮约 7K。**

平均 7K 听着不多。但账本里有一轮把这件事戳穿了：**第 2 轮，干活本身花了 2,816 token，整理花了 3,118 token——整理比干活还贵。**

这就是"过早优化"的教科书形态：一轮只需要 2.8K 的活，你花 3.1K 去整理它。而更致命的是总账——把整理成本算进去，管理组和裸跑到最后**打平了**：

| | A 管理组（14 轮） | B 裸跑（15 轮） |
|---|---:|---:|
| 名义 token | 2,255,448 | 4,966,437 |
| 等效输入（不含管理） | 377,668 | 475,686 |
| 整理开销 | 98,111 | 0 |
| **含管理的等效成本** | ≈475,779 | ≈475,686 |
| 步数 | 112 | 153 |
| 上下文峰值 | 57,472 | 66,456 |
| 工具报错事件 | 10 | 16 |

看那两行：**不含管理时，管理组比裸跑省了 1.26 倍；把 98K 整理费加回去，两边的比值变成 475,779 对 475,686——约等于 1.00。** 那 98K 的整理费，把管理机制在等效成本上的**全部优势，吃回去了。**

这个表还藏着另一个反直觉：管理组的步数（112）比裸跑（153）少了 27%，上下文峰值也低了——**管理确实让每一轮变轻了，这一点它做到了。** 它输的地方不在"有没有把活变轻"，而在"变轻赚到的钱，刚好被整理的固定开销花光"。这也是为什么我们最后没去优化整理的"质量"，而是去优化整理的"频率"——一个做对了事、但做错了量的机制。

我们当时面对这个数字的第一个反应是"是不是整理得不够好"，第二个反应才是"是不是根本不该每轮都整理"。答案是后者。

先解释为什么"每轮整理"听起来那么合理。整理做的是把一段原始的对话历史，压成结构化的视图——哪些文件动过、哪些决策定了、状态字段现在是什么。它的动机是好的：越早整理，历史越轻，后面每一轮的基座越小。但这里有个隐藏的假设，就是**整理的成本，跟它要整理的内容成正比、跟会话长度无关。** 实际不是。轻的一轮只有两千多 token 的活，整理它同样要走一遍完整的整理流程——读这一轮、生成结构化视图、落盘。于是固定成本砸在了可忽略的内容上。

V3 改成了**水位触发的批量合并整理**：轮闭合后不再立刻动手，没整理的轮先把原始体量挂着，等挂到一条水位线再一次批量收编。水位线的默认值是 100,000 token。

这个改动的漂亮之处在于它**对小会话自动免疫**：会话从头到尾都没到 10 万 token，那水位永远不触发，整理成本就是零。早期再也不会有"负优化"——小会话零整理，大长会话才付批量整理的钱。

批量还有两个附带收益，是逐轮整理给不了的。一是**跨轮去重**：模型在很多轮里会反复交代同一件事（这个项目的背景、这个决策的理由），逐轮整理时每次都要记一遍，批量合并时天然去重。二是**摊薄**：N 轮 N 次整理调用，合并成 1 次。但有一条底线不能动——**合并的是"上下文视图"，不是原始历史。** 每一轮的原文和事件 ID 原样保留，你随时能精确回到某一轮问"这个参数是哪次测的"。压缩的只是给模型看的那个视图，不是账本本身。

这里我们想留一个方法论上的记认，因为它是三条想当然里唯一一个"改了参数就解决"的。整理本身没错，错的是**它被无条件地绑在了"每轮"这个节奏上。** 一旦把触发条件从"事件发生（轮闭合）"换成"状态到线（水位）"，固定开销就从"每轮一定付"变成了"可能永远不付"。这类修正的性质，和截断那一条完全不同：截断是方向错了，得整个换掉；每轮整理只是量错了，换一个触发器就够。**判错一个想当然的"性质"，会决定你接下来是改一行还是改一整套。** 我们一开始差点在"把整理做得更好"上花时间——那就是把"量错了"误判成了"方向错了"。

## 附赠的第四次：多 Agent 没更快，但贵了 4.6×

第四个想当然不在最初那三条里，是后来撞出来的，但值得记一笔，因为它的**结论常被一句话概括错**。

我们的项目有一层"组织运行时"，可以派子 agent 并行干活。直觉说：三个子任务并行，墙钟时间应该是三分之一。这个直觉甚至还有理论支撑——三个子任务在数据上确实是独立的：一个写游戏逻辑、一个写渲染引擎、一个做程序化贴图，互不依赖。**但独立不等于划算，也不等于快。** 实测用一个 Minecraft 复刻任务跑了三组对照：

| | A 单 agent（旧栈） | B 组织：3 子并行 | D 单 agent（新栈） |
|---|---:|---:|---:|
| 墙钟 | 116 分 | **108 分** | 94.5 分 |
| 等效输入 | 263K | **1,218K（+4.6×）** | 857K |
| 现金 | ≈0.45 元 | **≈1.10 元（+2.4×）** | ≈0.59 元 |
| 缓存命中 | 98.3% | 88.1% | 96.6% |
| 观感评分 | 0 | 1 | 通过 |

108 分对 116 分——**7%，在噪声里**。文档自己用的词是"≈持平"。

所以这里有一句我们必须写准的话：**多 Agent 不是更慢，是更贵。** 差 7% 的墙钟，你甚至没法说它是变慢了。真正的发现是：三个并行子 agent，买来的墙钟改进是**零**，代价是 4.6 倍的等效 token 和 2.4 倍的现金。

把 4.6× 拆开看，构成也很清楚：最大的一项是**冷启动税**——每个子 agent 都从零建自己的上下文，读契约、重爬文件、缓存从零爬坡，命中率 73.8% 到 94.5%，而单 agent 是 98.3%；等效成本每步 6K 到 10K，单 agent 是 2.7K。剩下的是翻译与调度的开销（主 agent 224K 等效只产出调度与汇报）、各块自带的 mock 和接口适配的重复劳动、以及多轮重建装配尾部造成的缓存破坏。

那个实验还有一个当时没在预期里、后来却很关键的对照：前面这一组的数据是旧栈跑出来的，后来同一句话在**新栈的单 agent** 上重跑了一遍，墙钟 94.5 分——比三个子 agent 并行的 108 分还快，等效成本只有它的七成。也就是说，**"单 agent"这一边后来自己提速了，而"多 agent"那边没有。** 并行不是没起作用，是它的收益被一个更慢的单体拖累的事实，盖过去了。

但有一个当时没被这组数据回答的问题，我们后来还是得自己认下来：**这三个数字，比的到底是"多 agent"还是"旧栈"？** 表里 B 组是旧栈的 3 子并行，A 也是旧栈，所以 B 对 A 的 4.6× 是干净的。可 D 是新栈单 agent，它比 A 快、比 B 便宜——这说明"栈"本身也是一个很大的变量，和"agent 数量"缠在一起。我们能确定的是：**在旧栈下，3 子并行比单 agent 贵 4.6 倍而不更快；** 至于"多 agent 这个方向在更好的栈上会不会翻身"，这组数据回答不了，我们也没打算假装它回答了。

这也直接通向这个系列后面第 3 篇的主题（"一次被数据判死的架构"）：组织层的价值主张最后收缩成了几项，而"并行更快"这条不在里面。这一篇只记那个数字：**多 Agent 没更快，但贵了 4.6×。**

## 那把量尺：等效输入，和它的刻度

三个想当然能被同时推倒，是因为有一把共同的尺子：**等效输入**。名义 37 万、命中 89.8%、等效 4.6 万——同一个"不截断"的动作，在名义口径下是"变贵了"，在等效口径下是"最便宜的布局"。**名义 token 是假象，等效输入才是成本。**

这个区别不是学术上的。我们最初盯着名义 token 看，得到的是一组**完全相反**的行动建议：名义高就该截断、该压缩、该少读——每一个建议都指向那三代机制里的前两代，每一个都被实测证伪。换成等效输入再看，同样一组数字给出的建议是：**别动眼前的上下文，把力气花在别让模型重读上。** 同一本账，两个口径，两套互斥的优化方向。所以"用什么口径记账"这件事，本身就是设计决策的一部分——**你选了哪个数当目标，就已经选好了后面要撞哪堵墙。**

但这把尺子自己有一个刻度我们后来才看清：等效输入 = 未命中部分 + 命中部分 ÷ 折扣率，而这个**折扣率的深度是服务商的参数，横跨整个行业，从 1/40 到 1/5，差 8 倍。** 我们初稿按 1/30 算，得出"管理含整理成本后打平（1.00×）"。把折扣率当变量重算，结论整个不一样：

| 缓存折扣 | 含整理开销的管理/裸跑 | 谁赢 |
|---|---:|---|
| 1/40（最深的折扣） | 0.95× | 管理**略亏** |
| 1/30 | 1.00× | 打平 |
| 1/10（行业主流） | 1.30× | 管理赢 |
| 1/5（最浅的折扣） | 1.58× | 管理赢 1.6 倍 |

规律很干净：**折扣越深，管理越不值钱**（因为省下来的基座本来就不贵）；**折扣越浅，基座税越重，管理越值钱。** 折扣为零的极限下，管理反而略输——因为裸跑零管理成本，而那 98K 整理费是管理永远甩不掉的结构性代价。

盈亏平衡点在折扣约 1/25 附近。这件事的真正教训不是"管理好不好"，是：**任何"打平/领先"的结论，都必须标注它是在哪个折扣深度下算出来的。** 我们最开始差点把一个"1/30 下打平"写成"普遍打平"，那是错的。

我们还做过一次更诚实的检验，是拿两套真实价目表，把同一堆生产账目各结算一遍（同一份账本、只是换价）：在 DeepSeek 的空闲价下，管理组比裸跑省 1.48 倍；在另一个半价套餐下，省 2.65 倍。同一堆 token、同一个机制，**光换价目表，优势就从 1.5 倍跳到 2.6 倍。** 这说明"管理值不值"从来不是一个机制属性，而是一个机制 × 价目的联合属性。轻负载（受控实验里基座本来就小）下整理甚至可能是净支出；负载越重、基座税越大，管理越值钱——**同一个公式，解出两个方向相反的答案，区别只在税基的厚度。**

## 账本顺手撞出来的第五件事

做这几个实验的时候，账本还顺手记下了一批根本不在上下文管理范畴里的开销：一个测试服务占着端口不放、服务重启后跑的还是旧代码、文件被外部改过后又被旧内容编辑、代理卡在 Fake-IP、依赖装错了环境。

它们跟上下文有什么关系？关系很大，因为它们造成的是同一条因果链：

```text
运行时不可靠
  → Agent 反复排查运行时问题
  → 步数增加 → 上下文增加 → token 增加
```

账本里最贵的一个单轮就是这么来的：对照组的某个会话，因为"旧服务占着端口 + 没有归属管理"，整整多烧了一轮，175 万 token——全场最贵的一轮，而它干的是本可以完全避免的排查。

这件事让我们把一句话写进了文档：**好的运行时本身，就是一种上下文优化。** 它不属于上下文管理机制，但它是上下文管理的成本上游。所以我们把它单独立成一个方向（运行时治理），不往上下文管理里塞——**什么都能管的代价，是没有任何一个机制被真正验证。**

值得记一笔的是，这些问题里有一半最后是用"账本"本身修掉的。后台进程开始记录自己是从哪个会话启动的，跨会话查看或停止会被拒绝，会话退出时该会话的后台进程连带整树关闭——于是"旧服务占着端口"这种只有人工才会发现的残留，变成了运行时自己就能挡掉的事。这个方向的原则很简单：**每一个上下文开销，先问一句"它是不是压根不该发生"，再考虑"怎么优化它发生时的开销"。** 前者往往比后者便宜得多。

## 说清楚我们有多不确定

这一篇的所有数字，都来自 `task.json` 的逐轮落盘，没有人工修饰。但也仅限于此。我们不想把 n=1 的实验包装成统计结论，所以把文档里那几句诚实声明原样摆出来。

关于三代截断实验：**n=1，模型输出有非确定性；B 是不同对话的参照而非严格对照。结论的强度来自三代机制在同一任务上的方向一致性，而非统计显著性。** 换句话说，我们信的不是"39 vs 3 这个读数"，是"三代机制在同一个任务上，方向一直指同一个地方"。

关于 Minecraft 的多 Agent 对照：**n=1、无重复；任务为纯前端观感类，任务书不含可自动化验收——观感结论里"模型上限 vs 运行时质量"的归因分不清。** 它可信的部分是成本、时间和机制验证；观感评分那几列不可信。

还有一条更硬的边界：**V1–V3 这些机制，连同 baseline 对照，现在全都标了"淘汰"。** baseline 模式已经从代码里删掉了，V3 也被 V4 取代——V4 甚至把"整理"这件事整个换成了逐轮笔记。也就是说，这一篇里所有漂亮的数字，**都来自已经被移除的机制**。它们的价值是**历史证据**——结论还在影响设计，但机制本身已经不存在了。我们引用它们的时候会一直带着这句话，免得读的人以为这些是现役机制的性能。

这三条边界叠起来，就是这一篇的全部可信范围：**方向可信，机制已废，数字别当精确刻度用。** 我们宁可把这句话写得比结论还醒目，也不想让一次 n=1 的实验被读成一条行业规律。

## 踩过的坑

**坑一：以为"省 token"和"省钱"是一回事。**

这是我们摔得最狠的一个。截断确实把上下文变小了，第二代失败轮的等效输入甚至比成功轮更低——按"省 token"的口径，它做得比成功轮更好。可它的产出是零。**等效成本是一个条件成本，它的成立前提是"活干成了"。** 我们现在看任何"省了多少 token"的指标，第一件事是问：省下来的这些，产出还在吗？

**坑二：把一个容易测的指标，当成了该优化的指标。**

命中率好测、好看、还能画成一条向上的曲线，于是我们追了它很久。基座难测、不好看，但才是税基。这个坑的教训不是"命中率没用"，是**"好测"和"该优化"之间没有必然关系**——一个指标越容易变成漂亮曲线，越要警惕它是不是只是"诊断"，不是"目标"。

**坑三：加速了平均，没加速关键路径。**

三个子 agent 并行，直觉上应该更快。但实测墙钟只差 7%。我们后来越来越确定，这个 7% 不是"并行的加速不够"，是**"加速根本没有落在关键路径上"**——子 agent 的冷启动税、主 agent 的翻译调度、多轮缓存重建，全都在关键路径上，把并行省下的那点时间又填回去了。并行度不是免费的，它的成本恰好也长在关键路径上。

**坑四：把"n=1 的方向一致"说成了"结论"。**

这是我们一直在跟自己较劲的地方。文档写"方向一致性"，我们写文章时手会痒，很容易滑成"实验证明"。目前每次都用"我们的判断是"来兜。但说实话，**一个只在一台机器、一个模型、一个任务上成立的方向，它离结论有多远，我们自己也没有一把尺。** 这是这个系列一直没解决的问题。

**坑五：把"被数据推翻"当成了一次性事件。**

写完这篇回头最不舒服的一点：这三堵墙没有一堵是撞一次就完的。每改一版机制，我们都会重新长出新的想当然——比如 V3 封版后，"水位触发一定比逐轮整理好"又成了一条没人验证的直觉；再往后，"按上下文窗口体量算水位"又替代了最早"按积压量算水位"的口径，用户拍板才改过来。**账本能推翻一个直觉，但推翻不了"人会不断产生新直觉"这件事。** 这个系列存在的意义，大概就是让每一次打脸都留下记录，而不是过一版就忘了上一版撞过哪。

**坑六：把"方向一致"当成了"因果确定"。**

三代截断实验最容易被误读的地方，是它的"方向一致性"。三代机制在同一个任务上，读取次数一路从 39 降到 11 再降到 3，方向非常干净。但方向干净不等于因果干净——三代机制之间除了"截断的松紧"，还同时改了别的东西：第二代到第三代之间，除了废除 2KB 截断，还一起加了窗口保底和文件地图。**也就是说，"3 次读取"里有几成是零截断的功劳、几成是文件地图的功劳，这批数据分不开。** 我们在文章里把它们分开讲，是因为后续的机制验证清单把每一项都对上了证据；但如果只看那条 39→11→3 的曲线，是分不出来的。**方向一致是"值得继续查"的理由，不是"已经查清"的理由。**

## 最后：变掉的是问题，不是答案

回头看这三个想当然，它们有一个共同的结构：**都是从一个看起来无懈可击的直觉出发，推向一个具体的动作，然后在账本上撞到一堵墙。**

| 我们以为 | 于是做了 | 账本上撞到 |
|---|---|---|
| 省 token = 省钱 | 执行期截断、折叠上下文 | 产出为零，钱花了活没干 |
| 命中率高 = 成本低 | 把命中率当优化目标 | 99.3% 命中依然贵，基座才是税基 |
| 早整理 = 更轻 | 每一轮闭合就整理 | 整理比干活贵，优势被 98K 吃光 |
| 并行 = 更快 | 三个子 agent 并行 | 墙钟持平，等效 4.6×、现金 2.4× |

四行里有一行是"方向错了"（截断），一行是"指标选错了"（命中率），一行是"量错了"（每轮整理），还有一行是"对照选错了"（多 agent）。**四种错法需要用四种不同的方式修正**——这是我们在复盘里反复体会到的一件事：一个想当然被推翻之后，下一件事不是"改它"，是"先判清它是哪一类错"。

而四条墙撞下来，改掉的其实是**问题本身**。最开始我们的问题是"怎么让 token 变少"；现在我们的问题是"**怎么让基座站得低、又让每一步的等效成本不被重读加倍买回来**"。前者的答案是压缩、截断、摘要；后者的答案是执行期零截断、水位触发批量整理、把命中率降级成诊断。

这两个问题看起来只差几个字，但它们能导出的设计，一个都不重合。举一个最小的例子：如果问题还是"怎么让 token 变少"，那"执行期零截断"看起来就是彻头彻尾的倒退——名义 token 从 11 万涨到 37 万，账面上一塌糊涂。只有当问题换成"怎么让基座低、又不让重读把省下的钱买回去"，你才会看到：那 37 万名义背后是 89.8% 的命中，等效成本只有 4.6 万，而且它一轮就干完了活。**同一个动作，在两个问题下一个是错、一个是对。**

再往深一层看，这三个想当然的根是同一个：**我们都在"怎么让看到的东西变少"上想办法，而真正该想的是"怎么让留下的东西更值"。** 截断是少看、整理是少留、优化命中率是让重复的部分别计费——三条路都指向"减少"，没有一条指向"提高单位信息的价值"。而账本逼我们承认的是：在这个成本结构里，"少看"反而贵，"看全"反而便宜，因为重复的前缀是打了折的，而重读是要按原价买的。**省的方向和贵的来源，恰好相反。**

这也是为什么我们愿意把这些"失败"写出来而不是藏起来：**被推翻的不是答案，是问题。** 而问题的替换，比任何一个具体机制的修正都值钱——修正一个机制，你改的是一行；替换一个问题，你换掉的是整套能导出的方向。

下一篇讲第二条墙背后那把尺子：为什么 99.3% 的命中率依然很贵，折扣的光谱为什么能差 8 倍，以及"什么时候值得主动破坏一次缓存"这个比"怎么提高命中率"更有意思的问题。
