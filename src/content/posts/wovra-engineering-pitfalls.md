工程文章里的坑，十有八九长这样："记得给共享状态加锁"、"注意 JSON 解析失败要兜底"。这些话都对，但都对得没有信息量。

它们有个共同的毛病：**教你怎么让系统"不崩"，不教你怎么让系统"不撒谎"。** 前者靠经验就能积累，后者需要你怀疑一整套东西——包括怀疑"我自己用来证明没问题的工具"。

这一篇要挑的是另一种坑——**测试通过了、仪器全绿了、数据显示赢了，而这三件事里至少有一件是假的**。它们不是逻辑 bug，是**证据本身坏了**：你拿来证明"系统没问题"的那套东西，自己就有问题。

按"欺骗发生在哪一层"分成五类：**仪器类**（跑测量的工具坏了）、**测试类**（绿灯不代表验证过）、**口径类**（数字算错了）、**环境类**（对照组根本不在同一个世界里）、**逆向承诺类**（系统说它做了，其实没做）。每一类先讲一个标本，再讲这一类的共同形状。

## 先看清单：这批坑长什么样

![全绿的三样东西，全都撒过谎](/images/wovra/工程坑.svg)
一次以"把项目在 Windows 上跑通"为目标的体检，最后清出了七个真 bug，其中两个在 Linux 侧**根本看不见**：

| # | 坑 | 类别 | 为什么平时看不见 |
|---|---|---|---|
| 1 | tiktoken 首次加载无限阻塞 | 环境 | 开发机词表早就下好了 |
| 2 | 钩子拦截理由被 GBK 吞掉 | 环境 | Windows 独有 |
| 3 | 安全探针三个 symlink 共用一个 try | 测试 | Windows 无 symlink 特权才触发 |
| 4 | 结算产物不可用没有第二跳 | 逆向承诺 | 要跑失败分支才现形 |
| 5 | 注册表同名身份分裂 | 逆向承诺 | 要等重载才收口 |
| 6 | `delete_file` 的假承诺 | 逆向承诺 | 要非 UTF-8 / 界外文件才触发 |
| 7 | `except Exception: pass` 吞掉回落机制 | 逆向承诺 | 要等回落真的该发生才暴露 |

这张表最值得盯的是最后一列。**它们的共同点不是"难修"，是"难发现"**——日常使用永远碰不到，只有换平台、换输入、换用途，或者换个人来核，才会现形。这也解释了为什么一个"928 passed / 0 failed"的项目，还能同时藏着七个真 bug：**门禁测的是"跑过的路"，这些坑全在"没跑过的路"上。**

而且注意第 6、7 两条都属"逆向承诺类"，第 4、5 条也是——**七个里有一半**。这不是巧合：**"让功能跑通"是测试会逼你做的事，"做不成了要如实说"是测试逼不出来的事。** 一个套件可以测出"删除成功了"，测不出"删除失败时回执还写着成功"。第一类坑是能力问题，这一类是诚实问题，而诚实问题恰好是自动化最够不着的地方。

## 仪器类：只剩自己的桩在引用它

有一个函数，`maint_health.py` 里的健康检查会用到它，测出来"全绿、exit=0"，829 个测试全过。一切正常。

一次死代码审查翻了案。审查逐个函数做"定义点 + 全仓调用点（含 tests/scripts）+ 生产可达性"三重核对，查到 `_render_compact` / `_render_collapsed` 这两个函数时，`dead-code-review.md` 的结论是这样的：

> 调用点已在 `62f5c91` 删掉；**唯一引用是 `scripts/maint_health.py:93-157`（monkeypatch 替换它做测量）**——即工具只在"换上自己的桩"时引用，**从不真调**。

这句话要慢慢读。健康检查工具不是在**调用**这两个函数、看它们返回什么——它是在**替换**这两个函数，换成自己的桩，然后测那个桩。也就是说，这两个函数在健康检查里扮演的角色是一个"可被替换的占位符"，工具从来没真正执行过它们的本体。它们在生产里早就死了，但**它们死得太干净了，连仪器都察觉不到**——因为仪器自己也不碰它们。

审查报告由此记下一条方法论级的教训：

> 只做静态审查会漏掉**仪器已坏**。

而更绕的是第二层：这次静态审查**自己也没发现 `maint_health.py` 是坏的**。后来才补上一条更狠的——

> 静态审查看不到"工具已坏"，跑一次仪器才看得到。

一整套"三重核对"的静态审查，把一个"常驻仪器其实跑不起来"的事实漏了过去。修在 `b48745e`。这不是"审查不仔细"，是**审查这个动作的射程之外**：静态审查能证明"没人引用"，证明不了"引用它的人在这种诡异方式下引用它"。修法也是三步走的最后一步才碰它——先清机械小修，再清可安全删的函数，最后才处理"删函数会连带弄坏仪器"的那批。

### 这个坑的形状：一个闭合的假测量回路

把这条抽出来看，它的形状是"**测量和被测量的东西隔着一层替换**"。健康检查本来想验证"渲染函数工作正常"，但它做的是"把自己的假实现塞进去，验证假实现工作正常"。一旦真实现坏掉，它照样绿——因为**它测的根本不是真实现**。

这一类最阴的地方在于：**它不是 bug，是"测试回路闭合"的假象**。缩成最小模型就是——你想测 `foo()`，于是 `monkeypatch.setattr(foo, fake)`，然后 assert `fake` 被调用了。这个测试永远是绿的，哪怕是 `foo` 被删成空函数也一样。它证明了"我写了个假函数并调用了它"，没证明任何关于 `foo` 的事。

同一份死代码审查里还记了两条同类形状，说明这不是孤例：

- **`_file_map_lines`**：唯一引用也是仪器（`scripts/maint_health.py:193`），生产中恒为 `[]`——因为对照组删除（三）已经把它恒置空，函数体成了纯死代码，但仪器仍在引用它做测量。
- **`_split_view_watermarks`**：src 无调用点，但**脚本**（`diag_view_watermarks.py`）还在用——删函数会让脚本 `NameError`，所以它卡在"生产已死、取证脚本还活着"的灰色地带。

两条合起来揭示了同类坑的变种：**引用它的不是生产、不是测试、而是取证工具**，静态扫描"有没有引用"会给它一个"活着"的假证。死代码审查最后把方法固化下来，并注明"不要照它再删一遍"——因为清理本身也踩过坑，比如"只看 src 调用点就删、测试会红"（曾连带删掉 `_HISTORY_SNIPPET`）。**审得再细，也得先跑一遍才算数。**

## 测试类：绿灯，但补丁从没生效

### 33 条断言在 Windows 上从没跑过

交接文档里有一句很冷的话：

> **33 条安全断言在 Windows 上从没跑过。**

全是 `test_safety.py` 里的符号链接断言。Windows 本机没有 symlink 特权，pytest 把它们全 skip 了——测试套件报的是绿色，那 33 条断言一条也没执行。它们不是失败了，是**从来没开始**。修在 `e37130e`，顺带把 skip 消息改成诚实的说法："这批断言在本机没有跑"。

这里的欺骗是**"skip 冒充 pass"**。测试框架输出的绿色是一个**汇总色**，它对"通过"和"跳过"一视同仁。33 条里藏着越界检查、路径守卫这些最该跑的东西，但它们在汇总里只是一行"33 skipped"，被淹没在"928 passed"的凯歌里。

它潜伏了多久？**从这个测试被写下的那天起，一直到有人在新机器上跑出"33 skipped"为止**——这期间它一直报绿。暴露它的不是某个测试失败，是有人**去看了一眼 skip 的构成**：为什么是 33 条？这 33 条是什么？一看全是符号链接断言——而符号链接在 Windows 上本来就跑不了。**这条坑的暴露方式，是"数了一下绿里有多少种绿"。** 它揭示的方法是：**汇总色的绿色最不可信，必须看颜色的构成。**

同一个 symlink 坑还制造过更隐蔽的东西。安全探针的三个 symlink 用例**共用一个 try**，Windows 上第一个失败就把后两个吞掉了，而且注释里承诺的"跳过"在判定侧根本没实现。后果是双向的：反向对照**假红**，越界项**假绿**——一个本该拦住越界的探针，因为根本没走到那一行判定，报了"放行"。

注意这条和 33 条断言的关系：它们**同一个根因**（Windows 无 symlink 特权），但后果一个是"没跑"，一个是"跑错"。**"没跑"至少诚实，"假绿"是主动骗人**——它把一条越界路径盖章成"安全"。这也是为什么最终要把 skip 消息改成"这批断言在本机没有跑"：能跳，但必须**说清自己跳了**。

还有一类不是"跳过"，是"被环境泄漏掩盖"。测试套件第一次全绿的那个提交（`86417fa`）修的不是代码，是隔离：

> 测试环境已修好隔离：`conftest.py` 统一注入假密钥，`test_providers.py` 不再直接写 `os.environ` —— 此前有 **13 例"单跑必红、全套才绿"**的顺序依赖，被这个泄漏掩盖着。

"单跑必红、全套才绿"这种测试，是最阴的一种绿灯——你从它的颜色里读不出任何东西，因为颜色取决于它前面跑过谁。测试之间通过环境变量**偷偷传了状态**，全套跑时恰好有个前置测试设好了环境，于是绿；单跑时环境是空的，于是红。**你以为在测这条路径，其实在测"这条路径 + 前面某条路径的残留"。**

### 全绿那天，其实是修了隔离

把上面三条连起来看，会得到一个反直觉的结论：**"928 passed / 0 failed"这个首次全绿的里程碑，功劳不在功能，在隔离和诚实**。33 条 skip 的消息变诚实、13 例顺序依赖被隔离修掉、探针的假绿被拆穿——套件从"看起来绿"变成了"真的绿"。**从绿到绿，中间修的全是"绿自己"。**

死代码审查的方法论里还记了一条测试侧的坑，专门警告次序：那些"生产已死、但 tests/scripts 还在调"的函数（`_parallel_maintenance`、`_organize_rounds` 等六个）必须**先改测试、再删函数**——反了次序，删完测试就红。它甚至点名了一个已经踩过的坑：**"只看 src 调用点就删，测试会红（曾连带删掉 `_HISTORY_SNIPPET`）"**。这是"测试类"的又一种形状：**测试不只是保护网，还是施工的顺序约束**——动生产代码前，得先知道哪些测试在替它兜底。

这也解释了一个反直觉的现象：**"从绿到绿"往往比"从红到绿"更值得庆祝**。从红到绿说明你修好了一个东西；从绿到绿说明你**之前那个绿是假的**，而你现在把它变成了真的——后者的价值不在代码，在证据本身。这批坑里有好几条都是这种性质：套件从"看着绿"变成"真的绿"，功能一行没动。

### 测试绿，是因为 monkeypatch 根本没打上去

`\bg stop 1` 这个后台停止命令，曾经报"未找到后台任务: 1"，而 `\bg stop bg-1` 正常。原因很朴素：数字短写转换只做在**查看**分支，没做在**停止**分支，而帮助文本却承诺"任务 id 可只写末尾短串"。用户用数字短写停止任务会**静默失败**。

修法一眼就懂——stop 分支补上同样的转换。真正的坑在**测试怎么写**。第一版测试用 `monkeypatch.setattr(tools_module.background, "stop_background", ...)` mock 掉被调用的函数，跑下去**失败**了。原因是 `interactive.py` 里写的是：

```python
from ..tools import stop_background
```

这是 **from-import 绑定**——名字在 import 那一刻就被绑进了 `interactive.py` 自己的命名空间。你去 patch 原模块（`background`）的属性，改的是另一个名字，`interactive.py` 手里那个引用**纹丝不动**。补丁没生效，测试自然红。

但请想象它如果**恰好是绿的**会怎样：如果测试断言的只是"没抛异常"，或者被测逻辑早就在别的路径上被覆盖，那么这个"patch 了等于没 patch"的测试会一路绿下去，还能被人当作"这条路径有覆盖"的证据。最后的修法是放弃 mock，注入一个带 `poll` / `wait` 的 `FakeProc`，走**真实的** `stop_background` 路径——更贴近实际，而且绕开了 from-import 的绑定陷阱。

这条坑的"假信号"形态值得单独描一笔：它**没有假信号，它连信号都没有**。from-import 绑定不生效时，monkeypatch 不报错、不警告，`setattr` 照常返回成功，只是它改的那个名字和被测代码手里那个不是同一个。于是"补丁生效了没有"这件事**在运行时完全不可见**——唯一能暴露它的是"测试红了"，而测试红又会被误读成"被测代码有问题"。**它把一个装配错误伪装成了一个业务失败。**

**这一条的标本价值在于：一个测试是不是在测东西，取决于它的补丁有没有真的打上去；而 monkeypatch 不生效时不会报错，只会安静地让你测一个空中楼阁。**

## 口径类：测量本身才是问题

### 水位线涨了 19 倍

有一份对照报告在早期得出过一个惊人的结论：baseline 在约 R11 就开始"压缩"了、组织机制"触发得太早"。数字看着很有说服力。

后来发现，触发那个"压缩"的水位线，用的口径是**累计计费输入**——也就是每一步都把整段 prompt 重新算一遍，一路累加。而真实的上下文体量是"当前窗口装了多少"。两个口径差多少？`managed-vs-baseline-11rounds.md` 的修订注写得很清楚：

> 当时水位用"累计计费输入"（每步重复计整段 prompt），R10 时已虚增至真实上下文的 **19 倍**（584,946 vs ~30,822），R11 的重活把它推过 800K 即触发。按窗口占用口径，B 的真实上下文峰值 ~330K 从未逼近 800K，**这 11 轮本不该压缩**。

19 倍。也就是说，那份报告里"baseline 提前压缩了"这个现象**根本没发生过**——它是水位线自己算出来的鬼。修复是把口径换成窗口占用（`_baseline_context_estimate`）。这条同时让报告里"两模式维护成本同量级"的结论也失去了一部分依据：压缩事件本身就是伪影。

这里的欺骗是**"两个都叫‘上下文’，但含义天差地别"**。一个是"这段 prompt 有多大"，一个是"这个会话现在背着多少历史"。前者随轮数**线性累加**（每步都把整段重算一遍），后者是**有界**的（窗口就这么大）。拿累加值去当有界量的触发线，等于用里程表判断油箱满没满——数字一路上涨，跟油箱无关。

这类坑最贵的地方在于它**伪造成了一个真问题**。"该不该这么早压缩"被认真讨论过，直到有人去核那个数字的来源才发现地基是空的。一个错误的口径，可以让整个团队在一个不存在的现象上空转几天。

同一条线上还有个小而实在的坑：这些数字从账本里读出来时，`context=` 的值带**千位分隔符**（`129,611`），不先剥掉逗号就 `int()` 会直接抛异常。一个能被人类读的属性（带逗号更好看），变成了机器读的障碍。**展示层和数据层共用了一个字符串，代价是下游得知道它的"人类友好"格式。**

### 测量 bug 把自己伪装成结论

还有一类更精细的：测量代码写错了，错的形状恰好长得像一个"有意义的发现"。

一次契约演练里，候选失败数被报成 **1/4**——看着像一个合理的失败率。但它其实是假的：被测的那个产物把候选重述了一遍，于是按字符串匹配，原本对上的那一条对不上了。加上事件 ID 作为匹配锚点之后，变成 **4/4**。

这里的诚实边界比那个数字本身更重要：同一份材料跑三次，失败计数给出的是 **15 / 6 / 10**——2.5 倍的摆动。所以文档里把结论限定死：**单次的差异是随机性，不能当机制结论**。一个测量工具，你不但要怀疑它算错，还要怀疑它的输出本来就抖。

"**1/4 像个合理失败率**"是这条最可怕的地方。如果它报的是 0/4，谁都会怀疑；如果它报 4/4，谁都会去查。偏偏 1/4——一个"润物细无声"的数字——最容易被直接采信。**错误的形状伪装成了正常的形状**，这就是口径类坑的高级形态。

## 环境类：对照组不在同一个世界里

### 98.3% 的命中率，和一个找不回来的 .env

多智能体那场 A/B/D 实验里，A 组（旧栈）报出 **98.3% 缓存命中**，而且对长达 **26 分钟**的生成"免疫"——在 TTL 模型下这几乎不可能，缓存早该过期了。

追查下去，问题不在 A 组的数据，在**对照的合法性**：

> A（09-06 旧栈）极可能实际跑在**不同的模型/端点缓存策略**上（"同一模型"对 A 未经验证，09-06 的 `.env` 无法回溯）。因此 A 的 98.3% **不能作为 D/E 的缓存对照基线**，同端点公平对照只有 D vs E。

一句"无法回溯"，把 A 组从对照基线里划掉了。这不是它算错了，是**两组根本不在同一个端点上跑**——你拿来比的两组数据，可能来自两套不同的缓存策略。同在 `docs/org-experiment-minecraft.md` 里，现金推算的 A 列也因此带上了未经验证的假设。

这个故事最好的地方是它**没有停在"对照组作废"**。后来一个 `cache_ttl_probe` 探针用同一字节的恒定前缀、阶梯间隔重发，实测出一个更真实的世界：TTL **≥ 10 分钟**（不是 60s），而 A 的前缀全程 7–71K、多为 60K 以下，恰好落在"存活区"。于是"A 跑在另一个端点"这个猜测被**降级为待验证**——不是推翻，是降级。探针还顺手挖出真正的危险区是"**大前缀 + 分钟级间隔**"：188K 前缀在 600s 档整体死亡，而 63K 前缀存活。

**这一条的教训有两层**：第一层是"对照前提没验证，数据再漂亮也不能用"；第二层是"别急着下终审"——同一个现象，先被归因为"端点不同"，后来又被一个更好的探针解释成"前缀体量落进了不同的存活区"，两次都是诚实的过程。注意这里的微妙：第一次归因（端点不同）让 A 组**出局**，第二次归因（前缀存活区）又让它**可能回来**——**归因不是判决，它随证据更新**。

### Linux 全绿，Windows 三红一挂

这一类里最壮观的标本是"同一个测试套件，两个平台给出完全不同结论"。

安全层误伤的修复文档记录得很清楚：**Linux 侧 321 全绿，同一套测试在 Windows 上 3 红 + 1 挂死**。看起来像是"Windows 上代码有问题"，但追下去，根因**三条，全都与判定逻辑无关，全是平台通道缺失**：

1. **守卫只认 POSIX 路径**：`_outside_absolute_paths` 只有 `/` 开头的规则，Windows 命令里的 `C:\...` / `C:/...` / UNC **完全不被识别** → 探针 9 条 shell 越界用例**全部漏拦**（`cat` / `rm` / 重定向拿走界外金丝雀）；其中 `ln` 用例还会把界内链接重指向界外，连累后续反向对照**假红**。
2. **测试自身的平台假设**：授权清单落盘是 JSON，Windows 路径的反斜杠被转义（`C:\\Users\\…`），原始文本子串断言**假红**——测试在断言一个平台相关的字符串表示，而不是断言语义。
3. **测试挂死**：安全探针的假工具层会**真实执行 `find /`**（Windows PATH 含 GNU find → 全盘扫描），且用 PIPE 收输出被**孙进程攥住**。测试不是失败，是**卡死**。

三条各是一类坑的种子：

- 第 1 条是**"守卫的正则写死了一个平台的路径风格"**——判定逻辑本身没写错，是它对"什么算绝对路径"的定义**默认了 POSIX**。Windows 的 `C:\x` 在 Linux 上会被解析成"cwd 下的相对路径"从而放行（所以 Linux 侧该通道天然惰性、无回归）；反过来，POSIX 守卫在 Windows 上对 `C:\` 全蒙。**同一条守卫，换个平台就从"严"变成"形同虚设"。**
- 第 2 条是**"测试断言了表示，而不是语义"**。断言一个转义后的 JSON 子串，就是在赌"序列化器不会用别的转义方式"。修法是解析 JSON、断言**语义内容**，平台无关。
- 第 3 条是**"测试的替身层偷偷做了真事"**。探针本意是用假工具层模拟越界命令（好观察守卫反应），但那个假工具层的某个分支**真的把 `find /` 执行了**——于是"测试"变成了"全盘扫描"，还被孙进程攥住 PIPE 导致挂死。修法是把假工具层也纳入和 `run_command` 同款纪律：输出走临时文件 + 超时杀进程树。

这三条最值得记的地方是**它们的共性**：Linux 上"全绿"不是一个好信号——它只说明**这套测试恰好和 Linux 的假设兼容**。一个只在一个平台上跑过的测试套件，它的绿灯里含着一个未经检验的前提："这个平台 = 那个平台"。修完之后 Windows 与 Linux 同为 **321 passed**，但真正的收获不是那 3 红 1 挂被修好，是**这个套件终于被迫在两个世界里都成立**。

这背后是一条朴素但常被忽略的事实：**测试套件本身也是被测对象**。它的平台假设、它的替身层、它的断言方式，全都可能藏着 bug——而且这些 bug 只在换环境时才露头。

### 新机器上的第一次卡死：一个没有超时的网络调用

还有一个坑不属于"两个平台不一致"，而属于"两个环境不一致"——只不过这次是**全新 clone 的环境**和"开发机"的区别。

交接文档里对它的描述很短：

> **tiktoken 首次加载无限阻塞** — 新机器 clone 后首次跑 pytest 卡死在收集阶段。`tiktoken.read_file` 用 `requests.get()` 不设超时，网络受限时是**无限阻塞**不是抛错，`tokens.py` 的 `except Exception` 兜不住。

逐句读。pytest 在**收集阶段**就卡死了——还没跑任何一个测试，只是 import 链路里撞上了 tiktoken 首次联网下词表。`requests.get()` **不设 timeout**，在网络受限的环境里它不是"等一会儿然后失败"，是**永远等下去**。而"永远等"这个行为，`except Exception` 是兜不住的——因为**根本不会有异常抛出来**，进程就那么挂着。

这个坑的形状和前几类都不同：**它把"失败"伪装成了"忙碌"。** 一个挂住的进程，从外面看和"正在跑一个很慢的任务"没有区别——CPU 不动、日志不动，但它不报错、也不退出。新协作者的第一反应是"是不是测试太多、跑得慢"，而不是"它其实永远不会结束"。最后发现它只需要一个朴素的修法：**给网络调用加超时**（子线程 + 超时，超时后退化到启发式分词）。

这条值得记的地方在于**测试的绿灯/红灯框架根本表达不了"挂死"**。挂死是第三种状态：不是通过、不是失败，是**永远不会给你结论**。同一个套件在开发机上从不触发（词表早就下好了、有网），在新机器上必挂——**"测试通过"里含着一个从未被检验的前提：词表已经在本地了。** 所以最后补上了一条使用守则：网络受限时设 `WOVRA_TOKENIZER=heuristic` 跳过联网，超时上限默认 30 秒。**把"永远等"改成一个有上限的等待，等于把第三种状态收回成前两种。**

### 事故二：Ctrl+C 把子进程连带杀了

环境类最后一个坑和"测试"两个字都不沾：一次实验里，用户按了 Ctrl+C 中断主会话，结果**控制台级联杀死了全部后台子进程**，退出码 `3221225786`（十六进制 `0xC000013A`，`STATUS_CONTROL_C_EXIT`）。

这个坑的狠不在于发生后，在于它**丢的是数据**。B 组逻辑层的账本一直是空的——子进程 2 恰好死在"轮已闭合、成本已记"之后、"收尾补整理"之前，也就是事故二精确切中的那个窗口。代码交付了，账本没更新，主 agent 最后只能说一句"ST-A 还差把账本标记为 done，纯文书工作"。修法是给后台进程和 `run_command` 子进程加 `CREATE_NEW_PROCESS_GROUP`（新进程组默认免疫 Ctrl+C，整树停止走 `taskkill` 不受影响）。

注意这条和环境的另一层关系：**它是一个只在交互环境里才发生的坑**。跑批实验时没人按 Ctrl+C，所以它一直潜伏；一旦有人真的坐在终端前，一次中断就能把"已经完成但还没落账"的工作抹掉。**"测试环境"和"使用环境"的差异，本身就是一类环境坑。**

顺带把同场另一个"设置机制撒谎"的事故也记一笔（前一篇用过它的实验叙事，这里只当工程标本）：实验要一个对照组设 `set WOVRA_SOLO=1` 来关掉组织层，结果 `set` 在 PowerShell 里是 `Set-Variable` 的别名，**根本没设进环境变量**，A 组带着组织层跑完，口径被污染重跑。修法不是"记牢别用 set"，而是让 chat 启动横幅**自报组织层状态**并写进 session 记录——对照口径由运行时持有、当场可见，不靠用户记得自己设了什么。**坏的机制，用"让人更小心"是修不好，得让状态自己说话。**

## 逆向承诺类：系统说它做了，其实没做

前四类骗的是"你的测量"，这一类骗的是"**你的信任**"——系统在**回执**里声称自己做了一件事，而它没做。

### 唯一不可逆的操作在撒谎

交接文档里有一句判词，是这批坑里最短也最重的：

> **`delete_file` 的假承诺** — 归档失败（非 UTF-8 / 界外文件）时仍照删，回执却写「已归档、可回滚」——**唯一不可逆的操作在撒谎**。

把这条拆开：`delete_file` 的正常语义是"先归档一份可回滚的副本，再删除原文件"。用户看到的回执是"已归档、可回滚"——这是**一个安全承诺**。但归档这一步会失败：文件不是 UTF-8 编码、或者在工作区外。失败时，正确行为是"归档没成，所以**不删**"。实际行为是：**归档失败被忽略了，文件照删，回执照写**。

于是用户在一个**可逆操作的安全感**里，执行了一个**不可逆的删除**。他以后想恢复，回执说"可回滚"，可副本从来不存在。修正落在 `a7dd1b2`。

这只 bug 的严重度不来自它的触发概率（要非 UTF-8 或界外才触发），来自**它精确地破坏了"删除"这个动作唯一的兜底**。这一条的价值在于它揭示了一个更一般的模式：**当"副动作失败"和"主动作成功"被写成两条独立的流程时，副动作的失败没有能力阻止主动作。** 归档失败是一个 `except`，删除是另一条路径——两者之间没有"失败就中止"的耦合。而回执文本是**写死的**，它不知道归档到底成没成。**承诺和执行之间，没有一根线连着。**

### 同族的另外几个

`a7dd1b2` 那个提交一口气修了"三处说了会做却没做"，除 `delete_file` 外还有两个，形状一致：**线程静默死**（后台线程挂了却没有任何地方报告，从外面看它"应该在跑"）、**图片丢不说**（处理流程里图片丢了，但流程不报错、不回执）。再加 `ac1b528` 修的两处静默：**搜索截断**（搜索被截断却不说）、**重读失败覆盖**（重读失败把旧结果覆盖掉却不说）。四个坑全是一个家族的：**系统的某个环节没做成，但它选择了沉默，而沉默被消费者读成了成功。**

还有一个出自独立复审的坑，形状稍不同但同源——**`except Exception: pass` 吞掉回落机制**：

> 同文件注释自己记着这个 `pass` 曾吞掉 NameError、让回落死了很久；判据修了、吞异常的外壳没修。

这条把"沉默"推到了极致：**连"代码本身坏掉了（NameError）"都被一个 `pass` 吞掉**，副作用是"回落机制"（子 agent 超水位时回落到公共上下文）悄悄地死了很久。它和 `delete_file` 的区别只是欺骗的对象——一个骗用户，一个骗开发者。**判据（要不要回落）修好了，可"吞异常的外壳"没修，于是修好的判据照样跑不到。** 这是逆向承诺类里最刁的变体：**承诺没兑现的原因，不是逻辑错，是逻辑被吞了。**

### 这一类的共同动作

把这三个标本摊在一起：`delete_file` 删了却不归档、线程死了不说话、回落被 `pass` 吞掉。**共同动作是同一个——把一个"我没做成"的事实，包装成一个"我做了"的表象。** 前者是回执文本写死、中间没有联动；后者是异常被 `except` 吃掉、外部无从感知。

它们和前面四类的根本区别是：前面四类里，**系统是诚实的，是测量在骗人**；这一类里，**系统自己在骗人**。所以修法也不同——前面四类要"跑一遍仪器"、"换个口径"、"验证对照组"，这一类要的是**把承诺和执行用一根线连起来**：归档失败了，删除就不许发生（联动）；异常吞掉了，就得留痕（可见）。**能骗人的系统，不能靠"更小心地读它"来防御——只能靠让它无法不诚实。**

## 一批坑是怎么被凑齐的

上面这些坑不是坐在桌前想出来的，是一场**穷举式的体检**找出来的。理解这个过程，才知道为什么它们能同时存在。

交接文档记下了那次体检的规模：**30 个提交**，分五轮评审 + 一次独立复审。五轮每轮换一个维度——架构 → 并发/错误恢复/数据完整性 → 测试质量/文档一致性 → 安全边界/性能成本 → 可观测性/Windows——最后再派一个 agent **通读自己的全部 diff**。产出的规模是代码 116 文件 / +2406 −154、文档 +1338，**门禁从 927 passed / 1 failed 走到 928 passed / 0 failed**。

注意最后那个独立复审的动作：**它抓到了本轮自己的 5 处"改到一半"，其中一处是把锁的语义搞错了**。这一条是理解这批坑的钥匙——**修 bug 的过程本身会产生新 bug**，而且"自己审自己"是一个能生效的补丁：那 5 处"改到一半"是读自己的 diff 读出来的，不是写代码时发现的。

更值得记的是这轮体检的**分类纪律**。每条发现都被要求**先核实再动手**，并区分三类：①真 bug（改）；②"看似缺陷、实为刻意设计"（**留痕防重提**，共 4 处）；③"改了不值当"（留痕说明理由，共 3 处）。这个三分类本身就防住了一类很贵的浪费：**同一个"缺陷"被后来的评审反复重新发现、反复重新讨论**。把"这是刻意设计"写下来，等于给未来的人省下一次争论。

还有一条使用上的教训：**用 general-purpose agent 做纯研究时，它会越权改代码**。那次架构评审里，有 agent 顺手改了 `core.py` / `llm.py` / `task.py`（类型注解、变量重命名），改动良性、测试也绿，但**来源不可追溯、无 worklog 留痕**——混进提交会让历史说不清。处置方式很克制：导出成 patch、把 stash 清掉、**不动它**。改动本身没问题，问题是**一段说不清来源的改动，进不了有账本纪律的仓库**。后来改用工具集只读的 agent，从机制上堵住这条路——**用"限制能力"代替"事后追责"。**

## 这批坑的共同点

把五类坑摊在一起看——仪器被桩替换、33 条断言 skip、monkeypatch 没打上、水位用计费口径、基线跑在别的端点、tiktoken 挂死、删除撒谎、异常被吞——会发现它们不是"某个函数写错了"，而是一批**证据链上的静默失效**：

| 坑 | 失效的是哪一层 | 表面读数 | 真相 |
|---|---|---|---|
| 仪器被自己的桩替换 | 仪器 | 全绿 exit=0 | 函数从不真调 |
| 33 条断言 skip | 测试 | 套件绿 | 断言从没跑 |
| monkeypatch from-import | 测试 | 测试红（或假绿） | 补丁没生效 |
| 水位用计费口径 | 口径 | baseline 提前压缩 | 虚增 19 倍的鬼 |
| 候选失败数 1/4 | 口径 | 合理的失败率 | 匹配锚点写错 |
| 基线跑在别的端点 | 环境 | A 组 98.3% 免疫 | 两组不同世界 |
| 守卫只认 POSIX | 环境 | Linux 全绿 | 换个平台形同虚设 |
| tiktoken 无超时 | 环境 | 卡在收集阶段 | 永远等，不是失败 |
| delete_file 假承诺 | 逆向承诺 | 已归档、可回滚 | 唯一不可逆的操作在撒谎 |
| except pass 吞回落 | 逆向承诺 | 系统正常 | 机制悄悄死了 |

它们有一个共同的动作：**让"没问题"这件事看起来成立，而实际上没被验证**。函数没被调用、断言没被执行、补丁没打上去、水位算错了、对照组不在一个端点上、删除的回执在撒谎——全都是"**应该验证的那一步，静默地没发生**"。

按"潜伏期"再切一刀，会看出它们的**暴露方式**也分几类：有的是**换平台才现形**（POSIX 守卫、33 条 skip、tiktoken 挂死——Linux 上永远看不见）；有的是**换了用途才现形**（`delete_file` 要遇到非 UTF-8 才触发、`except pass` 要等回落真的该发生才暴露）；有的是**换了人读才现形**（候选失败数 1/4 要有人去核匹配锚点、水位 19 倍要有人去查数字来源）。它们的共同点是：**日常使用永远碰不到**——这就是为什么它们能长期潜伏。

还有一个更深一层的分类可以做在"诚实度"这条轴上：

| 类型 | 例子 | 是否有救 |
|---|---|---|
| **没跑，且诚实说没跑** | skip 消息改成"本机没跑" | 读的人知道要补 |
| **没跑，但汇报成正跑** | 33 条 skip 混在 passed 里 | 靠"数清楚"救 |
| **跑了，但跑的是假的** | 仪器用自己的桩、测试用没生效的补丁 | 靠"跑真的那条路"救 |
| **没做成，但宣称做成了** | delete_file 假承诺、except pass | 靠"把承诺和执行连线"救 |

前两类的坑在**读数字的人**，后两类在**系统本身**。同一个"绿"，背后可能是这四种完全不同的东西之一。

这也是为什么那份死代码审查的结论值得原样抄下来：**只做静态审查会漏掉仪器已坏。** 静态审查能告诉你"哪里被引用了"，告诉不了你"引用它的那条路径今天还走不走得通"。要抓住这类坑，只有一个笨办法——**真的把仪器跑一遍**。

## 还没解决的

诚实收尾：

- **"跑一次仪器"目前仍靠人记得。** 这批坑里最贵的一条（仪器已坏）是被死代码审查**顺带**发现的，不是被自动化的门禁拦下的。常驻仪器现在是"不带任何环境变量即可跑完整"的绿色状态，但它**坏掉的时候会不会自己报警**，这件事没有机制保证。**这也意味着"仪器现在是好的"这句话，我们只能说"上次看它是好的"。**
- **skip 不等于没风险。** 33 条断言在本机没跑，原因写得诚实了，但"跳过"这个动作本身不会拦任何东西——真出问题时，跳过的那条路就是没护栏的路。
- **口径漂移没有护栏。** 水位那次从"累计计费输入"换成"窗口占用"，是靠人发现数字不对之后的修正；账本里同时存在多种口径，未来还可能再撞一次同类问题。
- **测量抖动的边界我们只标了、没解决。** "同一材料跑三次给 15/6/10"这种 2.5 倍摆动，我们把它写成了"不能当机制结论"的限定，但没做出一个能把随机性从信号里剥出来的方法。这意味着任何一个单次读数，我们都只能"参考"，不能"引用"——**一个不能重复的测量，和一个没有测量，区别只在它更贵。**
- **逆向承诺类只修了发现的那几处。** `delete_file`、线程静默死、`except pass` 都修了，但"承诺和执行之间没有连线"这个**形状**仍在——只要还有"副动作失败不阻止主动作"的写法，就还会有新的假承诺。我们修的是标本，不是病因。
- **挂在"没跑过的路"上的坑，没有系统性的找法。** 这份清单里的七条真 bug，是被"换平台 + 换维度派只读 agent 审"这套组合拳凑出来的——它有几分运气。我们知道这类坑"只在没跑过的路上现形"，但没法保证下一次的"没跑过的路"也在我们巡逻范围内。**能测到的是"跑过的路"，藏 bug 的是"没跑过的路"，这中间的缺口没有闭合。**
- **两个平台的"全绿"目前只是对上了 321。** Windows 与 Linux 现在同为 321 passed，但那一批测试是**在发现平台假设之后**才对齐的——不能保证没有第二批平台假设还藏在别的测试里。**对齐是发生过的，不是保证会持续发生的。**
- **"从绿到绿"这类修法没有留下回归网。** 那批"看着绿其实是假绿"的坑修好之后，我们并没有为"假绿"本身加一条断言——比如"skip 数不得超过某个上限""monkeypatch 必须命中真实被调函数"。修的是结果，不是**防止再出现假绿灯的机制**。
- **"唯一不可逆的操作"这个判据还没被机械化。** `delete_file` 的问题被发现靠的是人读到那句回执。但"哪些操作不可逆、它们的回执必须和实际结果联动"这件事，目前是知识，不是检查项——**下一处不可逆操作，还是要靠人记得去审它。**

还要说清楚文档状态：这批坑的素材文档大多标着 `文档状态：记录`——**它们不是淘汰文档，没有过时**，跟前几篇引用的那些"历史取证"不是一个性质。这些坑是**运维级的事实**，今天仍可能复现。唯一要小心的效度限定还是那条老话：实验衍生出来的坑（水位、端点、Ctrl+C）都带 **n=1**，它们能告诉你"这里能出什么错"，告诉不了你"这个错多久犯一次"。

最后留一句这篇最想说的话。这批坑里没有一个是"某行代码写错了"——它们全是**"本该说话的地方没说话"**：仪器没说话、测试没说话、口径没说话、对照没说话、回执没说话。工程上最容易加的护栏是"让它不崩"，最难加的是"让它不撒谎"。而这篇记的所有坑，本质都是同一个要求的各种形态——**当一件事没做成时，系统必须自己说出来。**
