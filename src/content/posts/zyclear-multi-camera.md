上一篇讲工厂：那张注册表怎么把"创建器 + 枚举器"配成对，怎么让新增品牌只动一处。工厂解决的是**怎么把一台设备造出来**。

这一篇接着往下问一层：**造出来之后，界面上靠什么认出它？** 一条产线上挂着好几台相机，参数面板调的是哪一台？图像窗口显示的是哪一台？这就是门面层 `CameraContext` 的全部职责——它是我整个系列里改动最少、也最容易被低估的一个类，一共两百多行。

先说结论：它只干四件事，序列号翻译、映射表、生命周期托管、会话状态。但这四件里有两件我一开始都做错了，而且错得不响——编译过、测试过、界面跑起来也没崩，是逐文件补注释的时候才翻出来的。后面第六节细讲。

为什么这个类值得单独占一篇？因为**它是"多机"这个需求真正落地的地方**。工厂可以只造一台设备，契约可以只描述一台设备的能力，只有门面必须同时面对 N 台——它得知道每台是谁、每台现在什么状态、用户正在看哪一台。**单机系统里门面可以退化成一个裸指针，多机系统里门面就是整个上层的地基。**

## 一、一条线挂多台相机，界面上怎么区分

先摆现场。

智澈的典型部署是一条产线挂多台相机：一个工位拍正面、一个拍侧面、一个拍细节。列表里要能同时列出它们，用户点哪台，参数面板和图像窗口就切到哪台。

最早的版本我用的是**索引**：枚举回来一个数组，界面上是 `QListWidget`，第 0 项、第 1 项、第 2 项。点第几项，就按下标去数组里拿对象。

问题出在**枚举顺序这件事根本不可控**。

我碰到过三次，每次都是同一个套路：

- 第一次，插上第二台相机再重新枚举，列表顺序变了。用户点"第 1 台"，实际连上的是另一台——因为新设备被枚举器插在了数组中间。
- 第二次，某台相机断线又恢复，SDK 把它挪到了枚举结果的末尾。界面上看着没变，点下去却连错了设备。
- 第三次，同一个物理设备经 USB 和 GigE 两个传输层各被枚举出一次，数组里出现了两条，但它们是同一台。

三次的共同点：**索引描述的是"枚举结果里的第几个"，不是"哪台设备"。** 只要枚举顺序变一下，索引到设备的对应关系就整体错位。而这个对应关系，恰恰是用户脑子里认的那个——他点的是屏幕上那台，不是数组里那个位置。

索引还有一个更隐蔽的坏处：它**没有任何容错**。换成序列号之后，设备换了位置，界面重新绑定还是能找到它；用索引的话，位置一变，之前所有的绑定全部作废。

所以我全部改成了**序列号寻址**。这可能是我在整个门面层里做得最对的一个决定。

## 二、序列号做唯一主键

主键这件事，契约层已经先定死了。看 `ZCCameraMetaInfo.h`：

```cpp
// 相机身份以 Serial 为准；UserDefineID 是用户可改的显示名，不承担主键职责
struct CameraMetaInfo {
    QString Serial {};
    QString UserDefineID {};
    QString VenderName {};
    // 相等性只由 Serial 决定：枚举去重与工厂按序匹配都依赖这一点，
    // 若把 UserDefineID 纳入比较，改名后的相机会被当成新设备重复登记
    bool operator==(const CameraMetaInfo& info) { return Serial == info.Serial; }
};
```

**为什么这么写**：三个字段里只有 `Serial` 不可变。`UserDefineID` 是用户能在界面上改的显示名（"正面工位""侧面工位"），改完之后它就不再指向同一个稳定对象了；`VenderName` 是品牌，多台同品牌相机完全重名。所以 `operator==` 只比序列号——**一旦把可变的显示名拉进相等性判断，用户改个名字，系统就认为这是台新设备，会重复登记**。

序列号为什么比索引和句柄都靠得住？

| 候选主键 | 换枚举顺序 | 断线重连 | 换传输层 | 用户可改 |
|---|---|---|---|---|
| 数组索引 | 错位 | 错位 | 错位 | 否 |
| SDK 句柄 | 不变 | **作废** | 不变 | 否 |
| **序列号** | 不变 | 不变 | 不变 | 否 |

句柄这一行值得单独说。句柄是"这一轮打开的设备"的临时凭证，`release` 之后句柄就没了，重连要重新 `acquire` 拿一个新句柄。拿句柄当主键，等于每次断线重连都要上层重新走一遍绑定——而序列号是**烧在设备里的**，设备还是那台设备，序列号永远不变。

这也是为什么契约层那个 `Serial()` 是个非虚方法（`CameraInterface.h`）——它直接从基类持有的 `m_cameraInfo` 里读，所有厂商实现共用，不需要谁重写。**身份信息是共性，不是厂商差异。**

## 三、门面层的映射表

门面层持有的就是一张"序列号 → 设备对象"的表。看头文件：

```cpp
private:
    // 序列号 → 设备对象，是本层唯一的持有者；无锁，约定只在 GUI 线程访问
    QMap<QString, CameraInterface*> m_serialCamMap;
    QString m_currentSerial;
```

**为什么用 `QMap` 而不是 `std::map`，也不是 `unordered_map`**：

第一，`QString` 做 key 时 `QMap` 少一层转换。`QString` 本身有隐式的字符串比较和哈希，用 `std::map` 要给它写比较器，用 `std::unordered_map` 要给它写哈希器——两个都得多写代码。

第二，`QMap` 是**有序**的（底层是按 key 排序的树），`QHash` 才无序。这一点工厂那边已经吃到过红利：`CameraFactory.cpp` 里注释写着「QMap 按 key 字典序遍历，枚举顺序因此是稳定的、与注册先后无关」。**稳定顺序对一个要反复比对日志、比对界面的项目太重要了**——同样的输入，枚举出来的顺序永远一样，出了问题我不用怀疑"是不是顺序又变了"。

第三，**这张表根本没有查询性能焦虑**。一台机器典型不超过四台相机，`QMap` 那次 O(log n) 查找的常数，跟一次 SDK 调用比是零头。**我选它是因为它顺手、有序、少写代码，不是因为它快。**

没用 `unordered_map` 还有一个理由：多出来的哈希开销在这里换不到任何东西——四台设备的表，哈希和红黑树没区别，但哈希带来了顺序不稳定，反而多一个要解释的现象。

表还有个前提写在注释里：**无锁，约定只在 GUI 线程访问**。门面不自己加锁，因为它被约定为只在 GUI 线程被调用；真正的并发在更下面——取帧回调线程只碰 `CameraImageQueue`，不碰这张表。**把锁的边界定在"谁碰什么"上，比无脑给每个容器加锁更清楚。**

这里还有一层设计取舍值得说明：表里的 value 是**裸指针**，不是 `QSharedPointer` 也不是智能指针。我考虑过用 `QSharedPointer<CameraInterface>`，被自己否掉了——因为如果用智能指针，门面就不再是"唯一的持有者"了，任何一处拿走了 `QSharedPointer` 的副本，就多了一个共同所有者，对象的销毁时机变得不可预测。而门面的整个设计前提是：**只有它持有这些对象、只有它决定什么时候销毁。** 用裸指针是把这个前提写进类型里，比写进注释里更硬。

代价是门面必须自己记得 `delete`——这正是第六节缺陷二栽的地方。**智能指针能帮我避免的错，我选择了用约定承担。** 这笔账划不划算，下面讲完那个泄漏缺陷你自己判断。

## 四、生命周期托管：谁 new、谁 delete

这里有一个所有权的转移，是门面层第二个容易做错的地方。

先看工厂那边怎么说的。`CameraFactory.h` 第 33 行：

```cpp
// 未注册品牌回 nullptr 而非抛异常，调用方必须判空；返回实例所有权归调用方，由它 delete。
CameraInterface* createCamera(const CameraMetaInfo& info);
```

注释写得很清楚：**工厂创建的实例，所有权归调用方**。工厂只负责 `new`，不负责 `delete`——因为它不知道这个对象要用多久，删早了就是悬垂指针。

那"调用方"是谁？是门面。门面在枚举时把对象收进表里：

```cpp
CameraInterface* camera = CameraFactory::instance()->createCamera(info);
if (camera) {
    m_serialCamMap[info.Serial] = camera;   // 对象所有权自此移交门面
    qDebug() << "创建相机成功:" << info.VenderName << info.Serial;
} else {
    qWarning() << "创建相机失败，不支持的厂商:" << info.VenderName;
}
```

**为什么这么写**：这一行 `m_serialCamMap[info.Serial] = camera` 就是所有权转移的那一刻。注释专门写了「对象所有权自此移交门面」，因为**这个转移在代码里是隐式的**——没有 `unique_ptr`、没有 `std::move`、没有任何 C++ 层面能拦住你的机制，只有一行普通的赋值。所有权从工厂手里"流"到了门面手里，靠的是约定，不是类型系统。

所以门面必须对自己收下的每个对象负责到底。析构时要还清：

```cpp
// 顺序不能反：设备已关再停采会报错
iter.value()->stopGrabbing();
iter.value()->disconnect();
// release 回收厂商 SDK 里的设备句柄，缺这一步句柄会一直留在系统里；
// 对象所有权在建表时就已移交门面，这里一并销毁，否则每建一台泄漏一个
iter.value()->release();
delete iter.value();
```

**为什么这么写**：这里有三层回收，顺序是硬约束。停采要在断连**之前**（设备已经关了再去停采会报错）；断连之后才能 `release` 销毁句柄（契约的两段式生命周期：`disconnect` 关设备、`release` 销毁句柄）；最后 `delete` 对象本身。**三层分别管的是"采集在不在跑""设备连不连""句柄还在不在"和"这块内存还在不在"，漏任何一层都是一个独立类型的泄漏。**

最后那句 `delete` 尤其容易被忘——因为它对应的是工厂注释里那句所有权承诺的**兑现**。工厂说"归调用方 delete"，门面就是那个调用方。第六节会讲，我第一版恰恰漏了这一步。

## 五、交互层全程只凭序列号说话

门面之上，参数面板和图像面板从来不说"第几台"，只说序列号。而且它们不自己记序列号——问门面要当前选中的那个：

```cpp
// ParamWidget.cpp —— 下发参数
QString serial = CameraContext::Instance()->currentSerial();
CHECK_RETURN(CameraContext::Instance()->writeParam(serial, curCameraParam));
```

```cpp
// ViewWidget.cpp —— 开始采集
QString serial = CameraContext::Instance()->currentSerial();
CHECK_RETURN(CameraContext::Instance()->startGrabbing(serial));
// serial 必须在 start() 之前落定：run() 一进线程就拿它去取帧，
m_pImageProcess->setSerial(serial);
```

**为什么这么写**：注意这两段里**一个厂商名都没有**，`serial` 就是一个不透明的字符串，面板不知道它底下是海康还是虚拟相机，也不需要知道。这正是第一篇那条 grep 约束落地的样子——交互层只凭序列号寻址，序列号是谁给的不重要，重要的是它足够稳定、足够唯一。

"当前选中哪台"这个状态也收归门面持有，就是那个 `m_currentSerial`。用户点列表切换相机时调 `setCurrentSerial`：

```cpp
// 只记录，不校验 serial 是否已注册，也不切换任何相机状态
uint32_t CameraContext::setCurrentSerial(const QString& serial)
{
    m_currentSerial = serial;
    return ZYCLEAR_OK;
}
```

**为什么这么写**：这个方法故意"什么都不做"，只记一个名字。它不连接、不校验、不通知——因为"选中"是个纯粹的 UI 概念，跟设备状态无关。用户可以在没连接的设备上点来点去，面板拉不到参数会报错，但门面不该替他做任何事。**门面里凡是掺进 UI 语义的逻辑，最后都会变成两边都不好改的耦合。** 这就是第二篇那条"面板之间走总线、不走直接引用"的延续——状态放门面，事件走总线，两边都不直接喊对方。

"不校验 serial 是否已注册"这一条单独说：它意味着 `setCurrentSerial` 可以在任何时刻接受任何字符串，包括一个已经被拆除的设备序列号。这不是疏忽，是有意的。因为**切换选中和切换设备连接是两条独立的时间线**——用户可以先把选中切到一台还没连接的设备上，然后再点连接。如果 `setCurrentSerial` 里加了"必须已注册"的校验，这条正常操作路径就会被卡死。**校验放在真正需要设备的地方（那些按序列号查表的接口），而不是放在记录状态的方法里。**

这种"用户点着 A 连上 B"之外的错误，还有一种更隐蔽：用户点了 A，参数面板刷新到一半，用户又点了 B。如果面板是异步去拉的，回来的参数可能属于 A 却显示在 B 的标题下。现在我靠的是所有按序列号寻址的接口在进入时先查表——**序列号本身就是那把锁**，A 的参数请求带着 A 的序列号，永远不会被当成 B 的。**这也是"全程只凭序列号说话"的另一个红利：它天然防串台。**

## 六、两个真实缺陷

这一节是这篇最想讲的。两个缺陷都记在 CHANGELOG 的"未发布 → 修复"里，都出在 `CameraContext.cpp`。它们的共同特征是：**编译器不报、测试不挂、界面照跑。** 是逐文件补注释、一行一行读"这段到底在干嘛"时翻出来的。

### 1. 缺陷一：丢弃返回值，检查了上一次的调用

`startGrabbing` 修复前的写法（我从 `git show 36ec32a` 拿到的）：

```cpp
auto ret = camera->creatStream();
if (ret != ZYCLEAR_OK)
    return ret;

camera->startGrabbing();          // ← 返回值没接收
if (ret != ZYCLEAR_OK)            // ← ret 还是 creatStream 的结果
    return ret;
```

**错在哪**：`camera->startGrabbing()` 的返回值被丢掉了，但紧随其后的 `if` 检的还是 `ret`——而 `ret` 里装的是上一步 `creatStream()` 的结果。也就是说，**`startGrabbing` 成功了还是失败了，这个判断根本看不见**。

症状很具体：假设 `creatStream()` 成功（`ret == 0`）、`startGrabbing()` 失败（返回非 0）。代码走到 `if (ret != ZYCLEAR_OK)`，`ret` 是 0，条件不成立，函数返回 `ZYCLEAR_OK`——**启动采集失败，被当成成功上报了**。用户看到界面提示"采集已启动"，画面却是黑的。

`stopGrabbing` 里是同一个错，同一条路径：

```cpp
auto ret = camera->stopGrabbing();
if (ret != ZYCLEAR_OK)
    return ret;

camera->destroyStream();          // ← 又是没接收
if (ret != ZYCLEAR_OK)            // ← 又是上一次的 ret
    return ret;
```

修法就是一行：把 `camera->startGrabbing();` 改成 `ret = camera->startGrabbing();`，`destroyStream` 同理。改完 `ret` 才真的装着当前这一步的结果。

**为什么这么难发现**：因为这四行代码**长得就像对的**。`auto ret = ...` 然后 `if (ret != ...)` 返回，是项目里用了几十遍的模式，眼睛扫过去会直接把它读成"检查了这次调用的结果"。只有当你逐字追问"这个 `ret` 到底是谁赋的值"，才发现中间有一次调用没有赋值给任何东西。

对比一下修完之后的正确版本，就知道差别有多小——就多了 `ret =` 那三个字符：

```cpp
ret = camera->startGrabbing();
if (ret != ZYCLEAR_OK)
    return ret;
```

### 2. 缺陷二：析构和重枚举都漏了回收

修复前，析构函数只有两步：

```cpp
for (iter = m_serialCamMap.begin(); iter != m_serialCamMap.end(); ++iter) {
    iter.value()->stopGrabbing();
    iter.value()->disconnect();
}
m_serialCamMap.clear();
```

**错在哪**：只停采、只断连，**没有 `release()` 回收厂商 SDK 的设备句柄，也没有 `delete` 销毁相机对象**。

后果是**双重泄漏**，而且是每一轮泄漏一份：

- **句柄泄漏**：`release()` 是对应 `acquire()` 的回收动作。`acquire` 在建句柄时，SDK 内部会在系统里登记一份设备资源；不 `release`，这份资源一直挂着。程序里反复枚举几次，系统里的句柄数就稳步往上走。
- **对象泄漏**：`delete` 那段缺失意味着工厂那句「所有权归调用方，由它 delete」的承诺**从来没兑现过**。每建一台相机，`HikCamera` 或 `VirtualCamera` 对象就留在堆上没人管。

同样的问题在 `EnumerationCamera` 里一模一样地出现了一遍——它开头的清理循环也只做了停采断连：

```cpp
for (iter = m_serialCamMap.begin(); iter != m_serialCamMap.end(); ++iter) {
    iter.value()->stopGrabbing();
    iter.value()->disconnect();
    // 重枚举会丢弃全部旧对象，句柄与对象都得回收，否则每枚举一次泄漏一轮
    iter.value()->release();
    delete iter.value();
}
```

**为什么这个更阴险**：析构函数只在程序退出时跑一次，泄漏一次还看得出来是"退出慢了"。**`EnumerationCamera` 是用户点一次"刷新设备"就跑一次的函数**——每刷新一次，整张表里的设备全部泄漏一轮。一个现场工程师调试时来回刷新十来次，就泄漏十来份句柄和对象。这不是"退出时的一点残留"，是**用户行为可放大的泄漏**。

修法同样是补两行：`release()` 加 `delete`。析构和重枚举两处都要补，缺一不可。

**这两个缺陷为什么能活这么久**：因为它们都**不改变任何成功路径的表现**。启动采集成功时，缺陷一走的是同样的返回值；程序正常退出时，缺陷二泄漏的那点资源操作系统会回收。它们只在**失败路径**和**长时间运行**里露头，而这两种情况在我的开发环境里几乎碰不到——**我天天跑的是短会话、成功路径**。这也解释了为什么它们是补注释时被读出来的，而不是被测试或崩溃逮住的。

## 七、`CAMERA_NOT_CONNECTED` 的语义复用

第二个缺陷讲完，第三个"轻一点的坑"也得说——第二篇从契约视角讲过它，这里从门面视角再讲一遍，因为借用这个码的正是门面。

看 `loadConfig`：

```cpp
// 采集进行中禁止读配置文件；这里用 CAMERA_NOT_CONNECTED 表示"正在采集"，
// 与字面语义不符，调用方别按"未连接"去理解
if (camera->isConnect() == false || camera->isGrabbing() == true)
    return CAMERA_NOT_CONNECTED;
```

**为什么这么写、为什么是错的**：这个 `if` 有两个条件，对应两种完全不同的情况——"相机没连"和"相机正在采"。前者符合 `CAMERA_NOT_CONNECTED`（0x000A）的字面意思，后者**完全相反**：相机连着、还在出图，却返回一个"未连接"的码。`saveConfig` 里是一模一样的写法。

代价在第二篇详细说过：提示文案错位（弹"请检查连接"，可相机明明连得好好的）、日志排查被误导（看到一串 `CAMERA_NOT_CONNECTED`，去查连接状态，查半天发现连接没问题）。这里补一个门面视角的代价：**门面是所有错误码的出口**，实现层返回什么、门面加什么，上层都从这一个口子收。门面一旦在这里借用了语义，就相当于**在唯一的出口处伪造了事实**——上层基于这个口子做的任何统计、任何自动重试策略，都会踩空。

正确做法第二篇说得够清楚了，这里不重复：**当初就该多加一个 `DEVICE_BUSY`**。我现在没改，不是判断变了，是错误码表被下游依赖之后改动面太大——`CameraError.h` 里的 `CAMERA_NOT_CONNECTED` 已经带上了"门面在'正在采集故拒绝操作'时也复用它，别只按字面理解"的注释，注释就是我的止损。

## 我踩过的坑

**坑一：用索引做设备主键。** 见第一节。枚举顺序一变，索引和设备就错位，用户点着 A 连上 B。我为此反复解释过三次"列表顺序又变了"，才痛下决心全换序列号。教训是：**主键必须选那个"不随界面和枚举变化的字段"**，索引描述的是位置，不是身份。

**坑二：`auto ret` 后面跟了一次没接返回值的调用。** 见第六节缺陷一。`creatStream` 的结果被判了两次，`startGrabbing` 的结果一次都没判。**这种错编译器完全帮不了你**——`camera->startGrabbing();` 作为一个合法的表达式语句，值被丢弃是标准允许的。现在我的习惯是：一个函数里出现多次 `ret`，每次赋值前先问"这个 `ret` 是给谁看的"。

**坑三：认为"工厂 new 了、门面该管"，结果谁都没管。** 见第六节缺陷二。注释里明明写着"所有权归调用方 delete"，我写门面的时候脑子里想的是"反正程序退出会回收"，于是一个 `delete` 都没写。**注释承诺和代码兑现之间是没有编译器检查的**，这句承诺只有在我真去读注释、真去追所有权时才浮现。

**坑四：`setCurrentSerial` 一开始想顺手把连接也做了。** 最早我写的是"设置当前相机时，如果它没连接就自动连上"。后来发现这条逻辑根本不属于门面——它把 UI 的"选中"语义和设备的"连接"语义绑在了一起。用户只是点亮一下列表想看参数，凭什么触发一次硬件连接？删掉之后方法干净成一行赋值。**门面里每一条"顺手多做一点"，最后都变成两层耦合。**

**坑五：`m_currentSerial` 没跟着枚举结果清理。** 有一版我忘了在 `EnumerationCamera` 开头清掉 `m_currentSerial`——重枚举之后设备对象全换了，但"当前选中"还指着上一批里的序列号。后来确认现在这版是在 `EnumerationCamera` 里重建整张表、但 `m_currentSerial` 仍会指向可能已不存在的序列号（`setCurrentSerial` 不校验）。**"表重建了、选中没重建"是个典型的会话状态不一致**，好在所有按序列号寻址的接口都会先查表、查不到返 `NOCAMERA_ERROR`，不会野指针——但用户会看到"当前设备"是个幽灵。这提醒我：**门面持有的任何一份状态，都要跟设备的增删保持同步。**

**坑六：单例的首次调用没加锁。** `Instance()` 是懒汉单例，注释里写着「若日后多线程抢首次调用，这里会造出两个实例并泄漏其一」。现在靠约定"首次 `Instance()` 发生在 GUI 线程、任何工作线程启动之前"活着。**这不是没问题的写法，是当前没出问题的写法**——一旦将来有人在工作线程里第一次调 `Instance()`，就会静默造出两个门面。这条我留着注释，因为它是个**已知的、靠调度顺序兜着的风险**，不是已经解决的问题。

**坑七：把"门面能编译"当成了"门面没问题"。** 这是最值一条元教训。门面是整个项目里最干净的一层——没有厂商 SDK 依赖，能在一个没装海康 SDK 的机器上编译、能脱离硬件跑单测、CI 里天天绿着。我一度因此觉得它最可靠。

结果两个缺陷全在它身上。原因是：**可测试性和正确性是两回事。** 门面的成功路径极易测试（虚拟相机一挂就能跑通），失败路径和长期资源行为却几乎测不到——而两个缺陷恰恰都藏在失败路径和长期运行里。**一层代码"能独立编译、能跑测试"，只说明它的依赖干净，不说明它的逻辑对。** 我后来给门面补的单测里专门加了失败注入，就是为了让这两条路径有覆盖，而不是靠"我看过这行代码"。

## 八、这一层门面之后

门面到这里就讲完了：一张"序列号 → 设备对象"的 `QMap`、一次隐式的所有权转移、一套按序列号寻址的转发接口，外加两个不响的缺陷。

回头看，门面层的价值其实就一句话：**它是整个系统里唯一知道"有哪些设备对象、它们现在是什么状态、用户正在看哪一台"的地方。** 工厂负责造，契约负责定义能力，门面负责持有和调度——三层的边界清清楚楚，谁都不越界。

下一篇讲**参数模型**。门面把 `readParam` / `writeParam` 转发下去了，可参数本身是个比设备更麻烦的问题：海康的曝光是带上下限的 `float`，巴斯勒的增益是带步长的 `int`，某家的触发是枚举、另一家是字符串。我会讲 `CameraParam` 这个外观类怎么把六种类型压成一套、GenICam 的访问权限怎么自动推成界面的三态、以及那个"新增型号只改 JSON、不编译不发版"的链路到底怎么搭起来的。

序列号把设备认出来了，接下来该认出设备身上的每一个参数——**寻址解决"是哪台"，参数解决"这台能调什么"。**
