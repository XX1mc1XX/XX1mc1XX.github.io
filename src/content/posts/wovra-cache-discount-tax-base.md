上一篇讲执行期零截断，落在一句话上：模型该看到的东西，执行期一个字都不省。

但「不省」听起来是要花钱的。我们凭什么觉得这条纪律划算？靠一个很朴素的观察：**Agent 的账单不是按「说了多少话」算的，是按「每一步重新发出去多少材料」算的。** 而这两者之间，隔着一个大多数人做优化时会先盯上的东西——缓存命中率。

这一篇是 Wovra 系列里数据最硬的一篇，因为它讲的是成本模型本身。先把结论摆出来，再用实测数据把它拆开：

> **每一步的等效成本 ≈ 新增 token + 基座 / 折扣率。**
> **命中率决定折扣，基座决定税基。**

这句话在文档里出现过两次，一次在核心修正节，一次在封版总结里。它听起来像正确的废话，直到你看到两组同向相反的数字。

## 两个必须一起读的数字

![命中率是折扣，基座是税基](/images/wovra/折扣与税基.svg)
单看命中率，会得出一个错误但很顺手的结论：命中率越高越省。Wovra 的实测把这个结论打穿了。

| 场次 | prompt | 命中率 | 当轮等效 |
|---|---:|---:|---:|
| R13（baseline，小基座） | 592,560 | 99.3% | **~5K** |
| R15（同一体系，大基座） | 31 步 / 上下文 66K | 96.4% | **~118K** |

两个数字都来自受控实验，同一批账本。**R13 是 99.3% 命中，当轮等效只有 5K——几乎等于免费。R15 的命中率只低了 2.9 个百分点，当轮等效却是 118K——贵了二十多倍。**

差别不在折扣，在税基。

R13 是全量回放的纯追加结构。它的上下文布局几乎不变，服务端从第 0 字节开始比对，一路命中到最后——命中率自然漂亮。而且因为它每轮只追加、不重写，基座虽然名义上很大，但**真正按原价计费的只有新增那一点点**，其余全吃折扣。这就是高命中率的威力，也是「折扣」这个词的实物。

R15 是另一种形态：31 步，上下文 66K。注意 66K 本身不算大——问题在「31 步 × 66K」这个乘积。每一步都要把 66K 的材料重新发一遍，折扣再怎么打，**税基是那 66K，而不是剩下的 3.6%**。96% 的折扣救不了一个臃肿的税基。

所以我们后来把优化对象整体换了。以前盯的是「怎么把命中率从 95% 提到 98%」，现在盯的是「基座能不能从 66K 压到 10K」——**前者是省折扣的钱，后者是省乘积里那个乘数。** Agent 循环步数越多，乘数效应越放大：一个 30 步的任务里，基座每多 1K，就是多 30K 的名义负载摆在折扣的税基里。

## 为什么「一步一次全量」会滚成天文数字

要把「基座是乘数」讲实，得先承认一件事：**Agent 每走一步，都要把当前的全部材料重新发一遍。**

模型没有记忆。它每一轮回答，都是「带着全部档案重新看一遍」。所以一轮的总输入大致是：

> 一轮的总输入 ≈ 步数 × 基座

这不是比喻。文档里有个直接的例子：基座 770K 走 17 步，就是

```
770,000 × 17 = 13,090,000   ≈ 1316 万 token
```

而基座 50K 走同样的 17 步：

```
50,000 × 17 = 850,000       ≈ 92 万 token
```

同一个任务、同样的 17 步、同样的活，输入量差 14 倍。多的那 13 倍不是「干了更多的活」，是**每一步都在为重读一份更厚的档案付费**。

第 69 轮的真实账单把这件事摊开了。同一会话、同一任务，两种策略：

| 第 69 轮（17 步） | baseline | Wovra |
|---|---:|---:|
| 每步发送 | 770–778K | 50–58K |
| 本轮原始输入 | 13,161K | 918K |
| 缓存折算后 | ≈ 446K | ≈ 38K |
| 基座构成 | 全部历史原文 | 历史浓缩视图 + 近 3 轮原文 + 状态表 |

这里最值得看的是最后两行。baseline 的原始输入是 1316 万 token，缓存折算后掉到 446K；Wovra 的原始输入是 918K，缓存折算后掉到 38K。**两边都吃到了深度折扣，但折算后的绝对值差了 11.7 倍。** 折扣是按比例打的，比例救不了绝对值——446K 打四折还是得按 446K 那档的体量计费，38K 打同样的折只会更小。

这就是「税基」具体的样子：它不是命中率的分母，它是乘法的另一头。

## 折扣光谱：同一套架构，从 0.95× 到 1.58×

讲到这里有个不能不补的坑。上面那些账，我们最初是按 DeepSeek 的 1/30 折扣算的，算出来是「含整理成本后打平（1.00×）」。后来意识到一件事：**折扣深度不是 Wovra 的参数，是服务商的参数，而且横跨整个行业。**

把两组实验的命中/未命中数据固定下来，只让折扣率当自变量，B/A 的等效成本比值是这样一条曲线：

| 缓存折扣（行业档位） | A 等效 | B 等效 | B/A | 含整理开销 B/A |
|---|---:|---:|---:|---:|
| 1/40（Claude Fable / Mythos） | 362,257 | 437,721 | 1.21× | **0.95×** |
| 1/30（DeepSeek 空闲时段） | 377,668 | 475,686 | 1.26× | 1.00× |
| 1/15（DeepSeek 高峰时段） | 439,313 | 627,545 | 1.43× | 1.17× |
| 1/10（OpenAI / Claude / Gemini / Kimi K3） | 500,957 | 779,405 | 1.56× | 1.30× |
| 1/5（GLM-5.3-Flash / Kimi K2.6） | 685,892 | 1,234,982 | **1.80×** | **1.58×** |

光谱两端差了 8 倍。同一套 managed 架构，在 1/5 的浅折扣下把 baseline 甩开 1.58×，在 1/40 的深折扣下含整理开销是 0.95×——**略亏 5%。**

第一行是全文最刺眼的一格。在折扣最深的那一档，我们这套管理的全部价值被折扣补贴掉了，整理开销变成净支出。这不是「我们的机制不够好」，这是**结构性事实**：折扣越深，服务商替你承担了越多「重新发一遍」的成本，而你为了降低基座而做的整理，本身要花模型调用——这笔调用在深折扣下不划算。

反过来说，这也是 Wovra 存在的价格学依据：**折扣越浅，管理越值钱。** 行业主流是 1/10，恰恰落在 managed 有明显净收益的一侧。但如果哪天所有服务商都卷到 1/40，这套架构的账要重算——我们把这个风险写在表格里，而不是藏起来。

## 盈亏平衡点在哪

光谱表能读出两条线，都写进了文档。

**第一条是经济账的平衡点，在折扣 ~1/25 附近。** 比这更深的折扣（DeepSeek 空闲、Claude 新系），整理结构化视图是净支出；比这更浅（行业主流 1/10），是净收益。1/25 这个数不是一个精确的临界值，是一个方向性的坐标——它告诉我们这套账对折扣深度有多敏感。

**第二条是方法论上的，更值得说。** 初稿用了 DeepSeek 的 1/30，算出的结论是「打平」。换成行业主流的 1/10，managed 的等效成本优势是 1.56×（含整理 1.30×）——**不是打平，是明显领先。**

同一个机制、同一批数据，只因为假设的折扣深度不同，结论从「打平」翻成「领先 1.3 倍」。所以文档里立了一条纪律：

> **任何「打平 / 领先」结论都必须标注折扣深度。**

这条纪律比任何一个具体数字都重要。成本模型的结论永远是条件结论，漏掉条件就是误导。

还有一条命中率的地板：managed 的结论要求命中率 ≥ ~89%。低于这个线，或者**重组摩擦比模型估计放大 3.4 倍**，收支才会翻盘。这两个数是保守边界，不是精确阈值——它们的存在是为了说明「这套账在什么条件下会不成立」。

## 现金成本：两种价位下的 29 轮回放

等效 token 是模型口径。真金白银的账，用 29 轮真实生产数据、同一账本按两套价目表结算：

| | DeepSeek 空闲 | GLM 半价 |
|---|---:|---:|
| baseline 全量回放 | 18.92 元 | 32.35 元 |
| managed 现行 | 12.76 元 | 12.21 元 |
| managed V3 水位 | 12.63 元 | 12.17 元 |
| managed V3 狠压（索引压到原文 2%） | 12.31 元 | 11.45 元 |

**两种价位下 managed 都赢：GLM 2.65–2.83×，DeepSeek 空闲 1.48–1.54×。**

这张表和上面的光谱表不矛盾，它们是同一公式在不同税基下的解。光谱表用的是受控实验——轻中度负载，基座本来就小，所以深折扣下整理显得贵。这张现金表用的是 29 轮真实生产——负载更重、基座税更大，所以「深折扣里整理是净支出」这条只在轻负载下成立。

魔鬼藏在命中率里：修正后的 managed 命中率是 93.6–94.0%，baseline 实测 98.7%——**managed 主动放弃了 4.7 个百分点的命中率，换来 3 倍的基座缩小。** 在重负载下，这笔交换是净赚的。这也是全文那句「命中率是折扣」的最直接证据：我们明明是「主动降低命中率」的一方，却赢了成本。

**负载越重、基座税越大，管理越值钱。**

## 第四项成本：缓存写入溢价

到上面为止，成本模型是两个词：命中价 + 原价。Claude 的定价暴露了第三个词，而且它专门惩罚 Wovra 这类机制。

Claude Fable 5.1 的完整结构：

| 项 | 价格 | 相对基础输入 |
|---|---:|---:|
| 基础输入 | $10 | 1× |
| 缓存命中 | $0.25 | 1/40 |
| 5 分钟缓存写入 | $12.50 | 1.25× |
| 1 小时缓存写入 | $20 | 2× |
| 输出 | $50 | 5× |

于是每次请求的成本升级成三项：

```
每次请求 = 未变化前缀 × 命中价
         + 变化的前缀段 × 写入溢价
         + 新增 token   × 原价
```

第三项「写入溢价」是新的。它意味着：**managed 每轮重写的装配尾部，不只是「缓存失效」，在 Claude 定价下还要按 1.25× 重新写入。** 我们损失的从来不只是一次命中，还要为「改写」额外付钱。这给「追加稳定尾部」这个方向补了一条独立的经济学依据——不是因为优雅，是因为改写这件事本身有价。

第二个推论更有意思：**1 小时缓存写入是「隔夜冷启动」的解药。** 一个长时运行的会话，付 2× 的写入费把前缀缓存延长到 1 小时，中断数小时后的第一轮仍能命中，避免整个基座按原价重新付费。代价换的是「冷启动不从头计费」——这是可以直接被产品层利用的定价选项。

## 基座的第二张脸：延迟乘数

上面讲的都是成本。基座还有一张面孔，在成本表里完全看不见。

文档里有一个真实体感锚点：

> 上下文 ~80 万 tok 时，首 token 延迟近 1 分钟；压缩到 1.8 万后仅 ~3 秒。

**这是 ~20×。** 但必须说清楚：这个 20× 是关于**基座体量压缩**的，不是关于缓存命中的。我们**没有**做过「同基座下命中 vs 未命中对 TTFT 影响」的实验，这一篇也不会假装有。

机制是清楚的：`prefill 时间 ≈ 未命中 token ÷ 吞吐`。缓存折扣保护的是**成本**，不保护**时间**。TTL 过期、服务重启、空闲时段切换之后，第一轮要按全量基座重算 prefill——不管你的命中率历史多漂亮。这跟上面 Claude 1 小时写入的「隔夜冷启动解药」是同一类问题：冷启动经济学。

所以基座是双重的：**每步计费的成本乘数 + 每步等待的延迟乘数。** Agent 循环步数越多，后者越致命——一个 30 步的任务，每一步都多等一点，累积起来是分钟级的体感差距。managed 的低基座于是同时是延迟保险：稳态 ~50K，即使冷启动也只有秒级。

这也是为什么我们在系列里把「时间」和「成本」并列为后续机制的优化目标——它们共用同一个决策变量：基座压多低、何时破坏缓存。

## 必须一起读的诚实限定

写到这里，如果不加下面这几段，上面每一个数字都会被误读。我们把它们按重要性列出来，一条都不省。

**一、这是观察性对照，不是 A/B 测试。** 两组对话的内容不完全相同，结论的强度来自「同类负载段的方向一致性」，而不是逐轮数值相等。文档里写得很直：`这是观察性对照，不是同输入的 A/B 测试……n=1`。另外受控实验本身也是 `n=1、无重复`，数字留待受控重复实验校准。

**二、V1–V3 已经淘汰。** 上面所有数字都来自已被 V4 取代的机制。它们作为历史证据保留，但它们描述的不是 Wovra 当前跑的东西。读者必须知道这一点——把淘汰版的数据当成现状引用，是我们最不想看到的误读。

**三、99.3% 和 89.8% 来自两个不同会话、两代机制，不是同条件的一对。** 它们各自成立，但不能拼成一个「同一条件下命中率从 89.8% 涨到 99.3%」的故事。

**四、`h ≈ 0.02` 和 1/40–1/5 的档位是用户口径和定价假设，不是线上测量。** 这条最有意思，单独展开在下一节。

**五、折扣深度是假设，还要叠一层 n=1 的不确定性。** 光谱表里每一格都同时受这两件事影响，所以它是一张「方向图」，不是一张「精度表」。

## 一个 API 拒绝确认的常数

这一节的标题听起来像开玩笑，但它是真的。

我们整个成本模型建立在一个常数上：缓存折扣率。这个数直接决定「managed 是领先 1.56× 还是略亏 5%」。而当我们想从 API 侧核实它的时候——

- `/models`：403
- `/user/balance`：403
- `/usage`：403
- `cache_write_tokens`：实测 `null`

**你想据以建模的那个折扣，API 拒绝确认。** 我们最终的 `h` 只能按用户口径取 0.02，档位按各家定价表手工维护。这不是一个技术难题，是一个信息可得性问题——而它恰好落在整个模型最敏感的那个参数上。

还有一条更硬的实测：**线上会出现「无原因的全量未命中」。** 同一场会话里，一次 working 调用 `cached=0`（prompt 81,712 全 miss），而它前后 6–9 秒的调用都正常命中，中间没有任何代码或轮次变化，紧接着下一次调用又命中了。上游节点或路由切换导致该前缀无缓存——这不在我们任何机制的控制范围内。

把那一场 183,332 tok 的「浪费」拆开看，会得到一张很说明问题的账：

| 来源 | 体量 | 性质 |
|---|---:|---|
| 用户改系统提示词 | 96,300 | 前缀首部变了，整段失效，合理 |
| 无原因的网关全量未命中 | 80,932 | 不可控、不可预测 |
| 合法的换档断点 | 6,100 | 机制主动所为，代价已知 |

三条里两条不在机制手里。这就是为什么我们最后把「命中率不能当验收指标」写进了封版清单——它太容易被上游噪声污染，用来看方向可以，用来考核会把团队的努力导向错误的地方。

## 换取低税基的实价

上面那张拆分表里最后一行值得单独讲，因为它是 Wovra 唯一「主动制造」的缓存破坏。

「命中 = 从第 0 token 对齐的连续公共前缀。」这是物理约束，不是设计选择。第一次分叉在哪，命中就到哪。所以我们每次整理、每次降档，本质都是**主动选一个位置，把前缀切断**。

问题是这次切断值多少钱。实测给出的答案：

| 项 | 值 |
|---|---:|
| 一次换档的实际花费 | **6,100 tok** |
| 上下文变化 | ~139K → ~14K |
| 保留的保守常数 | `PREFIX_BREAK_TOKENS = 18,830` |

一次真实的换档只花了 6,100 token，把每步要重发的体量从 139K 压到 14K。**用 6,100 的一次性支出，换之后每一步的税基降到十分之一。** 这就是「压缩本质上是主动的、一次性的缓存破坏」这句话的实物定价。

文档里另有一处口径略有不同的估算：`0.0075 元/批（净 18,830 tok @ 未命中 0.4 元/M）`，换每步体量从 ~250K 降到 ~40K，结论是「这笔交易压倒性划算」。6,100 与 18,830 的差异来自测量口径和会话负载不同——我们保留了后者作为工程上的保守常数，宁可高估破坏的代价，也不低估。

这也把「最终形态」讲清楚了：**不是「高命中」和「低基座」二选一，而是低基座 + 高命中。** 每当基座涨到不划算，就主动切断一次、把它压下去，然后在新基座上重新积累长链命中。命中率是这套机制运行的结果，不是它的目标。

## 结尾

把这一篇的四句话收拢：

**每一轮的账单 ≈ 步数 × 基座，经折扣折算。** 命中率是这个乘积里的折扣系数，基座是那个乘数本身。优化折扣的收益是线性的，优化乘数的收益也是——但乘数乘在步数上，而步数在长任务里会很大。

所以封版清单里有一条，是整个系列的题眼：

> **命中率从此只用来诊断，不用来讨好。**

这句话不是一个技术决定，是一个方向决定：把它从 KPI 的位置上拿下来。因为一旦命中率成为考核指标，团队就会去优化那些能让数字好看、但对账本没用的东西——比如维持一个臃肿但稳定的大基座，它的命中率天然漂亮，而它每一步都在按大税基计费。

而整套架构的账，从 0.95× 到 1.58×，横跨一个行业折扣光谱的宽度。这个事实我们选择正面写出来：**如果行业一路卷向更深的前缀折扣，Wovra 的价值主张会被削弱；如果停在 1/10 附近，它有明确的净收益。** 一个成本模型如果不敢标注自己的适用边界，它就不是模型，是宣传。

下一篇讲**执行期零截断**到底长什么样。这一篇一直在说「基座是税基」，但基座为什么会涨起来、又怎么在不让模型失忆的前提下压下去——那是机制层的事，也是三代实验里代价最惨烈的一段：39 次重读同一份文件，只因为一次「省 token」的截断。

省下的折扣钱，会被重读和返工加倍买回来。
