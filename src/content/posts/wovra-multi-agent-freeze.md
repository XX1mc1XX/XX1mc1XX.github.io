上一篇把成本模型讲完了，它的题眼是那句话：**命中率是折扣，基座是税基。** 这一篇讲一个具体的架构死法——我们花了大半年搭起来的一层"组织运行时"，被一次实验判死，然后被我们自己反复解剖了半个多月。

先把话说在前头：这不是一个"多 agent 是错的"的故事。**判死它的从来不是"多 agent 太贵"，而是"它想省下的东西，这个代码库里的另一个功能早就替它省掉了"。** 这两个理由看起来只差几个字，但它们决定了这个故事值不值得写。

## 一、被冻结的是什么

被冻结的东西在文档里叫 V1 组织运行时，定位是**"应该存在几个上下文、各自装什么"**——如果上下文管理 V3 管的是"一个上下文怎么不撑爆"，这一层管的是"要不要多开几个上下文"。

它的机制核心是三样东西：`spawn_subtask` 派生子任务、`dispatch_subtask` 异步派发（派发秒回、不阻塞主 agent）、以及**事件唤醒**——子任务跑完，系统发一个通知，主 agent 自动接手。主 agent 只做对话、拆分、汇总；具体活由子 agent 并行去干。

这套设计在当时看起来非常合理。三个子任务在数据上确实是独立的：一个写游戏逻辑、一个写渲染引擎、一个做程序化贴图，互不依赖。直觉说，三个并行，墙钟应该是三分之一。

它还有一套听起来很讲究的分工：**掌握全局的主 agent 只做拆分、汇总、修计划，具体活交给子 agent**。文档里给主 agent 写的限制是"不做具体工作、不深入细节"，理由不是职级礼仪，是**资产保护**——主上下文一旦开始装源码，整个架构就退化回了单 agent 旧世界。所以组织层的分工原则是"**切职责，不切视野**"：子 agent 带着全局视野去做自己那一块，不是只给它一小片。

传递纪律也定得很细：原始需求逐字下传、逐层只追加，目标下传、事实上传、方法不进传递——为的是防"电话游戏"，也就是传话过程中的语义漂移。

`spawn_subtask` 在那场实验里真的派出了三个并行子进程。文档里那张"机制实战验证清单"记录了**七项机制全部第一次真跑通**，其中几项特别能说明这套东西的设计意图：

| 机制 | 实测表现 |
|---|---|
| 异步派发 | 3 块并行后台执行，派发秒回、不阻塞 |
| 事件唤醒 | 子任务全部结束（exit 0）后，主 agent 自动接手 |
| 父驱动续派 | 主 agent 读完子任务产出，续派带精确决策（"你的 5 个 JS 已过校验，剩余工作：写 README"） |
| 交叉核验 | 逻辑层实测渲染层 30 个贴图名零缺失，还发现对方未导出 `scene` 并适配留痕 |
| 待办实验 | 子任务主动写出"机器无法自测，请人工目检"——**人当传感器**被模型主动使用 |

最后一条尤其值得看：交叉核验是"独立 agent 互相怀疑"，单 agent 在结构上做不到。**机制是活的，而且有几项是单 agent 真的做不到的。** 问题是它不划算。

## 二、三组对照：一个被数据判死的架构

![一次被数据判死的架构：多智能体冻结](/images/wovra/多智能体冻结.svg)
先用一个 Minecraft 复刻任务跑了三组对照。任务书一字不差，同一个模型，三组工作区隔离。下面是三组合计对照表——A、B 来自 09-06/09-07，D 是后来追加的：

| | A 单 agent（旧栈） | B 组织 V1.2 | D 单 agent（新栈） |
|---|---:|---:|---:|
| 墙钟 | 116 分 | 108 分（3 子并行） | **94.5 分** |
| 步数 | 99 | 135 | 229 |
| 上下文峰值 | 90K | 主 31K / 子 70K | 110K |
| 等效输入 | 263K | **1,218K** | 857K |
| 现金（GLM 半价） | ≈0.45 元 | **≈1.10 元** | ≈0.59 元 |
| 缓存命中 | 98.3% | 88.1% | 96.6% |
| 机器验证 | node --check 级 | 无（人当传感器） | 冒烟 31/31 + E2E 27/27 |
| 观感分 | **0** | **1** | **通过** |

这里有几件事必须一行一行说清楚。

**墙钟 108 分对 116 分，是 7%——在噪声里。** 文档自己用的词是"≈持平"。三个并行子 agent 买来的墙钟改进接近于零。我们要说的话很准：**多 agent 不是更慢，是更贵。** 你甚至没法说它变慢了，7% 的差距不足以支撑"更快"或"更慢"任何一个结论。

**等效输入 +4.6×，现金 +2.4×。** 这才是真正的代价。B 组等效 1,218K，A 组是 263K。现金 1.10 元对 0.45 元。

**质量 0 分对 1 分，而两边都不可玩。** A 组材质全部加载不出、世界空白、前后按键颠倒；B 组世界断成一小块一小块、功能还更少。0 和 1 都是"不可玩"档位里的读数。**这个质量差是噪音级的，它不能用来支持任何一边。**

那 4.6× 是怎么构成的？文档里归因写得比任何总结都清楚：

| 成本项 | 内容 |
|---|---|
| 冷启动税 ×3（最大单项） | 每个子 agent 从零建上下文，命中率 73.8–94.5%，而单 agent 是 98.3%；等效/步 6–10K，单 agent 2.7K |
| 翻译与调度 | 主 agent 等效 223K，只产出调度与汇报——不产生代码，但按全价计费 |
| 接缝与重复劳动 | 各块自带的 mock、测试、防呆、接口适配 |
| 轮边界缓存破坏 | 多轮重建装配尾部，命中率从 98.3% 掉到 88.1% |

四项里没有一项是"多 agent 这个概念的固有缺陷"——它们全是在"同时开三个上下文"这个决定下必然产生的开销。

## 三、真正打死它的那一组

如果故事停在 A 对 B，那只是一个「多 agent 比预期贵」的故事。真正把它判死的是 D 组——**2026-09-08 追加的、新栈上的单 agent 重跑**。

D 组跑的是同一句话原文，但栈不一样了：V1.2 里组织层已经删掉，单 agent + V3 水位管线 + todo 工具，步数上限 60。结果：

- **现金 ≈0.59 元，是 B 组的 54%。**
- **观感通过**——用户实测移动、挖掘、放置、飞行、地形连贯全部正常，而 A、B 两组在这些项上**全灭**。
- 唯一缺陷是材质全黑（法医定性：没开灯，不是没世界——两行亮度修复，详见下一节）。

D 组的结论是一句话：**新栈上的单 agent，在每一根轴上都赢了多 agent。** 更便宜、更快、质量更好。到这里，组织层冻结就不再是一个判断，是一组数据追认出来的事实。

这里有一个必须点出来的细节，因为它是整个实验最深的发现：**A、B 全灭的那几项，D 组是能做对的。** 差别不在 agent 数量，在验证密度——D 组把 96 次 `run_command`、约 42% 的步数花在了验证上（Node 冒烟 31/31 + Playwright E2E 27/27），而 A 组同期是 74 次 `edit_file` 纯干活、零验证。**质量差异的第一归因是"机器有没有眼睛"，不是"agent 有几个"**，这是另一条线，这儿只留一句。

D 组还顺手做了一次法医：为什么 E2E 27/27 全绿，材质还是黑的？因为全部断言都是**行为断言**（fps、顶点数、交互链路），零**像素断言**。几何与交互全部真实工作——"漆黑中可玩"——只是渲染亮度错了（本地化 three.js 默认物理光照，模型按旧光照模型调光强，全场景暗了 π 倍，加上天空背景没设置）。**补一条"视口中心平均亮度 > 阈值"就能当场抓住它。** 这件事和前面的多 agent 判死关系不大，但它解释了为什么"机器验证的密度"比"agent 的数量"更决定结果。

## 四、四十天后的法医：我们自己污染了对照组

写到这里，如果直接下结论，就太顺了。真实的复盘是：**这个实验的对照组被两起事故污染过，而且是靠法医、不是靠细心发现的。**

**事故一：`WOVRA_SOLO=1` 根本没设上。** A 组本该是"组织层结构性禁用"的单 agent 对照，我们用的是 `set WOVRA_SOLO=1`——但那是 PowerShell，`set` 是 `Set-Variable` 的别名，这行**静默失败**。于是 A 组跑的时候组织层还是活的，A 组的口径从一开始就是脏的，**最后整个重跑了一遍**。

修复方式很值得记一笔，因为它不是"下次小心点"：**chat 启动横幅自报组织层状态，并写进 session 记录**——对照口径由运行时持有、当场可见，不靠用户记得自己设了什么。**一个静默失败的环境变量，被换成了一个会自我声明状态的运行时。**

**事故二：Ctrl+C 级联杀死了所有后台子进程。** 用户中断主会话时，控制台级联把三个后台子 agent 全杀了（`exit_code=3221225786`，也就是 `0xC000013A` `STATUS_CONTROL_C_EXIT`）。后果是**游戏逻辑层那个子任务的账本整个丢了**——它的日志恰好结束在最终回答上、没有耗时行，等于"代码交付了，账没记上"。子进程死于"轮已闭合、成本已记"之后、"收尾补整理"之前。

修复是给后台进程和 `run_command` 子进程加 `CREATE_NEW_PROCESS_GROUP`——新进程组默认免疫 Ctrl+C，而整树停止仍走 `taskkill`、不受影响。**"用户中断"和"后台任务被顺手杀掉"本该是两件事，我们用进程组把它们切开了。**

这两起事故的性质是一样的：**都不是机制错了，是对照组的环境被污染了，而污染是静默的。** 这也是为什么文档里那套"账本"存在——没有逐调用落盘，你根本不知道自己污染了哪一组。

## 五、第三次法医，这次法医砍的是主角自己

真正让这个实验变得有意思的是第三次解剖：**它质疑了 A 组 98.3% 命中率的基线资格本身。**

事情是这样：我们对 A、D、E 三组做了逐调用生成时长重建加 TTL 拟合。D 组和 TTL≈60s 拟合得很干净，误差 6%；但 **A 组用任何 TTL 模型都拟合不上**——它晚期有三次长生成（245s / 264s / 118s，当时前缀已经 60–70K），按 D/E 表现出的缓存行为，本该产生约 198K 的 miss，而 A 组全程 miss 只有 90K。**A 组对 26 分钟的长生成"免疫"，在一个按时间过期的缓存模型下是讲不通的。**

于是当时的结论相当严厉：**A 组（09-06 旧栈）极可能跑在不同的模型或端点缓存策略上**，"同一模型"这个前提对 A 组从未验证，而 09-06 的 `.env` 已经无法回溯。**"A 的 98.3% 不能作为 D/E 的缓存对照基线，同端点公平对照只有 D 对 E。"**

这句话的杀伤力很大——A 组那张表里所有列，包括现金推算，都带着这个未验证的假设。**我们一度以为自己搭了一张干净的三方对照表，结果发现自己最依赖的那一列基线，资格存疑。**

然后是第四次出手，这次不是砍，是救。我们写了一个 `cache_ttl_probe`——**同一段恒定前缀，按阶梯间隔 [0, 10, 30, 60, 120, 300, 600] 秒重发，读 `cached_tokens`。** 结果推翻了"TTL=60s"这个判决：

| 间隔 | 63K 前缀 | 188K 前缀 |
|---|---|---|
| 0s（冷启） | 0% | 0% |
| 10s / 30s / 60s / 120s / 300s | **全部 100.0%** | **全部 100.0%** |
| 600s | **100.0%** | **0.0%（整体死亡）** |

**TTL ≥ 10 分钟，而不是 60 秒。** 于是 A 组 26 分钟免疫这件事**重新可以解释了**：A 的前缀全程在 7–71K 之间，大多小于 60K，恰好落在"存活区"；它的 98.3% 和"同一端点"假设不再矛盾，**此前那个"不同端点"的猜测被降级为待验证。**

我们后来意识到，.env 回不来那次事故其实不是缺陷，是一次强制的诚实——**它逼我们把"端点不同"这个带满好奇的假设先摆上台面，等一个探针来裁决。** 真相是两位都错了一半：A 的基线**部分可信**，但不是干净的对照。

这一整条弧线，比任何一句"多 agent 好还是不好"都更接近我们真正的工作方式：**先量，量出不动的数，再回头怀疑量尺本身，然后造一把更准的量尺。** 我们引用这个实验的时候，最信的不是那几格数字，是这条"数不干净就查数、查完再查仪器"的链条。

## 六、动态生成

三项独占资产里有一句"账本=报告 + 编制复用（长周期记忆与连续性，V2 蓝本未建未证）"——这里的"未建未证"值得单独点一句，因为它是整个冻结里唯一一个"我们没测完就下了判决"的地方。

组织层的价值主张收缩成三项之后，其中两项（人机协同通道、父驱动里程碑循环）都有小规模实证，唯独第一项**编制复用**——也就是"子 agent 的上下文和身份可以跨任务长期复用，形成长周期记忆"——**连蓝本都没建起来，更没有验证**。也就是说，冻结时砍掉的那部分里，有一块是我们**从来没有测过**的。

这个事实让我们在写判决书的时候多了一层心虚：**我们判死它，主要靠的是"它想省的东西别人已经替它省了"（那四条反驳），而不是"它所有价值都被验证为假"。** 编制复用这条路，是**因为前置条件（出现真实需要长周期复利的任务形状）没到，所以没动工**——不是被数据否定，是没被数据触碰到。冻结的时候我们说的原话是"动工前置条件 = 出现真实需要长周期复利的任务形状"。它是一个被搁置的选项，不是一个被证伪的假设。

## 七、账本：为什么这个架构"能被判死"

这个实验最容易被忽略的前提，是它**本来就有资格被判死**。Spawn 派发、事件唤醒、子任务账本、逐调用落盘——如果没有这套账，多 agent 只会留下一句"感觉有点慢"，然后一直跑下去。**能判死一个架构的，不是它失败，是它失败得能被测量。**

我们在这件事上吃过一次教训，正好可以记下来：D 组的法医发现，材质全黑这个缺陷**穿透了 E2E 27/27 全部验证**——因为所有断言都是行为断言（fps、顶点数、交互链路），零像素断言。一个"验证密度很高"的运行时，照样会让一个两行就能修的缺陷溜过全部检查，因为它**检查的维度里根本没有那一条**。

这和判死组织层是同一件事的两面：**你能测的维度，决定了你能优化什么、也决定了你能否证什么。** 组织层被否证，是因为账本量了等效输入、量了墙钟、量了缓存命中——这些维度都在。如果账本只记"任务完成了没有"，多 agent 和单 agent 在账面上会一模一样（都"完成了"或都"没完成"），那个 4.6× 永远不会被发现。

所以我们从这个冻结里拿走的不只是一条架构结论，还有一条方法论：**想让复盘有价值，先把测量的维度铺开。** 你无法否证你没在量的东西。

## 八、判决书：四条反驳，第一条才是主因

实验跑完之后，用户给了四条反驳。这四条是冻结决定的**官方理由**：

| # | 反驳 | 分量 |
|---|---|---|
| 1 | 主上下文不膨胀 | **V3 分层装配实测已保证**（A 组 90K 封顶从未失控），多 agent 增量为零；它多给的只有"专项 agent 手里是自己块的全分辨率"，对做调度的脑子没意义 |
| 2 | 并行 | 市面已有商品（commodity） |
| 3 | 交叉验证 | 有明确验收标准 + 独立审查轮即可大部分替代 |
| 4 | 失败隔离 | V3 降档本来就在做"无关话题淡化" |

**这里有一个我们最初差点写错的地方，值得单独说。** 一开始我们准备把冻结原因写成"多 agent 想省的那些东西，市面上已经有商品了"——也就是第 2、3 条。**这个框架只对了一半。**

第 1 条才是主因，而它比"竞品存在"狠得多：**多 agent 唯一想独占的那个价值——"让主上下文不膨胀"——V3 分层装配在同一份代码库里早就实现了。** A 组的上下文 90K 封顶、从未失控，而 A 组是**没有组织层的单 agent**。也就是说，组织层存在的头号理由，被它隔壁的功能替它兑现了，**增量为零**。它多给的，只是"专项 agent 手里是自己那一块的全分辨率"——而这个对做调度的脑子没有意义。

第 2、3、4 条是"它在别处也能买到"；第 1 条是"它想卖的东西，我们自己家里已经有了"。**后者才是致命的，因为它让组织层连"独占价值"都拿不出来。** 收缩之后，组织层的独占资产只剩三项：账本即报告 + 编制复用、人机协同通道、父驱动里程碑循环——全是长周期资产，跟"并行更快"无关。

顺带记一个被数据否掉的方案：我们曾提议给"每轮 15 步硬预算"，被否了。原因是实测多小轮的命中率只有 69.8%（主 agent 6 小轮），而大轮是 98.3%——**轮边界重建的预算税不划算**。改成"里程碑驱动轮"：轮长由父 agent 派发时写明的检查点定义，步数上限退化成安全网。

## 九、冻结之后：它不是被埋了

如果故事到这里结束，就成了一个"我们埋了多 agent 再也没回头看"的故事。**不是的，而且文档明确反对这么写。**

原来的必要性门槛写得很硬：**"只能从一个被证明的真实失败里长出来——某任务在单 Agent 栈里溺死，且死因明确是上下文混装了不兼容的职责。不是从'多 Agent 是趋势'长出来。"** 多 agent 被冻结在 V1.2，就是在等这个"溺死现场"。

然后 2026-09-11，用户拍板，把这条门槛**正式推翻了**：

> 多 Agent 没有等"单 Agent 溺死"，而是作为**整理的副产品自然长出**：水位整理与分域一体实现，从真实工作里析出职责域，注册表 + 分流（notify / consult）在同一运行时内按职责切换视角。本质仍是**单 Agent 分流**，不是同步并发的多 Agent。

这里有个漂亮的因果反转，是整件事的思想核心：

> **不是先有 Agent 再分配上下文，而是先有真实工作，从上下文的自然分化中产生 Agent。**

那条链条长这样：真实工作 → Event → Round → Block（运行时结构化，零 LLM）→ 语义标注（低频批量 LLM，随水位整理做）→ 稳定工作边界 → 水位拆分 → Context View → 必要时才是独立 Agent。

**换句话说：V1 是"先设计几个 agent 再往里塞上下文"，活过来了的是"让上下文自己长出边界"。** 冻死的是前者——模型驱动的同步并行编排；活下来的是后者——单运行时内的职责分流，子 agent 是"注册表条目 + 上下文视图 + 路由规则"，**共用同一份共享历史，没有并发协调开销**。现行 V4 就是这么跑的。

**多 agent 死于"它是个进程"，活于"它只是个视角"。** 这是这一篇真正想留下的东西。

## 十、一个连触发条件都碰不到的实验

还有一个数字，是后来做另一个实验时顺手撞出来的，但它戳中了同一件事。

我们拿一个真实产品做了 35 轮会话，目的是"构造双域场景、触发多 agent 分裂"。**结果从头到尾一次都没触发。** 原因写在会话记录里：分裂的门槛是水位到 10%（100K），而**纯聊天根本撑不到那条线**——聊到第 12 轮，上下文才 46,359 token，4.6%。用户原话："我们聊的体量还达不到，多 agent 的触发条件……需要达到 10% 才能触发压缩整理、多 agent 分裂。"

**这比"分裂了但不划算"更彻底：分裂的触发条件本身，在普通使用里根本碰不到。** 一个需要"上下文涨到 10%"才能启动的机制，在一个大多数人聊不到 5% 的场景里，等于不存在。

这件事还顺手改掉了一个设计口径。原来我们想的是"水位到了就该整理、整理就该分裂"，隐含假设是"水位迟早会到"。35 轮实测把这个假设证伪了——**水位不是迟早会到，是很多人都永远到不了。** 于是后来的方向从"设计一个 agent 分裂动作"改成了"从水位整理里自然析出职责域"——**门槛不再是一个需要人去凑的百分比，而是工作本身自然地把它推过线。** 会话记录里用户还补了一句很有代表性的抱怨："其实很多场景聊天到 500k，一轮对话走个 30 步，步算增量，都烧掉 15M 的 token 了"——这句话本身也是这个项目一开始的动机：被成熟 agent 失控的成本逼出来的。

## 十一、说清楚我们有多不确定

这一篇的数字看着很硬，但边界必须写清楚，一条不省。

**一、n=1，无重复。** 文档里那段效度声明我们原样引用：

> **效度声明**：n=1、无重复；任务为纯前端观感类（强多模态依赖），任务书不含可自动化验收——观感结论里"模型上限 vs 运行时质量"的归因分不清。本报告的**成本/时间/机制验证**部分不受此影响。

翻译过来：成本、时间、机制这三类结论可信；**观感评分的两列不可信**。这也是为什么我们从不拿"0 分对 1 分"来论证多 agent 差——它本来就是噪音级的。D 组也只跑了一次。

**二、V1–V2 机制的文档全部标了"淘汰"。** 上面所有这些数字，都来自已经被移除的机制。它们的身份是**历史证据**——结论还在影响设计，机制本身已经不存在。引用它们时必须带着这句话，免得被读成现役性能。

**三、B 组那三格看着最干净，其实也有故事。** 三个子 agent 是并行跑的，但账本被 Ctrl+C 事故误杀过一个，游戏逻辑层那份是重派一轮、靠 `organize_backlog` 补上的历史账。

**四、不要跟另一组同名的 A/B/D/E/F 搞混。** 日志里还有一批"A/B/D/E/F 组"，指的是另一场机制实验的分组，跟这里的组织层对照不是一回事。

**五、最诚实的一条：那个"多 agent 到底会不会赢"的问题，我们从来没测过。** 文档里写得很直白——这次的失败原因之一是**"任务形状错配"**：观感类任务测的是"模型 × 多模态"，不是运行时。而**"多 agent 在一个验收可自动化的任务上会不会赢"，从来没有人测过。** 我们把它留给了未来一个"验收可自动化"的任务形状（候选是"Wovra 开发 Wovra"——任务长、测试即验收、块天然独立）。**这个冻结点是"在旧栈、在这个任务形状下、在 n=1 上"的判决，不是"多 agent 永远不会赢"的定理。** 我们宁可把这句写得比结论还醒目。

**六、那个决定性的对照也许不干净。** D 组是"新栈单 agent"，它比 B 组便宜、快、质量好——但 D 组同时换了**栈**（删掉组织层、上了 V3 水位管线、换了 todo 工具、步数上限从 60 改到后来 200）。所以严格说，D 赢的是"新栈"对"旧栈 + 组织层"，不是纯粹"单 agent"对"多 agent"。

**这里要分清哪个结论仍然成立、哪个被削弱了。** B 对 A 的 4.6× 是干净的——A 和 B 都是旧栈，只差"有没有组织层"。这一条是这篇文章最硬的地基，不受影响。被削弱的是"D 证明单 agent 比多 agent 强"这个更宽的说法：**D 的胜利里，有多少来自"删掉组织层"、有多少来自"换了整套栈"，这组数据分不开。** 我们在正文里同时用了这两个结论，所以这里必须把它们的强度差标出来——**A 对 B 是干净对照，D 是"新栈整体更优"的证据，不是"单 agent 更优"的孤立证据。**

**七、还有一个连我们自己都改过口径的地方。** B 组的步数在不同表里有过 135 和 37 两个数——前者是三块子任务（含主 agent）的合计，后者只是主 agent 自己那一轮。两个数都对，指的是不同的东西。**这类"同一个名字指不同对象"的口径，是复盘里最容易埋雷的地方**，我们把它点出来，免得读者拿一个数去对另一张表。

## 踩过的坑

**坑一：把"环境变量设上了"当成"环境变量生效了"。**

`set WOVRA_SOLO=1` 在 PowerShell 里静默失败，A 组整个重跑。这是这个系列里最贵的一类错误——**它不报错、不崩溃，只是让你的一组数据一开始就是错的，而你要过两天才发现。** 修复不是"下次用对语法"，是让运行时把状态写进 session 记录、当场自报。**凡是"靠人记得设对了"的对照，都迟早会被污染。**

**坑二：以为"唯一的全局对照基线"是安全的。**

A 组是三组里唯一一个"与 B 干净的对照"，于是它成了整张表的支点。结果法医发现它的 98.3% 可能根本不在同一个端点/缓存策略上。**你把最多结论压在的那一列，恰恰是唯一没验证过的那一列。** 这把我们逼出一条纪律：**"同一模型"这种前提，也要有证据，不能默认。**

**坑三：以为"机制跑通了"就是"机制值得存在"。**

七项机制全部第一次真跑通——异步派发、事件唤醒、清算合并、交叉核验，一个不缺。**但"能跑"和"该跑"是两件事。** 机制清单全绿，账本上却是 4.6×。我们一度把"机制验证通过"当成了阶段的成功，后来才分清：**那验证的是"我们能不能实现它"，不是"实现它划不划算"。** 后者只有账本能回答，而且答案是否。

**坑四：差点把冻结原因写成"竞品存在"。**

"省下的东西市面上已经有了"——这个框架顺手、好写、听起来也很有道理。但它只对了一半。**真正的主因是"它想省的东西，我们同一个代码库里的另一个功能早就省掉了"。** 前者是"你能买到替代品"，后者是"你连独占价值都没有"。后者更难堪，但也更准确——而**复盘的价值恰恰在准确，不在好写。**

**坑五：在一个"控制组被污染"的实验上做判决，还差点没当回事。**

两组数据各自被一起事故污染过（环境变量、Ctrl+C），A 组的基线资格后来又被第三方取证质疑。**如果不是那套逐调用落盘、逐条取证的习惯，这个实验会以"多 agent 贵 4.6×"一句结论收场——而真相是"在这个端点、这个任务形状、这组 n=1 数据上，它贵 4.6×，且它的头号价值被 V3 免费提供了"。** 前者是一句口号，后者才是一个决定。

## 十二、最后：它死于一个免费的功能

把这个架构的死法收成一句：**它想做的那件事——"让主上下文不膨胀"——是一个已经被交付过的功能。** 组织层拿不出任何独占价值，剩下的三条（并行、交叉验证、失败隔离）要么是 commodity，要么有更简单的替代。于是一次实验就把它判死了，判词是数据，不是偏好。

但更值得记住的是它的**复活方式**。它没有作为"更多并行的 agent"回来，而是作为"同一运行时里切换的职责视角"回来——**不是先有 Agent 再分配上下文，而是先有真实工作、从上下文的自然分化中产生 Agent。** 冻死的是"把 agent 当进程"，活下来的是"把 agent 当视角"。

回头这一路，改掉的问题比任何一个机制都值钱：我们最开始问的是**"要不要多开几个 agent 来并行干活"**，现在问的是**"真实工作自己在哪里分出了边界"**。前一个问题导出的是 `spawn_subtask` 和调度链；后一个问题导出的是注册表、职责域和路由规则。**两个问题只差几个字，但一个死了，一个活着。**

所以这一篇写得很不干脆，是有意的：**这不是一个"我们错了"的故事，也不是一个"多 agent 不好"的故事。** 它是一个"我们花了很久才分清'能跑'和'该跑'"的故事，是一个"对照组被污染、又被我们自己的法医救回来一半"的故事。如果一个架构的死因写出来像一句口号，那它大概率还没被真正查清。

下一篇换一个任务——同一个文件、同一句话、三代机制。讲的是三堵墙里被数据推翻得最彻底的那一堵，和它身后两次实实在在的翻车。
