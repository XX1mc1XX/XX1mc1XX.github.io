上一篇把六层依赖画完了：资源层、交互层、门面层、契约层、实现层，依赖只准向下，唯一的反向是依赖倒置。

这一篇往下钻一层，讲那面墙本身——`CameraInterface`，17 个纯虚方法。

上一篇我说「契约层不认识任何具体相机」，这句话落地成代码之后到底长什么样、为什么是 17 个而不是 12 个或者 25 个、定少了会怎样，是这一篇的内容。

## 先想清楚"一台相机应该能做什么"

我装修过房子，签合同前会有一张清单：水电改造几米、墙面刷几遍、地板什么牌子。清单先定，施工队照着做。清单上漏了"窗台石"，后面要么加钱补做，要么就这么算了。

写相机客户端之前，我看的也是这么一张清单。只不过这份清单问的不是装修队，是设备：

> 一台工业相机，不管它是海康、巴斯勒还是大恒，**上层需要它能做什么？**

这就是契约。**契约层不关心海康的 SDK 怎么调，它只回答"一台相机应该能做什么"。** 上层（门面、参数面板、图像显示）只对着契约编程，永远看不到 SDK。

海康 MVS 的 SDK 有几百个接口，全都要在 `HikCamera` 里被接住。契约层要把这几百个接口的能力归纳成十几个动作，一份清单，谁都得照着满足。

清单定完，我心里踏实了点：**上限是确定的**。不管以后接什么品牌，界面、门面、图像链路全是按这张清单写的。

## 去数一遍：确实是 17 个

先把清单摊开。别信脑子里的印象，`grep` 一遍：

```bash
grep -n "= 0" src/CameraInterface/CameraInterface.h
```

去掉重复输出和结尾那行，正好 17 行。方法名逐个记下来：

```text
getParamList   isConnect   isGrabbing
acquire  release  connect  disconnect
creatStream  destroyStream  startGrabbing  stopGrabbing
loadConfig  saveConfig  configFormat
readParam  writeParam  getImageLast
```

我数了两遍，确认是 17 个。这个数字后来写进了架构文档、CHANGELOG、README——**一个能被 grep 复核的硬数字，比"十几个方法"这种说法可靠得多**。

## 17 个方法，三个域

17 个平铺着看很乱。我按"上层拿这台相机干什么"分成三域，一下就清楚了：

| 域 | 方法 | 个数 |
|---|---|---|
| **设备全生命周期** | `acquire` / `release` / `connect` / `disconnect` / `creatStream` / `destroyStream` / `startGrabbing` / `stopGrabbing` | 8 |
| **参数读写** | `getParamList` / `readParam` / `writeParam` | 3 |
| **图像获取** | `getImageLast` | 1 |
| 状态查询与配置（辅助） | `isConnect` / `isGrabbing` / `loadConfig` / `saveConfig` / `configFormat` | 5 |

第一眼看会觉得不对：生命周期占了 8 个，图像获取就 1 个，这重心偏得厉害。

但这就是工业相机的真实形状。**图像获取在契约里只要一个动作就够**——上层要的是"给我最近一帧"；真正复杂的缓冲、丢帧、复用，全被藏进队列里（后面第五节说）。而设备状态是一台真设备才有的一堆生命周期：句柄、连接、流、采集，每一样都要能开能关，还得能问"你现在是什么状态"。

## 生命周期为什么是两段式的

8 个生命周期方法里，最费我脑子的是 `acquire` / `release` 和 `connect` / `disconnect` 为什么要拆成两套。直接一对 `open` / `close` 不行吗？

我一开始就是那么想的。直到看海康的 SDK：**创建句柄**和**打开设备**是两件事。句柄可以先建好放着，不占设备；设备可以随用随开。如果契约只有一个 `open`，实现层就只能把两步塞在一起，某个厂商想先建句柄做点初始化就没有落脚点。

所以我拆开了，并且在头文件里把顺序写死：

```cpp
// 顺序契约：acquire（建句柄，不占用设备）→ connect；断开时 disconnect → release，二者成对
virtual uint32_t acquire() = 0;
virtual uint32_t connect() = 0;   // 打开设备并挂取帧回调
virtual uint32_t disconnect() = 0;// 注销回调、关设备，句柄留给 release
virtual uint32_t release() = 0;   // 真正销毁句柄
```

**为什么这么写**：这两对不是重复，是两段资源生命周期。`acquire` 管句柄、`connect` 管设备连接，各自可独立成败。多了一个"只建句柄不占设备"的中间态，上层可以在这段里做"检查设备能不能访问""预分配缓冲"这类事而不惊动硬件。代价是调用方必须记住顺序——所以我把顺序直接写进注释，让它成为契约的一部分，而不是靠实现层自觉。

采集流也一样成对：

```cpp
// creatStream 须在 startGrabbing 前、destroyStream 在 stopGrabbing 后调用
virtual uint32_t creatStream() = 0;     // 配流参数，不是采集开关
virtual uint32_t startGrabbing() = 0;
virtual uint32_t stopGrabbing() = 0;
virtual uint32_t destroyStream() = 0;
```

**为什么这么写**：`creatStream` 是"配置流"（缓冲深度、取帧策略），不是"开始采"。很多 SDK 把这两件事混在一个接口里，我在契约上把它俩拆清楚——配流是配置动作，采流是运行动作，中间还可能插入"改个流参数再重启"的操作。名字还留了个小瑕疵：`creatStream` 少个 `e`，是沿袭自厂商 SDK 的拼写。改起来一行的事，但改了所有实现都得跟着动，我就没改，**契约定型之后任何一个改名都是全体补丁**。

## 为什么用纯虚接口，不是继承一个基类

17 个方法全都写成 `= 0`，纯虚。也有人问过我，为什么不写一个带默认实现的基类，每个方法给个空实现，厂商只重写要用的？

我选纯虚，三个理由：

**第一，纯虚让"没实现"变成编译错误。** 如果 `readParam` 给了默认空实现，某个厂商忘了重写，编译照过，运行时悄悄什么都不做。纯虚的话，漏一个直接编译不过——**契约的强制性必须由编译器执行，不能靠人自觉**。

**第二，没有"默认行为"可继承。** 基类默认实现想给点什么？`connect` 默认什么都不做？那是个错误的语义。相机行为没有普适默认值，给了默认值反而诱导厂商偷懒。

**第三，实现层本来就得从零写。** 海康要调 MVS，虚拟相机要造帧，共同点只有签名，没有共同实现。既然没有可复用的实现体，继承一个基类只是背了个空壳。

代价也真实：**每加一个方法，所有实现立刻编译失败，必须同步补全**。这既是代价也是保障——我在下一篇讲工厂时会提到，虚拟相机和真机同契约，靠的就是这个强制力。

不过基类不完全没东西，它留了三个**非虚**的成员函数给所有实现共用：

```cpp
virtual QString UserName() { return m_cameraInfo.UserDefineID; }
virtual QString Serial()   { return m_cameraInfo.Serial; }

virtual CameraImageQueue& ImageQueue() { return m_imageQueue; }

protected:
    CameraImageQueue m_imageQueue;
    CameraMetaInfo   m_cameraInfo;
```

**为什么这么写**：这三样是"所有相机都长一样"的部分，不需要厂商重写。身份信息直接来自基类持有的 `m_cameraInfo`；图像队列是基类内置的一个成员，所有实现共用同一套线程安全队列。厂商实现只需要填 `m_cameraInfo`、重写那 17 个纯虚即可。**纯虚定边界，非虚给共性**——一个接口两类成员，分工很清楚。

还有个细节值得记：`UserName` 和 `Serial` 明明只是读 `m_cameraInfo`，理论上该标 `const`，实际没标。不是疏忽，是早期写着顺手，后来发现这个接口层被大量跨层调用，改动面太大就放着了。**这类"明知不理想但改动成本高"的妥协，契约层里会一直存在**，得学会分辨哪些必须现在修、哪些可以欠着。

## 统一参数模型：不同品牌怎么用一套结构表达

生命周期好办，参数才是真麻烦。海康的曝光是 `float` 带上下限，巴斯勒的增益是 `int` 带增量步长，某家的触发模式是枚举、另一家是字符串。

上层不能为每个品牌写一套参数处理。所以我在契约层定义了一个统一模型 `CameraParam`，**把六种参数类型压成一个外观类**。

先看类型枚举和值结构：

```cpp
enum ZCParamType { UNKNOWN = 0, INT, DOUBLE, ENUM, BOOL, CMD, STRING };

struct IntParam : public ZCParam {
    int64_t value {}, min {}, max {}, increment {};
    ZCParam* clone() override { return new IntParam(*this); }
};
struct DoubleParam : public ZCParam { double value {}, min {}, max {}; /* ... */ };
```

**为什么这么写**：每种类型一个结构体，各自带自己的元信息（`min` / `max` / `increment` 这类只有数值型才有的字段）。这比"一个结构塞所有字段、用不到的就空着"干净——`BoolParam` 里不会有莫名其妙的 `min` 字段。六种类型各自 Data 自洽，上层按需取。

值本身用 `QVariant` 承载，元信息单独一层：

```cpp
struct CameraParamMetaInfo {          // 静态描述：哪家的哪个参数
    QString group, name;
    ZCParamType type { UNKNOWN };
    QString relative_list, tips;
};

class CameraParam {                    // 外观类：元信息 + 值 + 权限
    CameraParamMetaInfo _meta;
    QVariant _value;                   // 存的是上面那几个结构体的副本
    struct { bool valid:1, readable:1, writeable:1; } _accessMode {};
};
```

**为什么这么写**：`type` 是取值的解包开关。写进去时按类型塞 `QVariant`，读出来时按 `type()` 决定解包成哪个结构体。外观类对外只暴露 `displayText()` 和三个权限查询，上层 UI 根本不需要知道底层是 int 还是 enum——面板按类型挂对应控件即可。**这一层抽象的收益是：新增一个参数型号，不编译不发版，只改 JSON。**

代价是这里埋了一颗雷，我特意在头文件里写死了警告：

```cpp
// 一旦 type 与实际存入的结构体不符，value<T>() 会静默返回默认构造值，
// 既不抛错也不告警 —— 厂商实现里 type 与 SetValue 的配对必须严格一致
```

**为什么标出来**：`QVariant::value<T>()` 类型对不上时**不报错**，给你一个默认构造的空对象。厂商实现里只要有一处 `SetValue` 塞的结构体和 `meta.type` 对不上，读到上层就是"参数值丢了但没任何提示"。这条契约没有编译器帮你查，只能靠实现层自觉 + 单元测试兜——**这是统一模型换来的便利，最贵的那张账单**。

枚举类型还多一份别扭，值得单独说：

```cpp
// 枚举同时保留符号名与整数值两套表示：写卡用 valueInt，UI 显示用 value
struct EnumParam : public ZCParam {
    QString value;
    QVector<QString> availableValue;
    int valueInt {};                  // SDK 只认这个
    QVector<int> availableInt;
};
```

**为什么这么写**：相机 SDK 的枚举参数只认整数编码，界面要显示的是文字。两套表示必须**由同一次 `readParam` 一起填出**，谁也不能只改其一。这不是冗余，是两侧各自的必需——曾经我以为只留整数、UI 自己映射就行，结果发现不同型号的编码表根本不一样，映射表也得跟着参数走。两套一起存是最朴素也最不容易错的做法。

## 统一错误码：那张表，和一处语义复用

所有返回 `uint32_t` 的方法，`0` 成功、非零是错误码。错误码统一定义在一张表里，全项目只有这一张：

```cpp
namespace CAMERAERROR {
#define ZYCLEAR_OK 0x0000
#define CONNECT_ERROR 0x0001
#define STARTGRAB_ERROR 0x0003
// ...
#define CAMERA_NOT_CONNECTED 0x000A
#define GETIAMGE_TIMEOUT 0x000E
}
```

**为什么这么写**：不用异常（跟 agent4cpp 那套 `Status` 同一个理由：工业软件的失败路径要可见、可跨线程传）。错误码集中成一张字典，任何厂商实现的返回码都必须落在这张表内，上层才能靠 `getErrorInfoEn(code)` 还原成可展示文案。**统一错误码的意义不是"有个编号"，是"上层能用同一段代码处理所有品牌的失败"**。

这张表有两个坑，第一版都没料到。

**坑一：这些是宏，不是常量。** 我一开始写的是 `namespace CAMERAERROR { const int ZYCLEAR_OK = 0; }`，觉得很干净——有命名空间，看着像个正经枚举。后来发现不行，改成了宏（`#define`）。原因很实在：这个文件被大量 `.cpp` 包含，用 `const int` 每个翻译单元各持一份，还得小心 ODR；而宏在预处理期展开，最省事。但宏的代价立刻显现：

```cpp
// 注释原文：预处理期没有命名空间概念，实际作用域是全局的
// 调用点必须写裸名，加 CAMERAERROR:: 前缀反而查不到
```

**上面那个 `namespace COMERAERROR { ... }` 包着宏是自欺欺人的**——宏不在乎外面的命名空间，`ZYCLEAR_OK` 在文件里就是全局裸名。我第一次写 `CAMERAERROR::ZYCLEAR_OK` 死活查不到，愣了一下才反应过来：宏在预处理阶段就替换完了，编译器根本没见过 `CAMERAERROR::` 这个东西。**看代码时"明明有命名空间"是一种错觉。**

**坑二，也是这一篇我最想讲的：`CAMERA_NOT_CONNECTED` 被挪作他用。**

这个错误码字面意思是"相机未连接"。但我在门面层写业务的时候，遇到另一种情况也要拒绝操作：**相机正在采集，此时不允许读写某些参数**。当时手上没有现成的"设备忙"错误码，建一个新的要改错误码表、改所有实现的映射，动静不小。我图省事，直接复用了 `CAMERA_NOT_CONNECTED`：

```cpp
// 门面：采集进行中拒绝参数写入
if (isGrabbing()) {
    return CAMERA_NOT_CONNECTED;   // ← 字面是"未连接"，实际是"正在采集"
}
```

当时想的是"反正都是拒绝操作，调用方看返回值非零就够了"。后来发现这个决定有真代价。

上层 UI 拿到 `CAMERA_NOT_CONNECTED`，第一反应是弹"相机未连接，请检查连接"。可相机明明连着，还在采着图，用户一脸懵：**提示文案和真实状态对不上**。而且 `getErrorInfoEn` 会老老实实返回 `"Camera not connected"`——字面和实际完全相反。

更麻烦的是排查：日志里出现一串 `CAMERA_NOT_CONNECTED`，我第一反应去查连接状态，查半天发现连接好好的，白花时间。**一个错误码的语义被借走之后，所有基于它字面含义的推断全部失效。**

我最后没建新码，而是在 `CameraError.h` 里把这处复用**明确注释出来**，并在门面调用点也标了：

```cpp
#define CAMERA_NOT_CONNECTED 0x000A   // 门面在"正在采集故拒绝操作"时也复用它，别只按字面理解
```

**为什么最后这么处理**：《CHANGELOG》记录过这件事——契约层的错误码表一旦被下游依赖，加新码的改动面比想象大得多。在现状下，把"这个码被借用"写进契约本身的注释，让每个人看到定义就知道它的完整语义，是成本最低的止损。但坦白说，正确做法是当初就该多加一个 `DEVICE_BUSY`。**我拿注释兜底，是因为建新码的窗口已经过了——这是顺序错了，不是判断错了。**

如果你今天问我，新项目里遇到这种情况怎么办：**错误码宁可多加一个，也别复用。** 多加一个码的成本是改一张表；复用语义的成本是此后每一个读日志的人都要踩一次。

## 缓冲队列为什么也放在契约层

`getImageLast` 只有一个方法，看起来很简单：给我最近一帧。但它的实现里藏着一整个缓冲队列，而这个队列的**接口**必须放在契约层。

```cpp
class CameraImageQueue {
public:
    uint32_t Put(const cv::Mat& m);      // 取帧回调线程调用
    uint32_t Take(cv::Mat& m);           // 上层调用
    void Recycle(const cv::Mat& m);      // 取完归还缓冲
private:
    std::mutex m_mutex;
    std::condition_variable m_condition;
    std::queue<cv::Mat> freeImageQueue;  // 空闲池
    std::queue<cv::Mat> workImageQueue;  // 待取帧
};
```

**为什么队列要放在契约层，而不是某个实现的私有成员**：

第一，**它是跨线程的**。`Put` 由 SDK 的回调线程调，`Take` 由上层调，`Recycle` 谁取谁还。线程模型是契约的一部分——每个实现都要接受"回调线程 Put、上层 Take/Recycle"这套规矩，队列接口不写在契约层，各实现就会各写一套线程约定，上层没法统一。

第二，**上层要能直接摸到它**。看基类那个非虚方法：

```cpp
virtual CameraImageQueue& ImageQueue() { return m_imageQueue; }
```

**为什么这么写**：基类内置一个 `m_imageQueue`，通过 `ImageQueue()` 暴露引用。这样队列的线程安全实现只写一遍，所有厂商实现自动共享；上层拿到的也是同一个 `Take` 接口，不用管底下是海康还是虚拟相机。**资源共享的复杂度被契约层一次性收口。**

第三，**队列的接口比它的实现更重要**。`CameraImageQueue.h` 里两个宏：

```cpp
#define TIME_OUT_MS 200        // Take 的等待上限
#define ImageQueueSize 10      // 缓冲池大小
```

**为什么这么定**：`TIME_OUT_MS` 同时决定了两件事——取帧等待上限，和**停止采集的最坏响应延迟**。`Take` 阻塞最多 200ms 就返回 `GETIAMGE_TIMEOUT`，所以停采时最多等这么久就能退出。这两个数写进契约层的头文件，等于告诉所有人：整个系统的实时性预期是 200ms 级别。改动它们是要全局评估的，不是某个实现的私事。

队列实现的细节（保新弃旧、稳态零分配、缓冲循环）留到图像链路那一篇讲，这里只立契约：**队列是契约的一部分，因为它规定了所有人怎么并发地拿图。**

## 契约定错的代价

契约层最贵的一课，是**它定晚了、或者定漏了**。

17 个方法里，每一个都是"签进合同"的条款。改动任何一个，等于改合同：

| 改动 | 波及范围 |
|---|---|
| 加一个纯虚方法 | 海康、虚拟相机、所有测试替身，全部立刻编译失败，当场补全 |
| 改一个方法签名 | 同上，加上所有调用点的适配 |
| 改一个错误码语义 | 错误码表 + 所有实现的映射 + 上层的处理分支 + 文案表 |
| 改 `ZCCameraParam` 的 type 语义 | 全部厂商实现里 type/SetValue 的配对、JSON Schema、面板控件分派 |

**为什么代价这么大**：因为契约是**被所有层依赖的**。门面依赖它、面板依赖它、实现层依赖它，契约一动，四面受力。这也是为什么上一篇的 grep 约束那么重要——契约层不认识任何具体实现，才能保证改契约时不牵出厂商代码；反过来，只要契约层干净，改契约就是"改一处、所有实现编译期同步暴露"。

我踩过的真实例子是 `m_cameraParams`：

```cpp
protected:
    QVector<CameraParam> m_cameraParams;
    // 预留的接口层参数缓存，当前各厂商实现各自维护静态参数表，此处未被使用
```

**为什么留在这里**：这是我一开始设计契约时的想法——"要不要在接口层缓存一份参数表，省得每个实现各存各的"。写了个字段放着，结果实现时发现每个厂商的静态参数表结构差异太大，统一缓存反而不如各自维护，于是这个字段成了死代码。我没删，留了注释说明它的来历。

**这笔学费的教训是：契约层的每个字段都该有明确职责，规划性字段是负债。** 一个没人用的成员挂在基类上，每个读代码的人都要停下来想"这个是干嘛的"。要么用起来，要么删掉——**"预留"在契约层是坏味道**，因为它让契约的形状看起来比实际能力大。

不过也有反过来的时候：`isConnect` / `isGrabbing` 两个状态查询，我原本觉得可有可无（上层自己记状态不行吗），后来发现**必须由设备回答**。上层记的状态是"我以为的"，SDK 里的状态才是"实际的"，断线、设备被抢占这类情况上层根本不知道。这两个方法不是冗余，是**把"真实状态"的话语权交还给设备**。契约里哪些看似可省、哪些其实必须，只有写过一轮实现才知道。

## 我踩过的坑

**以为 `CAMERAERROR::` 能限定宏的作用域。** 见上面第五节。`namespace` 包着宏是无效的，宏在预处理期展开，`ZYCLEAR_OK` 就是全局裸名。我写 `CAMERAERROR::ZYCLEAR_OK` 编译报"找不到标识符"，盯着那个 `namespace` 看了很久才想通——**预处理阶段根本不存在 C++ 的作用域**。

**复用了 `CAMERA_NOT_CONNECTED` 表示"正在采集"。** 最贵的那个坑。省了建新码的功夫，换来提示文案长期错位、日志排查白费时间。现在改成在定义处加注释兜底，但正确做法是当初多加一个码。**错误码复用一次的利息，比建新码的本金高。**

**`getErrorInfoEn` 写成 `static` 放在头文件里。** 这不是我最初的写法，最初是普通函数，一放进头文件就被多个 TU 包含、链接期重复定义。改成 `static` 后每个 TU 各持一份副本——不重复定义了，但**代价是改了这里只对当前 TU 生效，跨 TU 调试时可能被旧副本误导**。这个取舍我写进了注释。更正规的做法是拆 .h/.cpp，但错误码表要能被实现层随处包含，做成 header-only 最方便。**便利和正确之间，我这次选了便利，并把这个代价写进注释。**

**`creatStream` 拼写少个 `e`，定型后没法改。** 沿袭自厂商 SDK 的拼写。发现时已经有两个实现重写了它，改名意味着所有实现 + 调用点一起动。**契约定型后的任何改名都是全体补丁**，包括拼写错误。教训是契约文件写之前多读两遍——**定契约的时候不觉得，定完之后每个字都贵。**

**`m_cameraParams` 成了没人用的死字段。** 规划性设计，结果实现时发现不适用。它挂在基类上，每个读者都要停下来想它干嘛。**契约层的"预留"是负债**，要么用，要么删。

**差点漏掉 `isConnect` / `isGrabbing`。** 一度觉得上层自己记状态就够了，省两个方法。后来意识到上层记的是"我以为的状态"，设备被抢占、意外断线时上层毫不知情，界面会显示"已连接"但根本连不上。**状态的话语权必须在设备手上**，这两个方法不能省。

**`CameraParam` 的 type 与值不匹配会静默失败。** 这条不是踩出来的，是我在设计时预判到了、写进注释的——`QVariant::value<T>()` 类型对不上不报错，返回默认值。契约层要从源头承认这个弱点，让实现层知道这里必须严格配对、必须靠测试兜。**有些契约的正确性编译器管不了，只能靠契约自己把风险写在明面上。**

**以为 17 个方法重、图像只 1 个是设计失衡。** 数完第一反应是"图像域怎么这么少"，一度想把 `getImageLast` 拆成"取一帧 / 取多帧 / 取最新帧"三个。想清楚才明白：**契约要收的是"能力边界"，不是"使用姿势"**。取多帧是上层的循环，取新帧是队列的丢弃策略，这些都不该塞进契约。契约里图像只需要一个动作——拿最近一帧——剩下的交给队列。**方法是分母，不是成绩。**

## 结尾

契约层到这里立完了：17 个方法的边界、统一参数模型、统一错误码、共享的缓冲队列。它是一张谁都得签的合同，也是一面谁也改不动的墙。

但合同签了，得有人来履约。**谁来造海康的 `HikCamera`？谁来造不用真机的 `VirtualCamera`？新增一个品牌到底要改几处？** 下一篇讲工厂与适配器：那张注册表怎么把"创建器 + 枚举器"配成对，适配器怎么把几百个 SDK 接口压进这 17 个方法里，以及那个让帧被静默丢弃的 `RGB8_Packed` 漏认 bug。
