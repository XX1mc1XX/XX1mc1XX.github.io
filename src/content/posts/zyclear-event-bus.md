上一篇把图像链路从 SDK 回调一路走到了像素。那一篇里有一句话反复出现：「先接信号再启动」「停流之后不能再有帧投进来」「相机状态变了通知谁」。

这些都不是图像链路自己的事。采集线程为什么会知道相机被断开了？参数面板为什么会在相机连上的那一刻重新拉一遍参数？预览面板为什么不去问门面「现在开流了吗」，而是被动等着被通知？

**答案是：这些面板谁都不直接喊谁，它们都往一条总线上投递消息。** 这一篇写 `src/Listener.h` / `.cpp` 这两个加起来不到 140 行的文件——整个项目的通信骨架。

一句话先立住：**跨面板的联动不是「A 调用 B」，而是「A 广播一个事实，需要知道这件事的人自己来拿」。**

## 网状耦合的现场

先摆现场，还是跟前几篇同一种算法：先把最直接的写法写出来，再看它为什么会塌。

智澈界面上并排着四个面板：控制栏 `ControlWidget`（设备列表、连接、开关流）、参数面板 `ParamWidget`、预览面板 `ViewWidget`、还有 AI 侧栏。它们之间要联动的事实不少：

- 用户重枚举了设备 → 参数面板要清空、预览面板要清画面、控制栏自己要重建列表。
- 用户连上一台相机 → 参数面板要开始拉参数、控制栏要改按钮图标、预览面板要允许开流。
- 用户断开 → 以上全部反向，另外预览面板要停止采集、清空画面。
- 开流 / 停流 → 参数面板要禁掉一部分参数（有些参数运行中不可改）、预览面板要同步自己的开关外观。

如果让面板互相直接持有引用，最自然的写法是：控制栏构造时 `new ParamWidget(this)`、`new ViewWidget(this)`，然后每个状态变化点手动去调对方的方法：

```cpp
// 直接引用的写法（我没采用）
m_pParamWidget->onCameraConnected();
m_pViewWidget->onCameraConnected();
m_pAiPanel->onCameraConnected();
```

**问题不在这一处调用，在「这一处」有多少个兄弟。** 四个面板两两之间都可能有联动，连线数量按 `n × (n-1)` 长——四个面板就是 12 条有向连线。每加一个面板，不是加一条线，是加「它和已有每一个面板之间的线」。

而工业软件的面板是会长的：这一版四个，下一版可能要加相机标定面板、加日志面板、加产线编排面板。**更糟的是，连线不只是数量问题，是方向问题。** 谁持有谁的指针，谁就得先被构造；控制栏要能通知参数面板，就得先有参数面板——那参数面板如果反过来也想通知控制栏（比如它改了个参数、想让控制栏状态栏更新一下），就形成循环持有。

我最早一版真的踩过这个：`ControlWidget` 持有 `ParamWidget` 的指针，`ParamWidget` 又持有 `CameraContext` 和一张「当前相机」的引用，后来想让 `ParamWidget` 在参数下发成功后让控制栏刷新一下状态栏——**于是想让 `ParamWidget` 反向持有 `ControlWidget`**。两个类互相知道对方，构造顺序、析构顺序、谁先谁后，全变成了要小心推理的事。

**结论下得很干脆：面板之间不该有直接引用，一条都不要。** 需要联动的地方，改成「投递一个语义事件，谁关心谁订阅」——这就是事件总线。四个面板的事，从 n² 条有向连线，收成「每个面板向一条总线注册 + 总线向下投递」。

## 六个语义事件

总线的事件是六个，在 `Listener.h` 里用一个枚举定义：

```cpp
enum MESSAGE {
    CAMERA_ENUMRTION   = 0x00000001,
    CAMERA_CONNECT     = 0x00000002,
    CAMERA_DISCONNECT  = 0x00000004,
    CAMERA_STARTGRAB   = 0x00000008,
    CAMERA_STOPTGRAB   = 0x00000010,
    CAMERA_CAMERASWICH = 0x00000020
};
```

六个事件按「相机生命周期」一路排下来：**枚举、连接、断开、开始采集、停止采集、切换相机**。它们不是「哪个按钮被点了」，而是「系统里发生了什么事实」。这个区别很重要——

我刻意没有定义「控制栏请求刷新参数」这种事件。因为那是**动作**，属于某个面板的私有意图。总线传的是**状态变化的事实**，「连接上了」是事实，「参数面板该刷新了」是动作、是订阅方自己从事实里推出来的。**把动作塞进总线，总线就变成了一个隐式的函数调用表，又绕回直接引用了。**

这里要专门说那个拼写：`CAMERA_ENUMRTION`、`CAMERA_STOPTGRAB`、`CAMERA_CAMERASWICH`——这三个词都是拼错的，正确拼写应该是 `ENUMERATION`、`STOPGRAB`、`CAMERASWITCH`。我认出它们了，但没改。原因很朴素：**这六个常量被四个面板的注册语句引用着，改一个名字要动四处、还可能漏掉散在注释里的引用，收益只是「好看」，风险是「漏改一处编译失败」。** 当时正处在给全项目补注释的阶段，我给自己的原则是「这一轮只碰注释和确凿的缺陷，不顺手改名」。于是它们的拼写就留在那儿了。**这不是正确的决定，是一个权衡过的止损决定**——我把它写在这里，因为我不想让后来读代码的人以为这是随手打错的。

## 位掩码：订阅者怎么说「我关心 A 和 C」

六个事件各占一个独立的二进制位，这是整个设计的基石。`Listener.h` 开头那句注释把它写死了：

```cpp
// 事件位掩码。六个常量必须各占一个独立的二进制位且互不重叠 ——
// 订阅侧靠按位与把组合值拆成一个个事件位入表，
// 所以新增事件时只能往后取更大的 2 的幂，不能复用已占用的位。
```

**为什么是 2 的幂、为什么不能复用已占用的位**：因为订阅方是用位掩码表达「我关心哪几个事件」的。看参数面板的注册语句：

```cpp
ListenerManger::Instance()->registerMessage(MESSAGE::CAMERA_CONNECT
        | MESSAGE::CAMERA_DISCONNECT
        | MESSAGE::CAMERA_ENUMRTION
        | MESSAGE::CAMERA_STARTGRAB
        | MESSAGE::CAMERA_STOPTGRAB
        | MESSAGE::CAMERA_CAMERASWICH,
    this);
```

一行 `|`，把关心的六件事一次说完。这个表达力就是位掩码的全部好处——**如果事件不是 2 的幂，`A | C` 就可能等于 `B`，订阅「A 和 C」会被误解成订阅「B」。** 复用位、或者取个 `0x00000003` 这样非 2 的幂的值，两个事件的按位或就会撞进另一个事件的编码里，这就是测试里那条 `eventBitsAreDistinctAndSingle` 要钉住的东西。

订阅进来的组合值，在 `registerMessage` 里被按位与**逐位拆开**，每一位单独入表：

```cpp
auto Register = [&](int singleMessage) -> void {
    mmap::iterator iter = m_messageToLister.find(singleMessage);
    if (iter == m_messageToLister.end()) {
        QVector<Listener*> listeners;
        listeners.push_back(listener);
        m_messageToLister[singleMessage] = listeners;
    } else {
        iter.value().push_back(listener);
    }
};

if ((message & MESSAGE::CAMERA_CONNECT) == MESSAGE::CAMERA_CONNECT) {
    Register(MESSAGE::CAMERA_CONNECT);
}
// ……其余五位各一段
```

于是**表里的键永远是单个事件位**，值是这个事件的订阅者列表。投递时一次只查一个键、只回调订阅了这个位的人——**订阅者拿到的永远是单个事件位，不需要在自己的 `RespondMessage` 里再过滤一次。** 这个口径统一是刻意的，`Listener.h` 里写着：「传进来的 message 保证是『单个』事件位，不会是组合值，实现里直接做等值比较即可，不需要再按位解析。」

便利说完了，代价也得说。位掩码这套有一个隐含的维护负担：**订阅端和解构端必须对「32 位能放几个事件」保持共识。** 六个事件用了低 6 位，还剩 26 位——暂时够用。但位掩码的表达力上限是 32 个事件（如果用 `int`），而且**枚举的取值一旦定了就不能回收**：哪怕某个事件以后废弃了，它占的那一位也不能让给新事件，否则旧代码里一个残留的 `|` 就会把新事件带上。**这是「一次分配、永久占用」的代价，跟位运算省下的那点表达力相比，它更像是一种负债。**

## 两个真实的坑

![注册按位拆开，通知却整键查找](/images/zyclear/位掩码与那个坑.svg)

### 坑一：漏拆一个事件位

`registerMessage` 末尾那句注释，是我在补注释时盯着看出来的：

```cpp
// 下面必须覆盖 MESSAGE 枚举里的每一位。漏掉一位不会有任何报错，
// 订阅它的调用方只是永远收不到该事件（CAMERA_CAMERASWICH 曾漏在这里）。
// 新增事件时，这里要跟着枚举同步补齐。
```

修复前，这一串 `if` 里没有 `CAMERA_CAMERASWICH` 那一段。后果分两层：

**第一层**：`ControlWidget` 和 `ParamWidget` 都用 `|` 把六个事件全订上了，其中 `CAMERA_CAMERASWICH` 那一位在 `registerMessage` 里找不到对应分支，**直接被忽略、表里没有这一位对应的键**。它们以为自己订了六个，实际只订上五个。

**第二层，这才是可怕的**：这不是漏订阅那么简单。当有人真的 `notify(MESSAGE::CAMERA_CAMERASWICH)` 时（比如用户从列表里切了另一台相机），`notify` 拿这个键去表里查——**查不到，走 `else` 分支，什么也不做。** 而那个 `else` 分支的注释写着：

```cpp
} else {
    // 无人订阅是正常情况（比如某个面板没装配），不是异常，
    // 所以这里连日志都不打，静默吞掉。
}
```

**「无人订阅」和「订阅了但注册时漏了一位」在这条代码路径上长得一模一样——都是查不到键、都不报错。** 于是症状是：用户切了相机，参数面板该刷新、预览面板该清画面，结果是**什么都没发生，界面纹丝不动，日志里干干净净**。你不知道是没人订阅、还是订阅坏了。

我在 CHANGELOG 里写过这条：「`registerMessage` 没有 `CAMERA_CAMERASWICH` 分支，订阅它的调用方不报错、也永远收不到事件。」**它的可怕之处不是 bug 本身，是调试路径为负**——一个会报错的 bug，错误信息本身就是线索；这个 bug 唯一的线索是「什么都没发生」，而「什么都不发生」在 UI 上有一百种正常解释。

测试文件里那条 `everyEventBitCanBeSubscribed` 就是为它钉的，注释明说「现已补齐，这条用例钉住『枚举里的六个位都能订上』」。

### 坑二：组合值被静默丢弃

第二个坑更根本，因为它直指 `notify` 的查找口径。看 `Listener.cpp`：

```cpp
void ListenerManger::notify(int message)
{
    // 精确匹配而不是按位与：这里把 message 当整键查表。
    // 于是「一次 notify 只传单个事件位」成了调用方的硬性契约 ——
    // 传组合值（如 CONNECT|DISCONNECT）在表里找不到对应键，
    // 事件被静默丢弃，且不会有任何报错。
    mmap::iterator iter = m_messageToLister.find(message);
    // ... 找不到就走那个空的 else
}
```

**注意这个不对称**：`registerMessage` 入参是位掩码，会被**按位拆开**；而 `notify` 入参是**整键精确查找**，不做任何拆解。同一个类型 `int`，一个当掩码用、一个当键用——**这就是这个坑的根源。**

于是「一次 notify 只传单个事件位」变成了一条口头契约。而它极易被违反，因为**`registerMessage` 已经教会了使用者「事件可以按位或」**。一个刚读完 `registerMessage` 的人，很自然会写出：

```cpp
// 想一次通知两个事件 —— 但表里没有这个组合键
ListenerManger::Instance()->notify(MESSAGE::CAMERA_CONNECT
                                   | MESSAGE::CAMERA_DISCONNECT);
```

这一行**编译通过、语义看起来天经地义、运行时不报错、两个事件一个都不会被投递。** 表里只有 `0x02` 和 `0x04` 两个键，没有 `0x06` 这个键。

测试 `combinedNotifyValueIsSilentlyDropped` 把这个行为固化了：

```cpp
void combinedNotifyValueIsSilentlyDropped()
{
    ListenerManger* bus = ListenerManger::Instance();
    const int combined = MESSAGE::CAMERA_CONNECT | MESSAGE::CAMERA_DISCONNECT;
    bus->notify(combined);

    QCOMPARE(g_multi.count, 0);
    QCOMPARE(g_connectOnly.count, 0);
}
```

它验证的是**这个坑确实存在，而且目前就是既定行为**——两个订阅者计数都为 0，说明组合值被完整吞掉。CHANGELOG 里也说清楚了：「组合值传给 `notify` 会被静默丢弃……这些不是期望行为，注释里已写明缘由，修正时对应用例会失败并提示更新。」

我为什么当时没顺手修掉？两个原因。**其一**，修法本身有分歧：是让 `notify` 也走按位拆分（那一次 notify 就变成 N 次投递，语义更宽但更容易被滥用），还是加一层断言把「传组合值」变成显式的编程错误（那要在表里记住一个「已注册位掩码」来判非法）。两种都会改变总线的语义边界，不是补一行能了结的。**其二**，这个坑当前**没有任何真实调用点踩到**——所有 `notify` 调用传的都是单个枚举值（我在 `ControlWidget`、`ViewWidget` 里数过，全是 `notify(MESSAGE::XXX)` 单值）。**它是「被教会了错误用法、但暂时没人用」的状态，我选择先把它写成注释和测试固定下来，而不是急着改语义。**

## 总线自己的契约

`Listener.h` 的注释写得比我这几段总结更利落，我原样转述它的六条契约。

**一、进程内唯一。** `ListenerManger::Instance()` 是那个全局单例。`Listener.cpp` 里它甚至在静态初始化期就建好了对象：

```cpp
ListenerManger* ListenerManger::m_pListenerManger = new ListenerManger();

ListenerManger* ListenerManger::Instance()
{
    return m_pListenerManger;
}
```

那句注释解释了为什么这么写：「静态初始化期就建好，`Instance()` 因而永远返回有效指针，不需要懒加载、也不需要为空指针留分支。代价是这块内存到进程结束都不回收（也不需要回收）——**好处是任何静态对象的析构里触发 `notify` 都还能拿到可用总线。**」这是个漂亮的取舍：故意泄漏一个几十字节的对象，换来「生命周期没有灰色地带」。测试里的 `instanceIsStable` 两次调用返回同一个指针，钉的就是这条。

**二、不持有订阅者所有权，也没有反注册接口。** 头文件里写着：

```cpp
// 进程内唯一的全局总线。它不持有订阅者的所有权，也没有反注册接口 ——
// 一旦注册，Listener* 就永久留在表里，因此订阅者必须活得比所有后续 notify 更久，
// 否则 notify 会在已析构的对象上调虚函数。
```

表的 value 是 `Listener*` 裸指针。**没有 `unregisterMessage` 这个方法**——不是忘了写，是刻意的。代价是：订阅者一旦注册，就没有退场机制，必须活到进程结束（或者至少活到「再也不会有人 notify」）。参数面板的注释把这个约束写在了自己的构造里：「本对象必须先于它析构，否则后续通知会打到野指针。」所以四个面板的实际生命周期安排是——**它们都由 `MainWindow` 持有、活到窗口关闭，等于活到进程结束**，注册了就不撤。

**三、同一对象重复订阅同一事件会被追加多次。** 因为 `Register` 的逻辑就是「查不到就新建列表、查到了就 `push_back`」，没有任何去重。头文件写着：「同一对象重复订阅同一事件会被追加进列表多次（没有去重），效果是每次 notify 它都被调用多次。」测试 `duplicateRegistrationCausesDuplicateCallbacks` 把一个对象订了两次 `CAMERA_STOPTGRAB`，断言回调计数是 2。**常规代码不会重复注册同名事件，但一旦有人把注册语句写在了会被反复执行的路径上（比如某个 `refresh()` 里），症状就是同一个回调被调 N 次——同样不报错。**

**四、走普通虚函数，`RespondMessage` 在 `notify()` 的调用栈上同步执行。** `Listener` 故意不继承 `QObject`：

```cpp
// 订阅者接口。故意不继承 QObject：总线走的是普通虚函数调用，
// 不经过信号槽，因此 RespondMessage 是在 notify() 的调用栈上同步执行的，
// 也正因如此它必须跑在与 notify 相同的线程（实际上只有主线程）。
```

**同步执行的后果，比「性能好」这点重要得多**：`notify` 里那个 `while` 循环，是**等每个 `RespondMessage` 跑完才处理下一个订阅者、才返回**。所以控制栏 `notify(CAMERA_ENUMRTION)` 那一行，会在它自己的函数体内**同步递归地**把参数面板、预览面板的回调全跑一遍，然后才继续往下走。测试注释里那句「本类自己也订阅了枚举事件，所以这一行会同步回调进自己的 RespondMessage」，`ControlWidget.cpp` 第 131 行就是这么写的——**投递者在自己的调用栈上被自己的回调重入。**

这也直接推出一条线程约束：**总线只在主线程用。** 因为 `RespondMessage` 里会碰 Qt 控件、碰门面的映射表（那张表是「无锁，约定只在 GUI 线程访问」的），如果哪个工作线程也去 `notify`，回调就会在工作线程上跑 UI 代码。当前项目里所有 `notify` 都由 UI 交互触发，天然在主线程。**这条约束靠约定维持，代码里没有 `Q_ASSERT(thread() == mainThread)` 之类的护栏。**

**五、六个事件各占独立位、不得复用、新增只能往后取更大的 2 的幂。** 见上一节，不重复。

**六、禁止在回调里注册新订阅。** `Listener.h` 里 `RespondMessage` 上方写着「禁止在回调里注册新订阅」。原因在 `Listener.cpp` 的 `notify` 注释里：`notify` 遍历的是 `QVector<Listener*>` 的迭代器，**边遍历边投递**；如果某个 `RespondMessage` 里又 `registerMessage` 给它正在遍历的这个事件，`push_back` 可能触发 `QVector` 重新分配、让当前迭代器失效。**单线程约定「不在回调里注册」，就绕开了重入扩容这个坑**，不用为它上锁或做迭代器快照。

## 为什么不用 Qt 信号槽

这套东西是手写的，而 Qt 明明自带了信号槽——这是个必须正面回答的问题，不然就是重造轮子。

信号槽强在哪里，我很清楚：**接收方对象属于哪个线程，`connect` 时会自动判断，跨线程就自动走队列连接**，参数被拷进事件、投到目标线程的事件循环里执行。上一篇图像链路里 `sigUpdateImage` 从采集线程到 UI 线程，就是靠这个机制白拿的线程安全。**而这恰恰是事件总线不需要的东西。**

事件总线的所有投递都发生在主线程——控制栏 `notify` 时它就在主线程，参数面板、预览面板也都在主线程，**从头到尾没有一次跨线程投递。** 既然如此，信号槽那套「自动跨线程 + 参数打包 + 元对象系统查找」的实现开销，对我这里是纯成本：**每一次投递都要走 `QMetaObject` 的那套查找和参数类型检查，换来一个我用不上的能力。**

更关键的是**订阅方向**。信号槽模型的耦合方向是「发送方持有接收方的信号签名」——`connect(m_pImageProcess, &AcquireImageProcess::sigUpdateImage, ...)` 里，发送方必须知道接收方的**具体类型**。而事件总线的诉求恰恰是**发送方不知道谁在听**：控制栏发 `CAMERA_CONNECT` 的时候，它完全不知道参数面板、预览面板、AI 侧栏会订阅它——**它连这些面板的类型都不需要 `#include`。** 这正是我一开始要解决的那个「面板之间零直接引用」。

取舍说清楚就是一句话：**信号槽解决的是「两个已知对象之间怎么安全传递」，事件总线解决的是「一个对象广播、N 个未知对象按需订阅」。** 前者要线程安全和类型安全，代价是双方互相知道；后者要解耦和广播，代价是——**我上面写的整整六条契约，全部得靠人遵守，编译器一条都帮不了忙。** 没有反注册、不持有所有权、必须活得更久、不能在回调里注册、只能主线程用……这些如果用信号槽，Qt 的对象树和连接管理会替我兜掉一部分；手工总线则把它们全变成了注释里的字。

**这就是手工总线的真正代价：它把 Qt 帮我兜的安全网，换成了我必须自己记住的约定。** 我认为这笔账在「四个面板、全在主线程」的规模下是划算的——**总线小到一口气读完，约定就写在头文件里，谁都看得见。** 但如果哪天真的需要工作线程参与广播，我会毫不犹豫地把某些通道换成信号槽，而不是给这个手写总线加锁。

## 配套的错误码体系

总线传的是「状态变化」，状态变化里有一类是失败。失败怎么收口，靠的是同一套哲学的另一半：一张全项目统一的错误码表。

`CameraError.h` 定义了 **15 个失败码 + 1 个成功码**（0 个成功、15 个非零失败共 16 个常量）：

```cpp
#define ZYCLEAR_OK 0x0000                                   // 成功
#define CONNECT_ERROR 0X0001
#define DISCONNECT_ERROR 0X0002
#define STARTGRAB_ERROR 0x0003
#define STOPGRAB_ERROR 0x0004
#define NOCAMERA_ERROR 0x0005
#define INVALID_INPUT 0x0006
#define INVALID_CAMERA_HANDLE 0x0007
#define WRITE_PARAM_FAILED 0x0008
#define READ_PARAM_FAILED 0x0009
#define CAMERA_NOT_CONNECTED 0x000A
#define CAMERA_ACQUIRE_FAILED 0x000B
#define CAMERA_CONFIG_SAVE_FAILED 0x000C
#define CAMERA_CONFIG_LOAD_FAILED 0x000D
#define GETIAMGE_TIMEOUT 0x000E
#define DEVICE_NOT_ACCESSIBLE 0x000F
```

它的设计口径跟总线一脉相承：**0 为成功、非 0 一律失败**，各厂商适配器返回的码都必须落在这一张表内，上层靠 `getErrorInfoEn` 把码还原成可展示的文案（`"Camera Connect failed"` 之类）。`getErrorInfoEn` 是个 `static` 函数放在头文件里——注释解释了这份取舍：「`static` 给出内部链接，每个翻译单元各持一份副本，故放头文件不会重复定义；代价是改动只对当前 TU 生效，跨 TU 调试时留意别被旧副本误导。」

失败往上层走的时候是**两级触达**：不致命的错误收进状态栏一行文字，需要用户确认的（连接失败、取图超时）再走模态弹窗。`CameraError.h` 里还留了几条语义提醒，比如 `CAMERA_NOT_CONNECTED` 后面注了「门面在『正在采集故拒绝操作』时也复用它，别只按字面理解」——这个语义复用我在第 2 篇和第 4 篇都讲过，这里就带一句，不再展开。

**总线负责「发生了什么」，错误码负责「这件事是不是失败了」，两者都遵守同一条纪律：把变化收敛到一个固定出口，上层不需要知道底下是谁干的。** 面板不判断「是谁连失败了吗」，它只判断「事件来了、顺带带回来的错误信息是不是非空」。

## 我踩过的坑

**坑一：以为 `registerMessage` 里那一串 `if` 是「防御性检查」。**

我最早读 `registerMessage` 的时候，看到六个 `if ((message & MESSAGE::XXX) == MESSAGE::XXX)`，第一反应是「哦，这是在过滤非法输入」——**完全没意识到这六个 `if` 就是「订阅」这个动作的全部实现。** 它不是在检查什么，它是在把组合值拆成一个个键写进表里。漏掉一个 `if`，等于那个事件**根本没被写进表**。所以「漏拆一位」不是少了个保险，是少了整个订阅。

这个认知错位让我一开始没觉得 `CAMERA_CAMERASWICH` 漏掉有什么大不了——我想的是「反正入参不合法会被过滤掉」，而事实是**那位被静默地筛掉了，连个警告都没有**。教训：**看到一串同构的 `if`，先问它是「校验」还是「分发」——分发的 `if` 少一个，就是功能少一块，不是多一层保险。**

**坑二：把 `notify` 和 `registerMessage` 的参数当成同一个东西。**

这是坑二那个组合值 bug 的认知根源。`registerMessage(MESSAGE::A | MESSAGE::B, ...)` 我写得很顺手，于是**默认了「`notify` 也能接受组合值」**——同一个 `int`，前脚刚教会我用 `|`，后脚我就以为它也认 `|`。直到补注释时逐字读 `notify`，看到那句 `find(message)` 才反应过来：**这里是精确查表，不是按位拆解。**

**两个函数、同一个形参类型 `int`、语义却一个当掩码一个当键**——这种「签名一样、口径不一样」的接口最阴。现在我给 `notify` 想传值时会强迫自己问一句：「这是单个位还是组合？查表键得是单个位。」头文件里 `notify` 的契约我后来也补了注释，就是为了给下一个读它的人留一句话。

**坑三：以为「事件来了、回调就会响」，忽略了「谁先构造」。**

有一版我把 `ParamWidget` 的注册放晚了一点——结果它构造完成、还没执行注册那几行时，控制栏已经因为初始化流程 `notify` 了一轮。**那一轮事件发出去的时候，参数面板还不在表里，它错过了。** 总线不重放、不缓存，错过了就是错过了，界面停在初始态。

这和图像链路里的「先接信号再启动采集」是同一个道理——**事件的订阅必须发生在「可能触发它的事情」之前。** 现在四个面板的注册都放在构造函数最早期，控制栏在 `setupUi` 之末才发第一轮 `notify`，靠构造顺序保证「订阅者先到、广播后发」。**这个顺序没有编译检查，写在 `ControlWidget.cpp` 第 129 行那句注释里——「广播必须放在列表重建之后：订阅方都以『列表已就绪』为前提，提前发会读到空列表。」**

**坑四：在回调里就想顺手注册点东西。**

我写过一版参数面板的 `RespondMessage(CAMERA_ENUMRTION)`——收到枚举事件后，它想根据新列表再订一个开关流事件。**幸好动手前重读了 `notify` 的注释**，上面明说「禁止在回调里注册新订阅」，原因是遍历中 `QVector` 可能扩容导致迭代器失效。**如果当时写了，它不一定立刻崩——可能在订阅者少的时候一直正常，直到某个面板列表变大、触发了一次扩容才偶发崩溃。** 现在这类需求一律改成「在构造时注册全部可能用到的事件，回调里只做分支」。**订阅是静态的，回调是动态的**——这条界线划清楚，重入扩容的问题就不存在。

**坑五：想过把六个拼错的枚举「顺手改对」。**

`ENUMRTION`、`STOPTGRAB`、`CAMERASWICH` 这三个拼写，每次读到都想改。**我第一次真的搜了一遍如果改名字要动多少处——注册语句、`notify` 调用、注释、测试，散在五六个文件里。** 那一刻我想起第 4 篇里「顺手多做一点、最后变成两层耦合」的教训：**在一个「只做注释和确凿修复」的阶段里顺手改名，是典型的范围蔓延。** 收益是美观，风险是漏改一处编译失败或更糟——注释里引用了旧名字、代码里用了新名字，两边对不上。**我选择把它写进文章作为一条「权衡过的止损」，而不是假装它不存在。** 承认「这是权衡」比「偷偷改掉再说是优化」诚实得多。

**坑六：把总线当成「有了它就一定解耦」。**

刚建成总线那会儿我一度觉得「面板之间零引用了，耦合问题解决了」。**后来发现总线只是把「直接引用」换成了「隐式契约」。** 参数面板不再 `#include` 控制栏，但它**必须知道 `CAMERA_ENUMRTION` 事件发出来时列表已经就绪**——这仍是一条耦合，只是从「代码依赖」变成了「时序约定」，从类型系统里搬到了注释里。

**总线降低的是编译期耦合和构造顺序耦合，代价是把一部分耦合转移成了运行时的时序契约，而时序契约是不编译、不报错的。** 所以如果重来，我会在头文件里把每个事件的**前置条件**也写进注释——「CAMERA_ENUMRTION 发出时列表已重建完毕」这种。现在这些约束散在各面板的注册注释里，读一个面板看不全整条时序。

## 结尾

到这里，全项目的通信骨架就讲完了：**六个语义事件、按位掩码定向投递、进程内唯一的全局总线。** 四个面板谁都不直接引用谁，需要联动的都变成「订阅一个事实」。

回头看，这套设计真正的赌注是：**用一套能被一口气读完的约定，换取零编译期耦合。** 总线不到 140 行，六条契约全写在 `Listener.h` 里，代价是这六条里没有一条有编译检查——不持有所有权、没有反注册、不去重、同步执行且只在主线程、位不可复用、回调里禁止注册。**每一条都是「靠人记住」，而每一条我都用一条或者注释、或者测试，把它钉在了一个后来者会读到的地方。**

两个真实的坑也都是「静默」的——漏拆一位，订阅方永远收不到；组合值投递，事件被精确匹配吞掉。**它们不报错、不崩溃，唯一的症状是「什么都没发生」**，而「什么都没发生」是 UI 世界里最难排查的症状。这也是为什么这一篇值得把注释逐句转述出来：**在一个没有编译器护栏的设计里，注释就是护栏。**

下一篇讲**插件系统**。到这一篇为止，面板都是编译进主程序的——`ControlWidget`、`ParamWidget`、`ViewWidget` 各自实现 `Listener`、各自在构造时注册。但如果有人想写第五届面板、想让它不重新编译主程序就接进来呢？下一篇讲 `IPanel` 接口怎么定义、注册表怎么把面板收进来、动态库怎么在运行时装载，以及那个「插件接口只导出纯 C 符号」的约束到底在躲什么——**C++ 的 ABI 不稳定，一个 `std::string` 跨库边界就能让整个插件崩在加载的那一刻。**

面板之间已经能靠总线谈话了，接下来该让「还没被编译进来的面板」也能说话。
