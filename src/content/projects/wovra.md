## 这个项目解决什么问题

先看一个具体场景。让 AI 做一个要跑几小时的任务，比如「把这套后端从单体拆成三个服务」。前面四十分钟很顺：它读代码、列计划、改第一个模块。然后你回来问一句「进展怎么样」，得到的是**一整段对话历史**——你要自己从里面捞出「已经改完哪几个文件、卡在哪、为什么卡」。

真正的问题出现在更后面。上下文越堆越长，每一个小改动都要把前面所有无关历史一起带上；它第三次尝试的方案和第一次的失败记录混在同一段上下文里；你中途想引导一句，却发现没有合适的落点。

更麻烦的是失败。跑了三小时的操作挂了，**它不记得自己前面做过哪些尝试**——那些尝试还在上下文里，但已经淹没在几万 token 里了。

Wovra 要解决的就是这件事：**让 AI 的工作变得可管理、可观察、可引导、可恢复。**

**它不把 AI 智能体视为一段不断累积上下文的连续对话，而是把一个任务视为一个持久的工作空间**——拥有自己的状态、上下文、进度、历史、智能体、报告和评估。

要注意目标不是让 AI 更聪明。目标是让它的工作**能被人接住**：任务跑到一半换人接手、失败之后回到某个已知良好的状态、中途插入一句引导——这些在当前「一切都在对话历史里」的形态下都做不到。

## 为什么需要 Wovra

上面那个场景背后，是这一类问题：

- 随着对话和工具调用的累积，上下文持续增长
- 一个微小的改动，可能需要携带大量无关的历史信息
- 失败的尝试和中间结果混杂在当前活跃的上下文中
- 多个智能体可能重复携带相同上下文，增加协调成本
- 人类常常无法追踪 AI 已经做了什么、还剩什么没做、为什么被阻塞
- 解释性对话和实际工作对话可能互相干扰
- 执行任务的 AI，不应当必然成为判定任务是否完成的最终权威

Wovra 探索的是另一种思路：**把任务本身与处理任务所用的对话分离开来。**

## 核心思想

### 1. 持久的工作状态

任务并不简单地等同于一段对话。Wovra 为工作维护一份持久的表示：

```
Task（任务）
├── Goal（目标）
├── Requirements（需求）
├── Acceptance Criteria（验收标准）
├── Current State（当前状态）
├── Active Context（活跃上下文）
├── Report（报告）
├── History（历史）
├── Agents（智能体）
└── Evaluation（评估）
```

AI 可以从当前状态出发继续工作，而不必携带此前每一次交互的完整历史。

### 2. 上下文生命周期

并非所有信息都值得留在活跃上下文中。Wovra 把信息分成两层：

```
Active Context（活跃上下文）
      │
      ├── 相关信息
      ├── 当前决策
      ├── 当前状态
      └── 近期历史
               │
               ▼
        Archived History（归档历史）
      ├── 此前的尝试
      ├── 工具输出
      ├── 调试日志
      └── 详细对话
```

信息并不一定被删除，而是把不必要的细节**折叠成一种紧凑的表示**，需要时再取回。这样系统就不必反复为携带无关的历史付出代价。

### 3. 基于职责的智能体

Wovra 不认为智能体越多执行就越快。对于简单的任务，单个智能体可能更好。**只有当任务包含不同的职责或上下文时，多个智能体才变得有用。**

```
                     Task（任务）
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Agent A     Agent B     Agent C
        规划         编码         测试
          │           │           │
          └───────────┼───────────┘
                      ▼
                  Task State（任务状态）
```

每个智能体可以在聚焦的上下文中工作，而不是继承主任务的全部历史。因此隔离的目的主要是**职责分离 + 上下文隔离**，而不是简单的并行执行。

### 4. 人机对齐

人类不应该需要持续监督每一次工具调用，但应该能够在任何时刻了解工作的状态。所以 Wovra 用一份**持久报告**作为人类与 AI 之间的共享接口：

```
当前状态：
正在实现认证模块。

已完成：
- API 结构
- 数据库 Schema
- 登录端点

当前问题：
Token 过期后刷新偶尔失败。

已尝试：
- 复现了该问题
- 检查了中间件的注册顺序
- 怀疑是 refresh-token 校验的问题

下一步：
排查 Token 校验与过期处理逻辑。
```

这份报告紧凑地回答了几个问题：发生了什么？我们现在在哪里？还剩什么没做？什么在阻塞？接下来该做什么？

### 5. 工作与解释是两回事

人类可能会问「这个模块为什么这样实现」，或者「解释一下当前流水线是怎么工作的」。这类对话**不一定需要成为任务工作上下文的一部分**。

只有真正改变实际工作的信息——新需求、新决策、新约束、新发现的事实——才应当被提升为持久的任务状态。这样探索性的对话就不会污染执行上下文。

### 6. 独立评估

一个智能体不应当是判定自己工作是否完成的唯一权威。Wovra 把两者分开：

```
Execution（执行）
    │
    ▼
Agent 产出结果
    │
    ▼
Evaluation（评估）
    ├── 接受
    ├── 需要修改
    └── 失败
```

验收标准可以独立于智能体自己的声称来评估，这让长时运行的自主工作更容易验证和恢复。

```
                Human（人类）
                    │ 需求 / 反馈
                    ▼
        ┌───────────────────────┐
        │         Wovra         │
        │  任务管理 · 上下文     │
        │  状态 · 报告          │
        │  归档 · 评估          │
        └───────────┬───────────┘
                    │ 智能体编排
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     Agent A     Agent B     Agent C
        └───────────┼───────────┘
                    ▼
            现有智能体运行时
                    │
         文件 / Shell / 工具
```

Wovra 专注于 AI 工作的**组织与生命周期**，而不是重新发明每一个底层能力。现有的智能体运行时和成熟的工具实现都可以作为它的底层。

## 代码结构

运行时按职责组织，每个模块只做一件事。

| 目录 | 装什么 |
|---|---|
| `agent/` | **Agent 运行时**，由四个 mixin 组装：运行循环与轮生命周期（core）、共享历史装配与 fork 基线（assembly）、水位闸门与分域（maintenance）、计划账本与提交守卫（ledger） |
| `tools/` | **内置工具箱**：文件读写改删移与检查点、Shell 与进程管理、后台任务注册表、网页检索与抓取（含 SSRF 防护、正文提取、结果缓存）、截图与看图、附件原生解析（docx/xlsx/pptx/pdf/csv）、协作式中断、安全护栏（路径防护、命令越界判定、确认门、禁写区、设备只读白名单）、权限守卫 |
| `cli/` | **终端入口**：参数解析与子命令分发、会话锁、系统提示词组装、流式轮次渲染、交互主循环 |
| `blocks/` | 零 LLM 的块结构（V4 下只用于文件生命周期账本）：轮 → 块、生命周期标签、块摘要、历史数据迁移 |
| 根级模块 | 持久任务树、文件生命周期账本、模型客户端（所有模型调用的唯一出口）、渠道商清单、运行参数登记表、`.env` 按行读写、token 估算、路径的鲁棒匹配、附件管理、观察快照、职责注册表、路由规则、分域经济判据、Web 服务 |

`webui/` 是人视图前端——纯静态页面，不需要前端构建工具链。

## V4 上下文模型

当前的上下文机制以**一份共享历史**为中心：

**取消重组。** 历史不再按域重切——所有 agent 读同一份共享历史：折过的轮变段落，近轮保持原文。

**每轮一段话。** 轮闭合时结算成一段话（问什么 → 干了什么 → 卡在哪 → 结论），追加进共享历史。分域前按水位攒批写，分域后每轮每 agent 各一段。

**分域 = 按活性文件画树。** 分不分由**代码判**（某条工作线装配体量 ≥ 水位，且活性文件按同轮共现能分成 ≥2 簇）；**模型只画结构树**。落地是增量演进：按名字匹配既有条目就地更新，新名字发新 id，不退休任何既有条目——树只长不改。

**首次激活才 fork。** 未激活的子 agent 共享公共上下文（零成本待命）；它第一轮真正干活时 fork——之后它看「自己未折的轮全量 + 别人的段落」（forked_at 基线）。

**四成线折叠与回落。** 公共线内容到 40% 水位 → 折叠：只保留最近 50 轮，更早的轮只留用户输入（要时展开）；已激活的子 agent 到水位 → 回落为「当前公共上下文 + 自己的职责」（重建基线，而不是自己折）。

**观测在材料变化边界重算。** 折档 / 分域 / 改名 / 回落都会改变「每个 agent 会看到多少」，在这些边界重算各 agent 的上下文占用数字。

对话页把一轮之内发生的事按时间铺开：用户原文、模型的思考与正文（Markdown 实时渲染）、每一次工具调用与结果（默认折叠，点开是原文）、每个 agent 各占一个消息块。

![对话页](/images/wovra/ui-conv.png)

顶栏六格是「这一刻的账」：Σ prompt / 缓存命中率 / LLM 调用 / 轮次 / 工具调用 / TTFT 均值。两处口径值得说明：**工具调用一步可以大于 1**（一步里并行调多个只读工具，也就顺带看出并行度）；**TTFT 均值只统计干活轮**——结算/分域那种一次读 20 万 token 的批量调用不计入，否则均值会被它们抬飞。六格在跑轮期间按步刷新，不必等这一轮结束。左边每个 agent 一条上下文占用条（当前/窗口 + 实测峰值）。

底部是维护进度条：每轮一段话的结算与分域分析跑在后台线程里，轮一闭合作业就结束了——没有它，那一两分钟页面是全黑的。结束时在这里给出结果，包括「被拒收 / 本次未分域」的原因。

**开放轮 + 续跑**：一轮只有产出最终回答才算闭合，被打断或步数用尽的轮会一直开着，新消息并入它——界面上明确标出来，并给一个「▶ 续跑」（等价于命令行 `/c`，不注入新消息）。

## 命令行与本地命令

| 命令 | 作用 |
|---|---|
| `wovra run "<目标>"` | 一次性跑完一个任务（退出前把结算/分域做完） |
| `wovra chat [id]` | 交互会话（输入历史 / 底栏状态 / 本地命令） |
| `wovra list` · `wovra report <id>` · `wovra maint <id>` | 列会话 · 人视图报告 · 维护账 |
| `wovra serve [--port N]` | 起 Web UI |
| `wovra delete <id>` | 删除会话（其本地数据一并删除） |
| `wovra views ["<域>"] [id]` | 域视图材料导出。V4 运行时已不按域重组，这是排查历史数据用的 |

会话内的本地命令（`/` 或 `\` 前缀，零模型成本）：`/c` 续跑最近一个开放轮、`/report` 报告、`/todo` 计划、`/maint` 维护账、`/bg` 后台任务、`/help`。

`Ctrl+C` 在输入行是退出、在轮运行中是中断本轮（轮保持开放，可续跑）。`approve`（敏感操作先问）/ `auto`（全放行，适合无人值守长跑）切换安全模式。

## 工具与安全能力

**输出默认全量。** 工具输出上限 200,000 字符（`WOVRA_OUTPUT_LIMIT`）；真超限时返回开头预览 + 原文体量 + 落盘路径，随时可以 `read_file` 取回——不丢文本。

**`tasks/` 是禁写区。** 会话数据是 Runtime 的真相来源，工具层对它拒写放读，而且**不可授权**（越界访问可以授权一次，禁写区不行）。

**网页检索走专业 API。** Tavily / Serper / Exa / Bocha / SerpAPI / Firecrawl / TinyFish 填哪几家都行。每次检索随机挑一家先试，失败就换下一家——把调用摊到各家免费额度上，而不是只烧第一家。一家都没配或全部失败时，退回单一本地抓取通道（DDG lite，10 秒预算），并在结果里标注「本地兜底、没有相关性保证」——因为一句光秃秃的「未找到相关结果」会被模型读成「网上没有这个东西」。

**按需的云浏览器。** `web_automate(url, goal)` 把一句自然语言目标交给云浏览器，执行轨迹进账本、结果作为文本返回。它对付的是「必须真交互才拿得到东西」的页面（登录墙、筛选、SPA 渲染的数据）。

**附件原生解析。** `read_file` 自动识别 `.csv` / `.tsv`（带 GBK 回退，并把实际编码写在表头）、`.docx` / `.xlsx` / `.pptx`（ZIP + XML）与 PDF 文本层——全部 stdlib，零新依赖。解析不出来时直接说明并给下一步建议，绝不返回乱码。

**图片上限。** 模型能「看见」的图每边 ≤ 3000px；服务端硬上限 8192px（实测裁定：8192 收、8193 拒）。超限的图不注入，并在下一次回复里明确告诉模型「这张图你没看到」，而不是让它编。另有每回合看图预算，到硬上限后续 `view_image` 直接拒绝执行。

**越界与确认。** 命令默认限定在工作区内；跨工作区访问需授权一次并记入 `.wovra/authorized-paths.json`；`rm -r`、`git push/reset` 等破坏性操作走确认门；设备只读白名单允许硬件排障类只读查询，带写意图照旧拦。

**成败判定只有一套口径。** `tools/status.py`（首行锚定 + 结构化 exit_code），CLI、前端、报告、文件账本共用——不靠「正文里出现『出错』字样」瞎猜。

**文件权限守卫。** `tools/permissions.py` 按 agent 归属限制改写删——干不干看有没有权限，不看该不该。

## 设计哲学

**低成本优先** —— 不要把 token 花在维护与当前任务无关的上下文上。

**先隔离，后并行** —— 多个智能体的存在，应当是因为职责或上下文有实质性不同，而不是仅仅因为并行执行看起来很厉害。

**持久状态优于对话历史** —— 工作的当前状态，应当比整段对话的历史更重要。

**人类可读的进度** —— 人类应当能够在不阅读数千条工具调用的前提下，理解一个长时运行任务的状态。

**可恢复性** —— 失败、此前的尝试和决策应当保持可恢复，而不是在上下文被压缩时消失。

**评估独立于执行** —— 执行工作的系统，不应当是判断工作是否成功的唯一裁判。

## 与现有智能体工具的关系

Wovra 不取代现有的编码智能体或工具运行时，它可以作为**它们之上的编排层**：

```
                    Wovra
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   智能体运行时    智能体运行时    智能体运行时
        │             │             │
        ▼             ▼             ▼
      工具           工具           工具
```

这使在不同底层智能体上试验成为可能，而不改变上层的任务组织模型。

- 分域：代码判据 + 活性文件画树；落地增量演进、按名字匹配、永不退休
- 水位折档 + 子 agent 回落 + 观测刷新
- 安全机制：禁写区 + 黑名单 + 敏感确认 + 设备只读白名单 + 过期保护 + 审计 + 原子落盘
- 成本核算：三分账 / 等效输入 / 上下文占用 / 缓存命中，逐轮落盘
- 注册表 ID 体系 v2（主 agent + A/B/C…，子域 A-1/A-1-1），老数据加载期自动迁移
- 人视图前端：六页签 + 顶栏六格 + 维护进度条 + 开放轮续跑 + 工作目录选择器 + 分域生长树画布
- 模型配置页（按渠道商的模型：上下文窗口 / 最大输出 / 视觉 / 思考等级）

未落地：开工前规划闸门、重度场景验证、独立任务评估。

## 实测结论

三代机制实验与对照实验是历史证据。其结论仍指导设计：

**执行期截断是反优化。** 三代机制实测——轮内折叠 39 次重读、2KB 锁孔 11 次沉没读取，零截断后同量级任务 **3 次读取**完成。

**缓存命中率是折扣，基座才是税基。** 对照模式命中率 99.3% 仍会在臃肿基座上付出高昂代价；管理机制的目标是**基座**而非命中率。

**每轮必整理是过早优化。** 14 轮整理 98K token（约 7K/轮，轻轮整理费超过干活费）——V3 改为水位触发批量，V4 干脆用每轮一段话取代整理。

## 开发者须知

**安全层 vs venv。** `run_command` 会拒绝「离开工作区」的命令，包括界内指向界外的符号链接。`uv` 创建的 `.venv/bin/python` 恰恰是这种链接，所以按设计会被拦。改用：

```bash
uv run python -m pytest        # 跑测试
uv run python -m wovra --help  # CLI 冒烟
```

**`tasks/` 只读。** 工作区里的 `tasks/` 是会话记录的真相来源，只由 Runtime 落盘。工具层对它拒写、放读：文件类工具的写/改/替换/恢复/删/移一律拒绝，`run_command` 里「写到 tasks/」的命令也拒绝（不可授权）。读取完全不受限——复盘会话数据不需要额外许可。

## 路线图

**阶段 1 —— 最小运行时。** 用户 → LLM → 工具调用 → 工具执行 → 结果 → LLM。目的是先建立一个能跑通的基础，而不是去优化它。

**阶段 2 —— 任务状态。** 引入持久的目标、需求、状态、报告、历史、验收标准。

**阶段 3 —— 上下文生命周期。** 上下文选择、压缩、折叠、归档、检索与隔离。

**阶段 4 —— 智能体编排。** 基于职责的智能体与受控的任务委托。

**阶段 5 —— 人机协作（大部分已落地）。** `wovra serve` + `webui/` 已提供进度查看、干预、审批、恢复。任务修改与解释性会话仍在路上。

**阶段 6 —— 评估。** 构建独立判定任务是否满足验收标准的机制。

## 长期愿景

Wovra 在探索一个简单的问题：**如果 AI 可以连续工作几个小时甚至几天，那么围绕 AI 的系统应该是什么样的？**

如今的智能体接口往往以对话为中心。Wovra 探索一种以工作为中心的模型：

```
Conversation（对话）
      ↓
      ↓
      ↓
     Task（任务）
      │
      ├── 状态
      ├── 上下文
      ├── 智能体
      ├── 报告
      ├── 历史
      └── 评估
```

长期目标是让复杂的 AI 工作给人的感觉，不再是「我让一个 AI 去做了某件事」，而更接近：

> 我向一个智能系统指派了一份工作，并且在任何时点，我都能理解它、引导它、检查它、恢复它。
