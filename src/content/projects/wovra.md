> 这是一个**合作开发的开源项目**，我与另一位开发者共同开发。

Wovra 是一个实验性系统，用于组织和管理人类与 AI 之间复杂、长时运行的工作。

它不把 AI 智能体视为一段不断累积上下文的连续对话，而是**把一个任务视为一个持久的工作空间**，拥有自己的状态、上下文、进度、历史、智能体、报告和评估。

目标不是让 AI 更聪明。目标是让 AI 的工作变得**可管理、可观察、可引导、可恢复**。

核心主张只有一句：

> **把任务本身，与处理任务所用的对话，分离开来。**

## 为什么需要它

当前的 AI 智能体越来越有能力自主完成复杂任务。但**长时运行**带来的是另一类问题：

- 随着对话和工具调用的累积，上下文持续增长
- 一个微小的改动，可能需要携带大量无关的历史信息
- 失败之后难以回退到某个已知良好的状态
- 人在中间想介入引导时，找不到合适的落点

## 核心思想

### 1. 持久的工作状态

任务并不简单地等同于一段对话。Wovra 为工作维护一份持久的表示：

```
Task（任务）
├── Goal（目标）
├── Requirements（需求）
├── Acceptance Criteria（验收标准）
├── Current State（当前状态）
├── Active Context（活跃上下文）
├── Report（报告）
├── History（历史）
├── Agents（智能体）
└── Evaluation（评估）
```

AI 可以从当前状态出发继续工作，而不必携带此前每一次交互的完整历史。

### 2. 上下文生命周期

并非所有信息都值得留在活跃上下文中：

```
Active Context（活跃上下文）
      │
      ├── 相关信息
      ├── 当前决策
      ├── 当前状态
      └── 近期历史
               │
               ▼
        Archived History（归档历史）
      ├── 此前的尝试
      ├── 工具输出
      ├── 调试日志
      └── 详细对话
```

信息不一定被删除——不必要的细节会被**折叠成紧凑的表示**，需要时重新取回。这让系统不必反复为携带无关历史付代价。

### 3. 基于职责的智能体，而不是「越多越快」

对于简单任务，单个智能体往往更好。只有当任务包含**不同的职责或上下文**时，多个智能体才变得有用：

```
                     Task（任务）
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Agent A     Agent B     Agent C
        规划         编码         测试
          │           │           │
          └───────────┼───────────┘
                      ▼
                  Task State（任务状态）
```

每个智能体在聚焦的上下文中工作，而不是继承主任务的全部历史。所以隔离的目的主要是**职责分离 + 上下文隔离**，而不是并行执行本身。

### 4. 人机对齐

人类不应该需要持续监督每一次工具调用，但应该能在任何时刻了解工作的状态。Wovra 用一份**持久报告**作为人与 AI 之间的共享接口：

```
当前状态：正在实现认证模块。

已完成：API 结构 / 数据库 Schema / 登录端点

当前问题：Token 过期后刷新偶尔失败。

已尝试：复现问题 / 检查中间件注册顺序 / 怀疑是 refresh-token 校验

下一步：排查 Token 校验与过期处理逻辑。
```

这份报告紧凑地回答了：发生了什么？现在在哪？还剩什么？什么在阻塞？接下来做什么？

### 5. 工作与解释是两回事

人类可能会问「这个模块为什么这样实现」或「解释一下当前流水线怎么工作」。这类对话**不一定需要成为任务工作上下文的一部分**。

只有真正改变实际工作的信息——新需求、新决策、新约束、新发现的事实——才应当被提升为持久的任务状态。这样探索性的对话就不会污染执行上下文。

### 6. 独立评估

一个智能体不应当是判定自己工作是否完成的唯一权威：

```
Execution（执行） → Agent 产出结果
                          │
                          ▼
                  Evaluation（评估）
                      ├── 接受
                      ├── 需要修改
                      └── 失败
```

验收标准可以独立于智能体自己的声称来评估。这让长时运行的工作更容易验证和恢复。

## 架构

```
                    Human（人类）
                      │
                 需求 / 反馈
                      ▼
              ┌───────────────┐
              │     Wovra     │
              │  任务管理      │
              │  上下文        │
              │  状态          │
              │  报告 / 归档   │
              │  评估          │
              └───────┬───────┘
                      │
                智能体编排
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Agent A     Agent B     Agent C
                      │
                      ▼
              现有智能体运行时
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        文件        Shell        工具
```

**Wovra 专注于 AI 工作的组织与生命周期，而不是重新发明每一个底层能力。** 现有的智能体运行时和成熟的工具实现都可以作为它的底层。

### 代码结构

运行时按职责组织，每个模块只做一件事：

```
src/wovra/
  agent/          Agent 运行时（由四个 mixin 组装）
    core.py         运行循环、轮生命周期、工具分发、用量记账、轮闭合结算链
    assembly.py     共享历史装配（段落档 + 近期原文）、fork 基线、路由裁剪
    maintenance.py  水位闸门、每轮结算、折档线、分域、增量落地、回落
    ledger.py       todo（大步/小步）、notify/consult、提交守卫
    prompts.py      模型可见的提示词与工具 schema（纯数据）
  tools/          内置工具箱
    safety.py       工作区属主、路径防护、确认门、禁写区、设备只读白名单
    files.py        读/写/改/删/移/回滚、搜索、检查点
    documents.py    附件原生解析：docx/xlsx/pptx/pdf/csv（纯 stdlib）
    shell.py        run_command、进程树强杀
    abort.py        协作式中断（卡住的工具调用也能中途停掉本轮）
    web.py          web_search / web_fetch（含 SSRF 防护、正文提取、结果缓存）
    eyes.py         截图 / 看图 / 页面文本
    limits.py       工具输出的统一上限与超限落盘
    status.py       工具结果成败判定的唯一权威口径
  task.py         持久任务树（Task、TaskState）
  lifecycle.py    文件生命周期账本
  llm.py          模型客户端（所有模型调用的唯一出口）
  pathmatch.py    路径的鲁棒匹配（模型抄的路径形态归一）
  economics.py    分域经济判据（该不该裂、在哪层裂）
  serve.py        Web 服务（HTTP API + 静态前端）
webui/            人视图前端（纯静态：index.html + vendor）
```

### 上下文模型（现行版）

以**一份共享历史**为中心：

- **取消重组**：历史不再按域重切，所有 agent 读同一份共享历史——折过的轮变段落，近轮保持原文
- **每轮一段话**：轮闭合时结算成一段话（问什么 → 干了什么 → 卡在哪 → 结论），追加进共享历史
- **分域 = 按活性文件画树**：分不分由**代码**判（某条工作线装配体量 ≥ 水位，且活性文件按同轮共现能分成 ≥2 簇）；模型只画结构树。落地是**增量演进**——按名字匹配既有条目就地更新，不退休任何既有条目，树只长不改
- **首次激活才 fork**：未激活的子 agent 共享公共上下文（零成本待命）；它第一轮真正干活时才 fork，之后看「自己未折的轮全量 + 别人的段落」
- **水位驱动折档与回落**：公共线到 40% 水位就折叠，只保留最近 50 轮；已激活的子 agent 到水位则**回落**为「当前公共上下文 + 自己的职责」，重建基线而不是自己折

## 设计哲学

| 原则 | 含义 |
|---|---|
| **低成本优先** | 不要把 token 花在维护与当前任务无关的上下文上 |
| **先隔离，后并行** | 多智能体的存在应当因为职责或上下文有实质不同，而不是并行看起来厉害 |
| **持久状态优于对话历史** | 工作的当前状态，应当比整段对话的历史更重要 |
| **人类可读的进度** | 人应当能在不读数千条工具调用的情况下，理解长时任务的状态 |
| **可恢复性** | 失败、此前的尝试和决策应当保持可恢复，而不是在上下文被压缩时消失 |
| **评估独立于执行** | 执行工作的系统，不应当是判断工作是否成功的唯一裁判 |

## 几个值得说的工程细节

这些是项目里我印象最深的部分，也是它区别于「演示级 agent」的地方：

**工具输出版本不丢文本**：输出上限 20 万字符，真超限时返回开头预览 + 原文体量 + 落盘路径，随时能读回。

**`tasks/` 是禁写区**：会话数据是运行时的真相来源，工具层对它**拒写放读**，而且**不可授权**——越界访问可以授权一次，禁写区不行。

**成败判定只有一套口径**：由 `tools/status.py` 统一裁定（首行锚定 + 结构化退出码），CLI、前端、报告、文件账本共用，不再靠「正文里出现『出错』字样」瞎猜——那会产生大量假阳性。

**网页检索摊到多家免费额度上**：支持多家搜索 API，每次检索**随机**挑一家先试，失败就换下一家，而不是只烧第一家的额度。一家都没配时退回本地抓取，并在结果里**标注「本地兜底、没有相关性保证」**——因为一句光秃秃的「未找到相关结果」会被模型读成「网上没有这个东西」。

**图片上限与「你没看到」**：模型能「看见」的图每边 ≤ 3000px，服务端硬上限 8192px。超限的图**不注入**，并在下一次回复里明确告诉模型「这张图你没看到」，而不是让它编。

## 实测得出的三条结论

三代机制实验与对照实验得到的结论（支撑了当前的设计）：

1. **执行期截断是反优化**：轮内折叠导致 39 次重读、2KB 锁孔 11 次沉没读取；零截断后同量级任务 3 次读取完成
2. **缓存命中率是折扣，基座才是税基**：命中率 99.3% 仍会在臃肿基座上付出高昂代价，管理机制的目标是基座而非命中率
3. **每轮必整理是过早优化**：14 轮整理花了 98K token（约 7K/轮），轻轮的整理费超过干活费——后来改为水位触发批量，再后来用每轮一段话取代整理
