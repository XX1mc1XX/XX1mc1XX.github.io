## 这个项目解决什么问题

工业现场选相机不是一次性的。产线扩一条，可能要加第二台；客户指定品牌，可能这次要换一家；同一台设备出个新型号，参数表就变了。而每接一个新品牌，传统写法要把上层的参数面板、图像链路、状态管理挨个改一遍——**改动点散在二十来处，改完重测重发**。

ZyClear 要解决的就是这件事：**把厂商差异关进实现层**。换品牌、加型号、加面板都变成增量动作，其余代码对品牌完全无感。

核心做法是六层单向依赖 + 一整套契约：契约层定能力边界，适配器把各家 SDK 的差异吃掉，门面往上只暴露与品牌无关的接口。上层拿到的是「一台相机」，不知道它是哪家的。

这套结构不止能装相机——**设备轴可以平移到 PLC、运动控制卡，应用轴整包搬迁**，这是它和一次性项目的区别。

## 一、架构设计与复用

### 1. 六层单向依赖架构

契约层、实现层、门面层、模型层、交互层、资源层逐层隔离，依赖倒置、单向向下，变化点向内收敛。

![六层单向依赖：变化点全部向内收敛](/images/zyclear/六层依赖.svg)

三条核心约束**可用 grep 当场验证**——门面层不出现任何适配器头文件、面板之间零相互引用、交互层零厂商判断：

```bash
grep -rn "HikCamera.h\|VirtualCamera.h" src/CameraInterface/     # 期望无输出
grep -rn "ControlWidget\*" src/ParamWidget/ src/ViewWidget/      # 期望无输出
grep -rniE "hikrobot|\"Hik\"|MV_CC_" src/ControlWidget/ src/ParamWidget/ src/ViewWidget/   # 期望无输出
```

**全仓厂商条件编译仅 2 处**，且都落在工厂的注册与枚举。

### 2. 契约先行与硬件无关的能力边界

**17 个纯虚方法**覆盖设备全生命周期、参数读写、图像获取三域；统一门面以「序列号 → 设备对象」映射收口多机寻址与对象生命周期托管，交互层全程只凭序列号寻址、不感知品牌。

新品牌接入由**侵入式改造**降级为**增量式扩展**：改动点由约 20 处收敛到 1 处，门面、参数面板、图像链路零改动。

![接一个新品牌要改几处](/images/zyclear/换品牌成本.svg)

### 3. 设计模式体系化治理变化点

| 要解决的 | 用的手段 |
|---|---|
| 创建解耦 | 工厂按厂商名登记创建器与枚举器 |
| 入口收敛 | 门面 |
| 异构适配 | 适配器把厂商 SDK 差异封在实现层 |
| 事件分发 | 发布-订阅总线 |
| 对象复制 | 参数原型克隆 |
| 数据视图分离 | Model-View-Delegate |
| 树形组合 | 参数分组树 |
| 全局资源治理 | 单例托管注册表与门面 |
| 高吞吐削峰 | 有界双队列 |

选型的唯一判据是**变化点是否被隔离**。

### 4. 参数能力由代码资产转为配置资产

参数定义建模为「**6 种参数类型 × 5 个业务分组 × 37 项 Schema**」，配置解析与界面渲染彻底隔离，视图**运行时动态装配**。

新增型号**不编译、不发版**，改 JSON 分钟级生效——不再触发编译发版流程。

### 5. 参数权限闭环自动推导

打通 GenICam 访问模式（`RO` / `RW` / `WO` / `NI` / `NA`）到界面语义的映射链，参数的**有效性、可读性、可写性三态**由设备实时上报、逐项自动判定：

- 只读项在**模型层**即被拦下——视图连编辑控件都不会创建
- 不支持项静默剔除
- **参数界面不含任何硬编码权限判断**

## 二、图像链路与性能优化

### 1. 像素格式归一化

覆盖 **36 种** GigE Vision 像素格式（Mono / Bayer / YUV / BGR 各族）判定，借 SDK **硬件转换通道**统一归约为**灰度与彩色两种形态**，上层图像链路与像素格式彻底解耦，且转换失败不产出半成品帧。

### 2. 高吞吐图像缓冲层

空闲 / 工作**双队列**复用 + **保新弃旧**（满队列丢弃最旧帧并回收其缓冲，保障预览实时性），取帧带**超时保护**、归还闭环回收、**稳态零堆分配**。

采集回调、有界缓冲队列、独立采集线程、界面渲染**四级异步隔离**，持续满帧下界面不阻塞、无延迟堆积。


![一帧图像的四级异步隔离](/images/zyclear/图像缓冲链路.svg)

### 3. 发布-订阅总线消除面板网状耦合

跨面板联动收敛为 **6 类语义事件**按位掩码定向投递，模块间**零直接引用**，新增面板与事件类型不触动既有业务。

配套 **15 类错误码 + 成功码**的统一错误模型，异常收口至**状态栏 + 模态**两级触达。

![面板联动：从网状耦合到一处收口](/images/zyclear/事件总线.svg)

## 三、工程化与效能提升

### 1. 界面即代码替代可视化拖拽

全仓**零二进制窗体**，布局骨架、弹性策略、主题钩子**全量代码显式声明**，消除生成代码**不可读、不可评审、不可合并**三个问题。

参数区仅保留空壳视图，**6 类编辑控件**按类型运行时挂载，界面层对参数规模**完全无感**。

### 2. 状态驱动的交互互锁

拉流期间参数面板**自动整面禁用**，断连、重枚举与切换相机**自动清空脏帧与旧参数**。

交互可用性由设备状态事件**单向推导**，非法操作序列在架构层被排除，而非依赖人工纪律。

### 3. 设备独占与幂等重入

连接前判定设备**独占占用**、异常接入**显式降级为可读错误**；重复枚举自动停流、断连、逐台重建注册表，句柄与设备占用无残留。

设备信息**值拷贝自持**，不引用 SDK 枚举列表内部内存；SDK 运行日志**定向落盘**，现场故障可回溯。

**SDK 那些没有文档、只能靠读断言才知道的约束**，全部显式化到适配层：结构体必须清零初始化（否则未定义字段带着栈上的垃圾值进去）、联合体的分支要靠标志位判定而不是猜、厂商名要做逐字匹配（大小写和空格都不能差）、进程级日志打点要显式开关。这些不是「写得好看」的问题——它们中的任何一条没满足，症状都是设备打不开或者行为诡异，而报错信息不会指向真正的原因。

### 4. 虚拟设备抽象（同构仿真）

与真机共用同一套契约与同一个图像缓冲队列，开发、调试、演示、压测、持续集成**全程无需真机**——硬件采购成本归零，硬件依赖降级为可选项。

### 5. 声明式构建与依赖管理

源码清单、依赖声明、资源打包、交付路径**全部代码化**，元对象与资源编译**全自动托管**；**3 个项目自定义缓存变量**覆盖全环境差异，**官方包优先 + 手动兜底**双路径依赖探测，调试 / 发布构件自动二选一，产物集中落盘、整体可搬运。

### 6. 多环境自适应兼容矩阵

OpenCV 多部署形态、硬件 SDK 缺失**降级为纯仿真仍可构建可运行**、操作系统差异**三维覆盖**，交付物**单一、可复现、可搬运**。

CI 即在**缺失厂商 SDK 的降级配置**下构建并跑通全部测试。

### 7. 运行时装插件平台

面板契约与注册表分离，主程序启动时扫描目录、以 **QLibrary 装载动态库**挂载面板，新增面板**不重编主程序**。

插件接口只导出**纯 C 符号**（`extern "C"`），规避 C++ 类无稳定二进制布局导致的 ABI 断裂。

**QDockWidget** 停靠体系支持任意边停靠、浮动成窗、关闭后从「视图」菜单恢复，工具栏按钮随面板实际停靠位置自动重排；注册表按唯一 ID 去重、同名注册被拒。附**独立示例插件工程**。

## 四、AI Agent 集成与质量保障

### 1. 设备能力自动工具化

接入 [agent4cpp](/projects/agent4cpp/)，把相机全生命周期能力注册为 **10 个 LLM 可调用工具**（枚举 / 连接 / 读写参数 / 拉流 / 画面量化分析），工具带用途描述与参数 Schema，自然语言即可驱动。

工具提供者以**四方法接口**抽象，**通用 AI 层不含任何相机知识**，领域绑定收口在唯一的宿主适配层，`Extension` 目录**整包可移植**到其他客户端。

同一 agent 核心另供**无头控制台模式**，命令行复用全套工具与会话历史；AI 依赖缺失时构建**自动降级**，主功能不受影响。

**这一层对原有代码的侵入度**：现有 27 个编译单元**一行不改**，AI 层只在 `src/AiAgent/` 下新增文件，改动既有文件**仅 3 处**（构建脚本加一个可选的依赖探测、主窗口两处挂载、README）。所以它可以被整包删掉——删掉它就是原来的项目。这是把 AI 当插件而非改造工程来做的直接结果。

![同一套门面，两个入口](/images/zyclear/双通道.svg)

### 2. 面向 LLM 可靠性的工程处理

**超范围拒绝而非静默钳位**——参数写入前用设备上报的 min/max 与枚举可选值校验。钳位会让模型以为写进去的就是它要的值，后续推理全建立在错前提上。

**写后回读确认**，把「请求值 / 实际生效值」并列回传。

**失败可自恢复**——工具执行失败同样回灌错误状态与结构化结果，驱动模型下一轮自我修正；步数上限兜底防调用不收敛。

**不碰线程安全**——工具回调经阻塞队列切回主线程串行操作设备，避免给整个相机层加锁。

配套本地文档导入 → 切块 → **top-k 检索**灌注，多轮会话历史 JSON 落盘。

### 3. 单元测试守住无硬件可测面

**114 个用例**覆盖图像缓冲队列（双队列复用 / 保新弃旧 / 超时归还 / 稳态零分配）、参数模型（类型判定 / 权限三态 / 整包写回）、JSON Schema 解析、事件总线、相机工厂与门面。

**刻意只选不含硬件依赖的纯逻辑组件**——无需相机与海康 SDK 即可编译运行。注册进 CTest 并与主程序共用运行时目录，**虚拟设备 + 单元测试**构成不依赖真机的双层保障。

## 五、注释补齐时挖出的 7 个静默缺陷

项目收尾阶段做了一次全量注释补齐，注释率由 **2.3% 提升到 11.2%**，41 个零注释文件清零。

真正的收获不是注释本身。逐文件复述「这段为什么这么写」的过程，逼出了 **7 个既不导致编译失败、也不易从代码本身读出的缺陷**：

| 缺陷 | 表象 | 根因 |
|---|---|---|
| 门面丢弃关键返回值 | 启动采集失败被当作成功 | `startGrabbing` / `destroyStream` 返回值未接收，紧随其后的判断检的是**上一次**调用的结果 |
| 门面泄漏设备句柄与相机对象 | 每轮枚举泄漏一份 | 析构与重枚举只做了停采断连，未回收 SDK 句柄、未销毁相机对象 |
| 适配器漏认 `RGB8_Packed` | 帧在下游被静默丢弃 | 它恰是本层转换的**目标**格式；相机一旦把 `OutputFormat` 设为 RGB8，两个判定同时落空 |
| 虚拟相机序列号与显示名互换 | 对外语义错，功能却自洽 | 聚合初始化按 `{名称, 序列号, 厂商}` 传参，而结构体声明为 `{Serial, UserDefineID, VenderName}` |
| 事件总线漏拆一个事件位 | 订阅方不报错、永远收不到 | `registerMessage` 缺一个分支 |
| 枚举控件写回错误编码 | 落到磁盘的选项是错的 | 取值取自下拉框**下标**而非相机侧编码表，两者只在编码连续时相等 |
| 模型与面板缺索引防护 | 根节点被写坏 / 越界 | 无效索引经 `getItem()` 回落到根节点；空选择走到 `QList::first()` |

这几处的共同点是：**它们全都能编译通过，有的功能表面上还正常**（序列号互换那个字段反了但自洽）。只有把「这里本来想做什么」写出来，才发现写出来的和想做的不是一回事。

注释遵循统一口径——**只写「为什么」与契约语义**（前置条件、返回值口径、所有权归属、线程约束、厂商 SDK 的坑），不复述代码本身。挖出的缺口随后**固化成单元测试记录**：修正时对应用例会失败并提示更新，防止回归。

| 界面卡顿 | 采集阻塞主线程 | 四级异步解耦 | **满帧零阻塞** |
